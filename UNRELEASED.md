# Unreleased changes · 未发布的更新

**English** · [简体中文](#简体中文)

What is already done for the next version, **0.3.4**, and not in a release yet. When that version is published, this list becomes its release notes and the file starts over.

### What's new

- **Light theme.** SpaceKnife now has a light theme and follows your system's light or dark setting by default (**Settings › Appearance › Theme**: Match system, Light, Dark). The treemap, the flame graph and the polar flame graph change with it, and file classes keep their colors where they can. Switching takes effect at once, with no white flash, and the next start opens in the theme you chose. On Windows, **Match system** follows the default app mode. In a browser (headless mode) it follows the browser, and a reload opens in the theme you chose. A class color you pick in **Settings › File classes** applies to the theme you are in; tick **Also apply to the other theme** to use it in both. A built-in class you recolored can go back to its default color with the button next to **Delete**. Colors you picked before this version are kept for both themes.
- **Portable versions for ARM.** Windows 11 on ARM and ARM Linux (arm64) get the portable versions too: `SpaceKnife-<version>-win-arm64-portable.zip` and `SpaceKnife-<version>-linux-arm64-portable.tar.gz`, the same as the x64 ones (unpack and run, data in the `data` folder next to the program). An x64 portable copy on Windows on ARM, which Windows ran emulated, moves to the ARM build with its next update. The installers stay x64 only.
- **A portable version for macOS.** `SpaceKnife-<version>-mac-arm64-portable.zip` (Apple Silicon) and `…-mac-x64-portable.zip` (Intel): unzip anywhere and open `SpaceKnife.app`; snapshots, settings and everything else stay in the `data` folder next to it, nothing goes to your user Library. Keep the two together. Opened straight from where it was unzipped, macOS may run the app from a hidden copy (App Translocation); SpaceKnife still finds its `data` folder. **Seamless update** works for it as for the Windows and Linux portable versions. Like the dmg, it is not notarized yet: allow it once in **System Settings › Privacy & Security**.
- **Disks** keeps what a complete scan of a whole volume showed (its file classes, largest folders, counts and scan time) per volume, so the volume still shows them after you leave the page, close the scan's tab, reload the window or restart SpaceKnife, until the next complete scan. Only the same volume gets them back (drive letter or mount point and volume serial), so another drive on the same letter never does.
- **Disks** has a big **File classes** bar at the top: the classes of every volume with a known mix added up, with each class's size and share, and which volumes it covers.
- The help page **Visualizations** explains how the treemap, the flame graph and the polar flame graph each organize the picture, with a table that sets them side by side. The polar flame graph reads like a stacked pie chart with no center area: each ring is one folder level, the angle is the share. A picture of each shows on that page, in the app's help as on the website, and on the website's home page.
- **New switch: Keep large scans in mapped files** (**Settings › Advanced › Memory**, off by default). When on, a scan of more than about two million items keeps its data in memory-mapped files in the cache folder instead of private memory; the system keeps the parts in use in RAM and can drop the rest at any time. On a drive of 3.2 million items the backend then settles at about 250 MB instead of about 600 MB, and peaks at about 400 MB while scanning instead of about 750 MB, at the same speed. The cost, and why it is off by default: after a scan its data is written to those files once, about 200 bytes per item (about 1.8 GB for a drive of 8.6 million items).
- **Command line: `scan --mft`** reads the $MFT of a whole local NTFS drive, the app's MFT quick scan, instead of listing it folder by folder (Windows; asks for administrator rights once). It is off by default. A path it can't read that way (a folder rather than a whole drive, a ReFS, FAT, exFAT or Btrfs drive, a network drive, several paths at once) is scanned folder by folder anyway, after a line that says why, and so is a drive whose administrator prompt you refuse. The scan result says which way the drive was read.

### Fixes

- **SpaceKnife refuses the compromised eMudhra certificates.** In October 2026 it came out that the private keys of eight intermediate certificates of eMudhra, a certificate authority in India, had been generated wrongly in 2025: each was a small number instead of a random one, so anyone could work it out from the public certificate and use it to issue certificates for any website. Firefox, Chrome, Apple and Microsoft blocked the eight certificates between 17 and 20 October; Mozilla and Google also withdrew trust in the root that issued them, emSign ECC Root CA - G3, and Linux distributions such as Ubuntu and SUSE removed it from their certificate packages. SpaceKnife now ships Electron 44.9.3, whose Chromium and Node.js refuse the eight certificates; SpaceKnife's window shows only the app's own pages and makes no connections of its own to the internet, so it was not exposed. The update check, which connects only to GitHub, now has Windows and macOS verify the certificate themselves, so it refuses certificates the system has blocked, these eight included; before, it checked a certificate against the trusted root certificates only, without the system's list of blocked ones. On Linux it uses your distribution's certificate bundle as before: keep the ca-certificates package up to date.
- **Hard scans decide for themselves how many folders they read at once.** The native scanner now keeps one set of listing threads per process, and decides how many folders they list at once: as many as the CPUs SpaceKnife may use (2–16; twice that on macOS), at least 32 while the folders have to be read from the disk, and fewer where fewer list faster. It now counts only the CPUs it may use: under a CPU affinity or a container's CPU quota it no longer starts 16 listing threads on 4 cores, and its other thread pools follow the same count. The disk load limit still holds: no more folders are read at once than it allows, and a paused scan starts no new reads. With the folders in memory, on a 32-core PC, an NTFS drive of 1.9 million items takes 2.1 s instead of 2.6 s with 17 % less CPU time, and the other folders tried are 11–25 % faster; held to 4 cores, a scan uses 4–12 % less CPU time. Read from the disk (the file cache emptied first), on the same PC with NVMe drives, the NTFS drive takes about 7.7 s instead of 11.4 s and a ReFS drive of 3.2 million items about 22 s instead of 35 s; a WinBtrfs folder on 4 cores takes about 2.3 s instead of 4.3–5.7 s. What a scan finds is the same, whatever the number of folders read at once.
- **Small changes in the dark theme that come with the light one.** The icon on a file's class color in the details panel and the results list is white on audio, documents, games and other files, so it is readable there; the update badge's text on hover and while downloading is easier to read; scroll bars, drop-down lists and check boxes are dark too. The selected block in the treemap is no longer darkened by its own shadow, nor are the blocks inside it. With an accent color other than the default, the compare view's **New** badge, the highlighted suggestion under the filter box and the part of the filter still being typed are in that color too, instead of periwinkle. On the bars the flame graph and the polar flame graph light up around the selection, the size is in the same color as the name, so it stays readable. The log's error level stays readable on the row under the pointer.
- **Settings › File classes:** a click on the left end of a class's name no longer opens the color picker.
- **The block under the pointer stays lit while the view updates.** With live monitoring of a busy drive, every change redraws the view, and the block under a still pointer lost its highlight and the light around its folders until the mouse moved; the hover card's dates and type also went blank for a moment each time. Now the highlight, the light around it and the card stay through every new picture, with the new numbers, and so does a row lit from the results list. The comparison view's hover card no longer flickers either while a live comparison updates.
- **Hard scans on Windows count size on disk as the file system does, and drives with many sparse or compressed files scan much faster.** On local NTFS, ReFS and WinBtrfs drives a file's size on disk now comes from the folder listing, which holds the file system's own count; before, every sparse or compressed file was opened by its full path to ask (on the benchmark tree, 12.8 s of a cold scan). Only a sparse or compressed file written in the last minute, whose listing can still show an old value, and a file compressed by Windows (WOF) are still asked. The count changes where the old estimate was wrong: a small file kept inside its NTFS record (about 513 to 700 bytes) and a ReFS file small enough to be stored inline (under about 1.5 KB) now take 0 bytes instead of one cluster, as they do in the MFT quick scan. FAT, exFAT and network drives are counted as before.
- **The command-line scan starts and finishes faster.** It loads only what a scan needs, and the frozen backend no longer loads the packaging tool setuptools at every start; it ends as soon as its output is written. Scanning an empty folder takes about 220 ms instead of 410 ms on Windows and 120 ms instead of 240 ms on Linux. The output is the same.
- **Hard scans on Linux make one system call fewer for most folders.** A folder you own is opened so that its access time stays as it is straight away, instead of being opened and then changed.
- **Live monitoring on Linux no longer misses changes made right after a scan.** A scanned folder gets its watch a moment after the scan read it, and a file created, deleted or renamed in it in that moment never reached the tree: a file written into a folder just as a scan finished stayed missing until that folder changed again or you rescanned. Now, once a folder's watch is on, its modification time is checked against the one the scan recorded, and a folder that changed is read again. Polled folders (network drives, or folders beyond the inotify watch limit) get the same check, on macOS too. A file that only changed size in that moment still shows its old size until it changes again.
- **A long job on one scan no longer holds up the others.** While something read a large scan for a long time, a file change on a monitored drive waited for it, and every picture, summary and new view waited behind that change: a scan started meanwhile seemed to hang for minutes before it showed anything. Now only the change waits for the long job; everything else goes on.
- **Thin scroll bars everywhere.** Every scrolling area, such as the start page's list of drives and the **Disks** page, now has a thin rounded scroll bar without arrows or a track, which widens under the pointer, in both themes, instead of Windows' wide gray bar.
- **Hard scans on Windows write far less to the drive.** Listing a folder used to update its last access time, so on a drive that keeps access times, one hard scan of a drive of 8.7 million items wrote 1.5–3.3 GB and left every folder looking as if it had just been opened. Now folders are opened so that their access times stay as they were. Where that is not allowed, a folder is opened as before: on a read-only drive, for a standard user in system folders, and even for an administrator in folders only Windows itself may change, such as `C:\Windows\WinSxS` (about one folder in six on a system drive, so a hard scan of the whole system drive still writes about 0.25–0.7 GB).
- **Hard scans on Windows are faster.** A folder found during a scan is now opened from its parent folder, which is still open, instead of from the root of the drive again. With the folders in memory, a ReFS drive of 3.2 million items takes about 3.8 s instead of 5.2 s, and an NTFS system drive of 8.8 million items 12.6 s instead of 13.1 s. This is done on NTFS, ReFS and WinBtrfs drives, where it was measured to be faster or as fast; on other file systems and network drives folders are opened as before. Every folder opened this way is checked to be the one its parent listed (the same file ID); one that does not match is opened from the root as before, or by its file ID when its name turns out to lead to another folder. What a scan finds is the same: on an NTFS, a ReFS and a WinBtrfs drive, scans with and without it were compared folder by folder, on the NTFS drive also with what the disk itself holds.
- **Hard scans on Windows no longer open folders the slower way on drives that do not keep access times.** On drives where Windows does not update access times anyway (ReFS by default, NTFS when `fsutil behavior set disablelastaccess` is 1 or 3), folders are no longer opened in the slower way that keeps their access times. After you turn access-time updates off, until Windows restarts (that is when the setting takes effect), a hard scan of such a drive can update folders' access times as scans did before 0.3.4. What a scan finds is the same: on NTFS, ReFS and WinBtrfs drives, scans of whole drives were compared folder by folder with scans before the change.
- **Hard scans build the tree without holding up the folder listing.** The folders a scan lists are now added to the tree natively, in one pass during which the listing threads carry on, instead of with dozens of Python steps for each batch. A warm scan of a Linux system of 770,000 items takes 0.26 s instead of 0.34 s. On Windows, together with the change above, a ReFS folder of 1.4 million items in memory takes 0.50 s instead of 0.65 s and a WinBtrfs folder of 380,000 items 0.29 s instead of 0.31 s; an NTFS system folder takes as long as before. How much it gains depends on whether adding to the tree was the slowest part: on the same ReFS folder at another time, when listing it was, the time stayed about the same with about a tenth less CPU. Read from the disk (cache emptied first), `C:\Users` with 7.7 million items takes 14.9 s instead of 15.8 s.
- **On Linux the backend keeps about half as much memory after a scan.** The C library kept the memory a scan had freed in some thirty separate pools, between blocks still in use, and could not give it back. SpaceKnife now has glibc map large blocks on their own and use at most four pools, and hands the free pages back after a scan and while idle. After a scan of about 700,000 items the backend settles at about 170 MB instead of about 310 MB, with the same scan speed. Other C libraries, such as musl, are left as they are.
- **Saving a snapshot needs about a tenth of the extra memory and is two to three times faster.** Every finished scan is saved as a snapshot; the whole compressed snapshot used to be built in memory before it was written, with room as large as the data itself, so for a moment the backend needed about as much again as the scan: on a drive of 8.9 million items 1.0–1.4 GB more, which was the highest point of the whole scan. It is now compressed piece by piece straight into the file: about 0.1 GB more, in 0.8 s instead of 2.8 s on a computer with 32 logical CPUs (the old way used one compressor thread per logical CPU; with four it took 1.7 s). A snapshot saved while live monitoring changes the tree, as after a scan of a busy drive, is no longer written half from before and half from after a change, which could leave a snapshot that does not open: it is saved again, with the changes held back for that second or so. Snapshot files are the same as before, and older versions read them.
- **Hard scans of WinBtrfs drives no longer mix up folders whose names differ only in case.** Linux lets folders such as `a` and `A` sit side by side, and a WinBtrfs drive shows both, but opening either by its name reached the same one: one of them was counted twice and the other's contents not at all, without any warning (the test drive has 102 such pairs; one terminfo folder was missing 335 files). Now each folder is opened as the one listed, by its file ID where its name leads to the other, so each is counted with its own contents. Folders whose Linux names have a backslash are listed the same way. Those with a colon or another character Windows names cannot hold cannot be opened from Windows at all, not even by file ID, so they still show as unreadable, now with a message that says why instead of "path not found". Deleting an item or moving it to the trash is refused, and nothing is touched, when its path would open another item that differs from it only in case; items whose name another item in the same folder has exactly (Linux names that are not valid text show with a � and can look alike) or whose name has a character no path can hold (a backslash, a colon and the like, which Linux names may have) can't go into the delete basket, as no path leads to them alone. Without the native extension such folders show as unreadable instead of with the wrong contents. Such a folder is not read again on its own: a refresh or live monitoring keeps it as the last scan listed it. A new scan that starts at the folder itself, or at a folder inside it, still reaches the other one, and so do Explorer and a copied path; scan the folder that holds both instead.
- **Folders whose names end in a dot or a space are listed correctly without the native extension, and deleting one no longer deletes another.** Windows drops that last character from such a path, so the folder `odd.` was listed with the contents of the folder `odd` beside it, and deleting `odd.` after a hard scan deleted `odd`. Deleting such an item or moving it to the trash, or adding it to the delete basket, is now refused, and nothing is touched.
- **Hard scans on Linux keep folders' access times.** Under `relatime`, the usual default, the first scan of a day rewrote the inode of every folder not opened for a day. Now the folders you own are listed so that their access times stay as they were (on the test system, 33,000 of 47,000 folders: your home folder and its caches). Folders owned by someone else, such as system folders for a standard user, are listed as before.
- **Hard scans on Linux and macOS no longer leave out folders with very long paths.** A folder whose path was 4,096 bytes or longer (1,024 on macOS) could not be opened by its path, so it was shown as inaccessible and nothing below it was counted, although it was there to list. Such folders are now opened a piece of the path at a time and listed like any other.
- **Scans of folders with many hard links are faster.** Counting each hard-linked file once was worked out in Python, about 0.5 µs per linked file; it is now done natively. A warm scan of a Linux system of 600,000 items, 160,000 of them hard links shared by uv's cache and virtual environments, takes 0.29 s instead of 0.37 s.
- **Closing a tab while its snapshot loads no longer keeps the scan in memory.** A snapshot that finished loading, or a scan that started, after its tab was closed stayed in the backend with no tab until SpaceKnife quit (about 1.1 GB for a snapshot of 8.6 million items); a started scan even kept running. Now it is freed at once.
- **The toolbar fits narrow windows.** In a window narrower than about 1,400 px the toolbar's right end was cut off: at the smallest window size the split, command palette and delete basket buttons were out of reach, and the path could disappear. Now the filter box shrinks first, then the chips show only their swatch, and the coloring, the chips and last the visualization switch move into a new **More** (…) menu, so every control stays reachable at any window size, in a comparison too.
- **MFT fast scans are about four times faster.** Reading the $MFT now keeps several large reads in flight at once and parses what comes in on all cores, and the tree is built natively instead of in Python. On a system drive of 8.9 million items, a fast scan at the default load level takes about 4.7 s from start to finished tree instead of about 19 s (reading 7.2 s → 2.8 s, building the tree 12 s → 0.4 s). How many reads are kept in flight is found while reading: a drive already at full speed with one or two (such as a SATA SSD) keeps just those, so other programs do not wait behind a long queue, and a fast NVMe drive gets more. With a load limit set, the scan keeps the drive busy just that share of the time. The result is the same, item for item.
- **MFT fast scans need far less memory at their peak.** Building the tree of a large volume used to take about 325 bytes per item on top of the table read from the $MFT, for a moment: on a drive of 8.6 million items the backend reached about 3.6 GB (SpaceKnife as a whole 3.8 GB). It now takes about 57 bytes per item (about 0.5 GB on a drive of 8.9 million items). On that drive the backend's highest point during the scan, about 1.9 GB, is now the moment the last of the table arrives, and the tree is built at about 1.5 GB. The administrator helper that reads the $MFT peaks at about 1.65 GB there instead of about 2.85 GB.
- **Memory no longer jumps every few seconds while files change after a scan.** With live monitoring on, every batch of changes made the details panel work out the whole drive's summary again, often several at once, each needing about 100 bytes per item for a moment (about 0.85 GB on a drive of 8.6 million items); and the first change after a scan doubled the memory of the scan data for good. Now the summary is worked out in small pieces, once for everyone who asks for the same one, and refreshes less often on large scans (at most every 10 seconds); a change adds only a little room. On a drive of 3.2 million items with files changing for a minute, the backend's peak went from about 1.3 GB to about 660 MB (about 300 MB with **Keep large scans in mapped files** on), and it settles at about 600 MB instead of 835 MB.
- **Scans moved to memory-mapped files write half as much to disk.** Once the scan data passed **Scan data memory limit**, each mapped file was first filled with zeros on Windows, and copied to a new file every time it grew. Now the files grow in place and only the data itself is written: on a drive of 3.2 million items about 0.67 GB instead of about 1.3 GB.
- **Live monitoring no longer makes memory jump by gigabytes after a while.** Once many files had changed, the backend renumbered the whole tree, and for a moment needed about 760 bytes per item on top of it: about 6.3 GB more on a drive of 8.7 million items. It now needs about 1 GB, the size of the renumbered copy itself, at the same speed.
- **Opening a snapshot needs half the memory.** Each column was first unpacked into a temporary copy, so a snapshot of 8.7 million items briefly needed 1.8 GB for the 0.95 GB it keeps. Now it is unpacked straight into place and needs just the 0.95 GB.
- **The backend keeps less memory all the time.**
  - About 50 MB less: the command palette's pinyin search no longer loads a Chinese dictionary when SpaceKnife starts.
  - 8 bytes less per item while a scan is open (about 66 MB on a drive of 8.6 million items): the treemap and the palette work out sizes only for what they show, instead of an array for every item that was worked out again after every file change. The treemap also redraws faster after a change.
- **A hard scan of a drive scanned before sets its memory aside once,** from the number of items the last complete scan found, instead of growing it step by step and copying everything each time.
- **The window gives memory back when it is hidden.** A minimized or covered window releases its drawing surfaces and draws again when it shows. Moving the pointer over the treemap now reuses the same buffers, so it no longer allocates new memory every time something lights up.
- **The details panel and the picture no longer fail now and then during a hard scan.** A summary in the details panel or an update of the picture could fail while the scan added items, and some files could show the wrong color (by their extension instead of the class of the folder they are in, such as a game or a project) until the scan listed more folders, or even after it ended. Which class each item takes from its folder is worked out while the scan goes on, and the newest items could be counted as done without being worked out; now they never are.
- **The details panel no longer waits forever when part of a summary can't be worked out.** One failing part, such as the file classes that come from folders, used to lose the whole answer: the panel stayed on **Loading…** and the log filled with `handler for tree.summary failed` (in 0.3.3, after a scan of `/` on Linux that took 0.3 s, from the failure above). Now the panel shows everything else, with a note on what is missing and why, and counts classes by extension alone when the folder classes fail; when even the item itself can't be read, it says why and offers **Try again**. Each kind of failure goes into the log once per scan, not every second.
- **Folders you classify take their class in a scan from the moment it lists them.** If none of the folders you gave a class (**Classify** on a folder) was listed yet when a scan was first drawn, those choices did nothing in that scan until you classified a folder again or opened the scan from its snapshot.
- **The log panel lines up in English.** The level and the category of each event had room for two Chinese characters only, so an English category such as **Permissions** or **Snapshots** ran into the message after it, and **Warning** spilled out of its badge. Both columns now take the width of their longest name in the interface language, and every message starts at the same place; in Chinese the panel looks as before.

## 简体中文

下一版 **0.3.4** 已经做完、但还没发布的更改。这一版发布时，这里的内容会成为它的发布说明，然后这个文件清空，重新开始记录。

### 新功能

- **浅色主题**：新增浅色主题，默认跟随系统的浅色 / 深色设置（「设置 › 外观 › 主题」：跟随系统、浅色、深色）。树图、火焰图和火焰-极坐标图一起换色，文件类别尽量保持原来的颜色；切换立即生效，不闪白，下次启动直接用选好的主题。在 Windows 上，「跟随系统」看「默认应用模式」；浏览器里（headless 模式）跟随浏览器，重新载入也直接用选好的主题。在「设置 › 文件类别」里改的颜色只作用于当前主题，勾选「同时应用到另一主题」则两套都用；改过颜色的内置类别可以用「删除」旁边的按钮恢复默认颜色。这一版之前选的颜色两套主题都保留。
- **ARM 版的便携版**：ARM 版 Windows 11 和 ARM Linux（arm64）也有便携版了：`SpaceKnife-<版本>-win-arm64-portable.zip` 和 `SpaceKnife-<版本>-linux-arm64-portable.tar.gz`，用法和 x64 的一样（解压即用，数据存在程序旁边的 `data` 文件夹里）。ARM 版 Windows 上原来以模拟方式运行的 x64 便携版，下一次更新就换成 ARM 版。安装包仍只有 x64。
- **macOS 便携版**：`SpaceKnife-<版本>-mac-arm64-portable.zip`（Apple Silicon）和 `…-mac-x64-portable.zip`（Intel），解压到任意位置，打开 `SpaceKnife.app` 即可；快照、设置等一切都存在旁边的 `data` 文件夹里，不写进你的「资源库」。两者要放在一起。解压后直接打开时，macOS 可能从一个隐藏的副本运行应用（App 转移），SpaceKnife 照样能找到它的 `data` 文件夹。「无缝更新」和 Windows、Linux 便携版一样可用。和 dmg 一样还没经过公证：第一次要在「系统设置 › 隐私与安全性」里放行一次。
- 「本机磁盘」按卷保留整卷完整扫描的结果（文件类别、最大的文件夹、文件数和扫描时间）：离开这一页、关掉扫描的标签页、重新载入窗口或重启 SpaceKnife 之后，卷下面照样显示，直到下一次完整扫描。只有同一个卷才会拿回它（盘符或挂载点和卷序列号都相同），换一个盘插在同一个盘符上不会。
- 「本机磁盘」顶部加了一条大的「文件类别」条：所有已知类别构成的卷加在一起，写出每类多大、占多少，以及算进了哪些卷。
- 帮助页「三种可视化」讲清楚树图、火焰图和火焰-极坐标图各自怎样组织信息，加了一张对照表。火焰-极坐标图可以看成一种多层堆叠、没有中心区域的特殊饼图：每一环是一层文件夹，角度就是比例。这一页给三种可视化各配了一张图，软件的帮助页和官网都显示，官网首页也有。
- **新开关「大扫描存进映射文件」**（「设置 › 高级 › 内存」，默认关）：打开后，约 200 万项以上的扫描把数据存进缓存文件夹里的内存映射文件，不占私有内存；常用的部分由系统留在内存里，其余的随时可以丢掉。320 万项的盘，后端扫完稳定在约 250 MB（不开约 600 MB），扫描中峰值约 400 MB（不开约 750 MB），扫描速度不变。代价是扫完后把数据写进这些文件一次，每项约 200 字节（860 万项的盘约 1.8 GB），所以默认关。
- **命令行 `scan --mft`**：读取整个本地 NTFS 卷的 $MFT，也就是应用里的 MFT 快速扫描，不再逐个文件夹列目录（Windows；会请求一次管理员权限）。默认不开。读不了的路径（只是一个文件夹而不是整个卷；ReFS、FAT、exFAT、Btrfs 卷；网络盘；一次写了多个路径）照样逐个文件夹扫描，开始前先说明为什么不支持；拒绝管理员授权时也一样。扫描结果里写明这次是怎么读的。

### 修复

- **SpaceKnife 拒绝 eMudhra 出问题的证书**：2026 年 10 月，印度的证书颁发机构 eMudhra 被发现有八张中间证书的私钥在 2025 年生成时出了错：每个都只是一个很小的数而不是随机数，任何人都能从公开的证书把它算出来，再用它给任意网站签发证书。10 月 17 日到 20 日，Firefox、Chrome、Apple 和 Microsoft 先后拦截了这八张证书；Mozilla 和 Google 还撤销了对签发它们的根证书 emSign ECC Root CA - G3 的信任，Ubuntu、SUSE 等 Linux 发行版也从各自的证书包里去掉了它。SpaceKnife 现在带的是 Electron 44.9.3，其中的 Chromium 和 Node.js 都拒绝这八张证书；SpaceKnife 的窗口只显示软件自带的页面，自己不连互联网，所以此前没有受影响。检查更新只连 GitHub，在 Windows 和 macOS 上现在交给系统自己验证证书，系统拦截的证书（包括这八张）它也拒绝；以前它只拿证书和受信任的根证书比对，不看系统拦截的名单。Linux 上照旧用发行版的证书包，记得把 ca-certificates 更新到最新。
- **硬扫描自己决定同时读几个文件夹**：原生扫描器现在每个进程一组共用的列目录线程，由它决定同时列几个文件夹：平时是 SpaceKnife 能用的 CPU 数（2–16；macOS 上两倍），文件夹要从盘上读时至少 32 个，在少一些反而列得更快的盘上就少一些。现在只数它能用的 CPU：限定了 CPU 亲和或容器的 CPU 配额时，不会再在 4 个核上开 16 个列目录线程，其他线程池也按这个数。磁盘负载上限照样有效：同时在读的文件夹不超过它允许的数目，暂停的扫描不再开始新的读取。文件夹都在内存里时，在 32 核的电脑上，191 万项的 NTFS 盘从 2.6 秒降到 2.1 秒、CPU 时间少 17%，试过的其他文件夹快 11–25%；限定在 4 个核上时 CPU 时间少 4–12%。要从盘上读时（先清空文件缓存），同一台电脑、NVMe 盘上，这块 NTFS 盘约 7.7 秒，以前 11.4 秒；322 万项的 ReFS 盘约 22 秒，以前 35 秒；4 个核上的 WinBtrfs 文件夹约 2.3 秒，以前 4.3–5.7 秒。不管同时读几个文件夹，扫描结果都一样。
- **随浅色主题而来的深色小变化**：详情面板和结果列表里，类别色块上的图标在音频、文档、游戏和其他上改用白色，看得清了；更新徽章悬停和下载中的文字更清楚；滚动条、下拉框和复选框也跟着变成深色。树图里选中的块不再被自己的投影压暗，里面的块也一样。强调色不是默认色时，对比视图的「新增」角标、过滤框下面高亮的候选项和过滤框里还在输入的部分也用这个颜色，不再固定是长春花蓝。火焰图和火焰-极坐标图围着选中项点亮的条上，大小改用和名称一样的颜色，看得清。日志里鼠标所在那一行的错误级别也看得清。
- **「设置 › 文件类别」**：点类别名称的左端不会再弹出取色器。
- **视图更新时，鼠标下的块一直亮着**：实时监控一块忙碌的盘时，每次变化都会重画视图，鼠标不动时它下面的块会失去高亮和外层文件夹的光晕，直到再动一下鼠标；悬停卡上的日期和类型也会每次空一下。现在高亮、光晕和悬停卡在每一帧新画面里都保持，数字跟着更新；从结果列表点亮的行也一样。实时对比更新时，对比视图的悬停卡也不再闪。
- **Windows 硬扫描按文件系统自己的计数算占用，稀疏、压缩文件多的盘扫得快得多**：本地 NTFS、ReFS、WinBtrfs 盘上，文件的占用改取列目录时文件系统给的计数；以前每个稀疏、压缩文件都要按完整路径再问一次（在基准测试的目录树上，冷缓存扫描里占了 12.8 秒）。只有一分钟内写过的稀疏、压缩文件（列表里可能还是旧值）和 Windows 压缩（WOF）过的文件还会单独问。旧估算不对的地方数字会变：存在 NTFS 文件记录里的小文件（约 513 到 700 字节）和 ReFS 上内联存放的小文件（约 1.5 KB 以下）不再按一簇算，记 0，和 MFT 快速扫描一致。FAT、exFAT 和网络盘照旧。
- **命令行扫描启动和结束都更快**：只加载扫描用得到的模块，冻结后端不再在每次启动时加载打包工具 setuptools，输出写完就结束。扫一个空文件夹，Windows 上从约 410 毫秒到 220 毫秒，Linux 上从 240 毫秒到 120 毫秒。输出内容不变。
- **Linux 硬扫描对大多数文件夹少一次系统调用**：自己的文件夹在打开时就让访问时间保持不变，不再先打开再改。
- **Linux 上的实时监控不再漏掉扫描刚结束时的改动**：扫描到的文件夹要在扫描读完它之后稍过一会儿才加上监视，这段时间里在其中新建、删除、改名的文件进不了树：扫描刚完成时写进某个文件夹的文件，要等这个文件夹再变一次或者重新扫描才出现。现在每个文件夹一加上监视，就拿它的修改时间和扫描记下的比一次，变了就把这个文件夹重新读一遍；轮询的文件夹（网络盘，或超出 inotify 额度的文件夹）也这样核对，macOS 上也是。这段时间里只是大小变了的文件，仍要等它下次变化才更新。
- **一个扫描上的长任务不再拖住其他扫描**：有任务长时间读取一个大扫描时，实时监控的盘上一次文件变化要排在它后面，而所有画面、汇总和新开的视图又排在这次变化后面：这时开始的扫描看起来卡住好几分钟才出画面。现在只有那次变化等长任务，其余照常。
- **所有滚动条都变细了**：启动页的盘列表、「本机磁盘」页等所有能滚动的地方，都换成细的圆角滚动条，没有箭头和轨道，指针移上去时变宽，两套主题都一样，不再是 Windows 默认的宽灰条。
- **Windows 上的硬扫描写盘大大减少**：以前每列一个文件夹都会更新它的「最后访问时间」，盘开着访问时间更新时，硬扫描一次 870 万项的盘要往盘里写 1.5–3.3 GB，扫完所有文件夹看起来都像刚被打开过。现在打开文件夹时让访问时间保持原样。不允许这样打开的地方照旧按原来的方式打开：只读的盘、标准用户进系统文件夹，以及只有 Windows 自己能改的文件夹（例如 `C:\Windows\WinSxS`，管理员也一样；系统盘上约六分之一的文件夹），所以硬扫描整个系统盘仍会写约 0.25–0.7 GB。
- **Windows 上的硬扫描更快**：扫描中发现的文件夹，现在从还开着的父文件夹打开，不再每次从盘的根目录逐级找下去。文件夹都在内存里时，321 万项的 ReFS 盘从约 5.2 秒降到约 3.8 秒，880 万项的 NTFS 系统盘从 13.1 秒降到 12.6 秒。在 NTFS、ReFS 和 WinBtrfs 盘上这样做（实测更快或一样快），其他文件系统和网络盘照旧。这样打开的每个文件夹都要核对是父文件夹列出的那一个（文件 ID 相同），对不上的照旧从根目录打开；名字到达的其实是另一个文件夹时，改按文件 ID 打开。扫描结果不变：在 NTFS、ReFS 和 WinBtrfs 盘上，开与不开逐个文件夹比对过，NTFS 盘还和盘上实际记录的内容比对过。
- **Windows 上的硬扫描在不保留访问时间的盘上不再用更慢的方式打开文件夹**：在 Windows 本来就不更新访问时间的盘上（ReFS 默认如此；NTFS 在 `fsutil behavior set disablelastaccess` 设为 1 或 3 时），打开文件夹时不再用那种更慢、为了保留访问时间的方式。把访问时间更新改成关闭以后，到 Windows 重启之前（设置在重启后才生效），硬扫描这些盘可能会像 0.3.4 之前那样更新文件夹的访问时间。扫描结果不变：在 NTFS、ReFS 和 WinBtrfs 盘上，整盘扫描与改动之前的扫描逐个文件夹比对过。
- **硬扫描建树不再拖住列目录**：扫描列出的文件夹现在由原生扩展一遍加进树里，这期间列目录的线程照常工作；以前每一批要几十个 Python 步骤。一个 77 万项的 Linux 系统，热缓存扫描从 0.34 秒降到 0.26 秒。在 Windows 上，加上前一条，文件夹都在内存里时，ReFS 上一个 140 万项的文件夹从 0.65 秒降到 0.50 秒，WinBtrfs 上一个 38 万项的文件夹从 0.31 秒降到 0.29 秒；NTFS 系统文件夹用时不变。快多少取决于加进树是不是最慢的一环：同一个 ReFS 文件夹换个时间测，最慢的是列目录本身时，用时基本不变、CPU 少约十分之一。从盘上读（先清空缓存）时，767 万项的 `C:\Users` 从 15.8 秒降到 14.9 秒。
- **Linux 上扫完之后后端占的内存少一半左右**：C 库把扫描释放的内存留在三十来个分开的内存池里，夹在还在用的块之间，还不回去。现在 SpaceKnife 让 glibc 把大块单独映射、内存池最多 4 个，扫完和空闲时把空闲的页交还系统。扫完约 70 万项后，后端稳定在约 170 MB，原来约 310 MB，扫描速度不变。musl 等其他 C 库不受影响。
- **保存快照多占的内存只剩十分之一左右，速度快两到三倍**：每次扫描完成都会存一份快照；以前整份压缩好的快照先在内存里拼好再写盘，还按数据本身的大小留空间，所以这一刻后端要再占差不多一份扫描数据：890 万项的盘多 1.0–1.4 GB，是整次扫描的最高点。现在一段一段压缩、直接写进文件：只多约 0.1 GB，在 32 个逻辑 CPU 的电脑上耗时从 2.8 秒降到 0.8 秒（旧方式每个逻辑 CPU 一个压缩线程，4 个时要 1.7 秒）。实时监控正在改动树时保存的快照（例如扫完一块很忙的盘之后），不会再一半是改动之前、一半是改动之后，以前这样可能存出打不开的快照：现在会再存一遍，那一两秒里改动先等着。快照文件和以前一样，旧版本也能打开。
- **WinBtrfs 盘上只差大小写的文件夹不再混在一起**：Linux 允许 `a` 和 `A` 这样的两个文件夹并排存在，WinBtrfs 盘上两个都显示，但按名字打开哪一个都到同一个：其中一个算了两遍，另一个的内容一项也没算，也没有任何提示（测试的盘上有 102 对，一个 terminfo 文件夹少算了 335 个文件）。现在每个文件夹都按列出的那一个打开，名字到不了它时按文件 ID 打开，两个都按各自的内容计算。Linux 文件名里有反斜杠的文件夹也这样打开。名字里有冒号等 Windows 名字不能有的字符的，在 Windows 上连按文件 ID 都打不开，仍显示为无法读取，但说明从「找不到路径」改成了真正的原因。删除或移到回收站时，如果按路径会打开只差大小写的另一项，就拒绝执行，什么都不动；同一文件夹里另有一项与它名字完全相同（不是合法文本的 Linux 文件名显示成带 � 的名字，可能一模一样），或者名字里有路径不能有的字符（反斜杠、冒号等，Linux 文件名里可以有）的项，不能加入删除篮，因为没有路径单独指向它。没有原生扩展时，这样的文件夹显示为无法读取，而不是列出错误的内容。这样的文件夹不会单独重新读取：刷新或实时监控时保持上次扫描列出的样子。从这个文件夹本身（或它里面的文件夹）开始一次新的扫描，到达的仍是另一项，资源管理器和复制出去的路径也一样；请扫描包含这两项的文件夹。
- **没有原生扩展时，名字以点或空格结尾的文件夹也能正确列出，删除它不会再删掉另一个**：Windows 会去掉这种路径末尾的点或空格，以前 `odd.` 列出的是旁边 `odd` 的内容，硬扫描之后删除 `odd.` 删掉的是 `odd`。现在删除这样的项、把它移到回收站或加入删除篮，都会被拒绝，什么都不动。
- **Linux 上的硬扫描保留文件夹的访问时间**：在大多数发行版默认的 `relatime` 下，一天里第一次扫描会改写所有一天没打开过的文件夹的 inode。现在属于你的文件夹列出时访问时间保持原样（测试的系统上 4.7 万个文件夹里有 3.3 万个：家目录和其中的缓存）；属于别人的文件夹（标准用户扫系统文件夹）照旧。
- **Linux 和 macOS 上的硬扫描不再漏掉路径很长的文件夹**：路径达到 4,096 字节（macOS 上 1,024 字节）的文件夹按路径打不开，于是显示成无法访问，下面的内容一概没算，其实它是可以列出来的。现在这种文件夹把路径分成几段逐段打开，和其他文件夹一样列出。
- **硬链接多的文件夹扫得更快**：每个硬链接文件只算一次，以前在 Python 里逐个判断，每个多链接文件约 0.5 微秒；现在在原生扩展里做。一个 60 万项的 Linux 系统（其中 16 万个是 uv 缓存和各个虚拟环境共享的硬链接），热缓存扫描从 0.37 秒降到 0.29 秒。
- **快照加载途中关掉标签，扫描不再一直占着内存**：标签关掉以后才加载完的快照，或者才开始的扫描，会一直留在后端、没有标签显示，直到退出 SpaceKnife（一个 860 万项的快照约 1.1 GB）；已经开始的扫描甚至会继续跑。现在会立即释放。
- **窄窗口下工具栏不再被截断**：窗口窄于约 1400 像素时，工具栏右端会被截掉，最小窗口下分屏、命令面板和删除篮按钮都点不到，路径也可能消失。现在先压缩过滤框，再把芯片缩成色块，然后依次把配色、芯片、最后是可视化切换收进新的「更多」（…）菜单，任何窗口大小下每个控件都点得到，快照对比时也一样。
- **MFT 快速扫描快了约四倍**：读 $MFT 时同时有几个大块读在路上，读到的部分用所有核心并行解析，建树也改由原生代码完成，不再用 Python。890 万项的系统盘，默认负载档位下从开始到建好树约 4.7 秒，以前约 19 秒（读取 7.2 → 2.8 秒，建树 12 → 0.4 秒）。同时读几块是边读边定的：一两个读就已满速的盘（比如 SATA 固态盘）只保持这么多，别的程序不用排在一长串读后面；快的 NVMe 盘会多读几块。设了负载上限时，扫描占盘的时间正好是上限那么多。结果逐项不变。
- **MFT 快速扫描的内存峰值大幅降低**：大盘建树的那一刻，以前要在读到的 $MFT 表之外再占每项约 325 字节：860 万项的盘后端会冲到约 3.6 GB（整个 SpaceKnife 约 3.8 GB）。现在每项约 57 字节（890 万项的盘约 0.5 GB）。这块盘扫描时后端的最高点约 1.9 GB，现在是表的最后一部分传到的那一刻，建树时约 1.5 GB。读 $MFT 的管理员助手在这块盘上的峰值约 1.65 GB，以前约 2.85 GB。
- **扫完后文件持续变化时，内存不再每隔几秒冒高**：开着实时监控时，每批文件变化都让详情面板把整盘汇总重算一遍，还经常几份同时算，每份临时要每项约 100 字节（860 万项的盘约 0.85 GB）；扫完后的第一次文件变化还会让扫描数据的内存一直翻倍。现在汇总分小块计算，同一份只算一次，大扫描时刷新得慢一些（最长每 10 秒一次）；文件变化只多留一点余量。320 万项的盘、文件连续变化一分钟：后端峰值从约 1.3 GB 降到约 660 MB（打开「大扫描存进映射文件」约 300 MB），之后稳定在约 600 MB，原来是 835 MB。
- **存进内存映射文件的扫描，写盘量减半**：扫描数据超过「扫描数据内存上限」后，Windows 上每个映射文件都先整个写一遍零，每次变大还要复制到新文件。现在文件原地变大，只写数据本身：320 万项的盘约 0.67 GB，原来约 1.3 GB。
- **实时监控开久了，内存不再一下子冒高好几 GB**：文件改动累计多了以后，后端会把整棵树重新编号一次，这一刻每项要多占约 760 字节，870 万项的盘多出约 6.3 GB。现在只多出重新编号后那份副本本身（约 1 GB），速度不变。
- **打开快照只要一半的内存**：以前每一列都先解压成一份临时副本，870 万项的快照打开时要临时占 1.8 GB，最后只留 0.95 GB。现在直接解压到位，只要 0.95 GB。
- **后端平时占的内存更少**：
  - 少约 50 MB：命令面板的拼音搜索不再在启动时载入中文词典。
  - 打开扫描时每项少 8 字节（860 万项的盘约 66 MB）：树图和命令面板只算要显示的那些项的大小，不再为每一项建一整列、每次文件变化后再整列重算。树图在文件变化后的重画也更快。
- **硬扫描扫过的盘时，一次留好内存**：按上次完整扫描的项数一次分配，不再一边扫一边扩容、每次都把已有的数据整份复制一遍。
- **窗口隐藏时归还内存**：最小化或被完全挡住的窗口会交还绘图画布，再显示时重新画出来。鼠标在树图上移动时复用同一块缓冲，不再每次高亮都重新分配。
- **硬扫描进行中，详情面板和画面不再偶尔出错**：扫描一边添加项目，详情面板的汇总或画面的一次更新就可能失败；有些文件还会显示成错的颜色（按扩展名，而不是它所在文件夹的类别，比如游戏、项目），直到扫描又列了更多文件夹，扫完后也可能一直错着。每一项从所在文件夹得到什么类别，是在扫描进行中算的，最新加进来的项目可能没算就被当成算过了；现在不会了。
- **汇总的一部分算不出来时，详情面板不再一直停在「正在读取…」**：以前一部分出错（比如按文件夹得到的类别），整份汇总就都没了，面板停在「正在读取…」，日志里一条接一条「handler for tree.summary failed」（0.3.3 在 Linux 上扫 `/`、0.3 秒扫完后碰到过，原因是上一条的问题）。现在其余内容照常显示，上面一条说明写清缺了什么、为什么；文件夹类别算不出来时，类别只按扩展名统计；连这一项本身都读不出时，面板写明原因并给出「重试」。同一种失败每次扫描只记一条日志，不再每秒一条。
- **自己归类的文件夹，扫描一列到就按所选类别算**：扫描第一次画出来时，如果你归类过（在文件夹上右键「归类」）的文件夹一个都还没列到，这些归类在这次扫描里都不起作用，直到你再归类一个文件夹，或者从快照重新打开。
- **英文界面下日志面板对齐了**：事件的级别和分类只留了两个汉字的宽度，英文的分类名（如「Permissions」「Snapshots」）和后面的消息叠在一起，「Warning」也超出了它的底色块。现在这两列按界面语言里最长的名字定宽，每条消息从同一处开始；中文界面看起来和以前一样。
