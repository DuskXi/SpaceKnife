# 重复文件的检测与清理 —— 设计与接口约定

找出内容完全相同的文件，按能腾出的空间排序（§1–§15）；把它们变成腾出的空间，只经清理方案（§16）。**查找只读**：作业本身从不改、移、删用户的文件。**清理没有一键删除**：每组自己选保留点，其余每份选一种处理（不动、移到回收站、换成硬链接、换成符号链接、块克隆），风险逐份写明；方案先审阅、批准，执行前再核对每一份，执行后能撤销，只有「清除恢复区」不可逆。

代码：引擎 `packages/backend/src/spaceknife/dupes/`，服务 `server/dupes.py`、`server/dupes_handlers.py`，协议 `spaceknife_protocol/dupes.py`（能力 `dupes.v1`），原生读取 `packages/native/src/dupes/`（feature `dupes`，默认开），前端 `apps/electron/src/renderer/src/state/dupes.ts`、`shell/DupesDrawer.tsx`，测量工具 `spaceknife dupes`（`cli_dupes.py`）。清理的代码见 §16 开头。

## 1. 总体

入口在 §10.1。查找从不自动开跑；它只读和别的文件大小相同的文件，先读头尾几 KB，只有几份还一样时才读完整个文件；只有读完全文、内容一致的才叫「内容相同」。硬链接、块克隆、同一个文件经两条路径看到的，都是「同一份数据」，删了不腾空间，从不给删。云占位文件不读（读它会触发下载）。

## 2. 流水线

```
store ─S0 选候选（不读盘）─▶ 大小组 ─S1 身份（只读元数据）─▶ 物理文件 ─S1b 块映射（只在可克隆的卷）─▶ 不同的数据
         已核对 ◀─S3 全文 BLAKE3-256（组内同步、分段比对、一不同就停）◀─S2 头尾（每个文件一次数据打开）
           └─▶ S4 账本 · 保留规则 · 文件夹汇总 · 覆盖（不读盘）──▶ 清理方案（§16，用户打开时才建）
```

只有 S2、S3 读内容；每一步只处理前一步解决不了的。组按「可能腾出的空间」（(份数 − 1) × 大小）从大到小、一波一波地做，结果随时流出。

### 2.1 S0 选候选（不读盘）

合格的文件：普通文件、≥ 下限（默认 1 MiB，`dupes.min_size`），不是云占位、离线、出错、已不在、待扫、MFT 伪目录里的；排除受保护的系统和程序文件夹、回收站、网络盘、FUSE（设置可以打开）。按大小稳定排序，去掉大小独一无二的（不读盘就知道它们没有伙伴）。模式：`all`（整个范围）、`inside`（只看某个文件夹里的组）、`against`（组里至少一份在某个文件夹里，伙伴在整个范围里找）、`file`（只看某个文件的大小组）。路径按父文件夹缓存拼，不逐个调 `store.path()`；在锁下做，不分配与 store 等长的数组。`dupes.plan` 只做这一步。本机 C:（865 万行）分组 26 ms、排除树上溯 4.8 ms、拼全部候选的路径 48 ms（Understand 阶段实测）。

### 2.2 S1 身份（只读元数据）

每个候选一次只读元数据的查询（Rust 里批量做，每批 ≤256 个名字或约 30 ms，释放 GIL）：卷、128 位文件 ID、链接数、纳秒时间、属性、重解析标记，Windows 有 USN 日志时取 USN。身份相同的几个名字合并成一个物理文件；剔除云占位、名字被换成链接的、只差大小写的、名字不能用的；按新鲜大小重新分组（目录项里的大小可能过期：大小变了只会漏掉重复，不会误报）；查缓存（§7）：一组里所有物理成员都有可用于认定相同的全文摘要时，整组不读盘。只取属性的打开 + FileIdInfo 约 14 µs（暖缓存）。

### 2.3 S1b 块映射（只在可克隆的卷，只读元数据）

ReFS 等带 `FILE_SUPPORTS_BLOCK_REFCOUNTING` 的卷，Linux 的 btrfs、xfs、bcachefs、ocfs2：块映射从头到尾完全相同的两份判为「同一份数据」（块克隆、reflink），可腾出记 0，不读内容，永远不给删——这是关于存储的判断，不是关于内容的。部分共享的照常读，共享字节记进账本；查不到映射的当「不知道」，照常读，账本加注「可能共享数据块，实际腾出的可能更少」。估计 20–40 µs/个。

### 2.4 S2 头尾（每个文件一次数据打开）

在句柄上读第一个字节前，核对属性和标记、身份等于 S1、大小等于组的大小，取打开时的戳。读头 [0, 4 KiB)、尾（4 KiB 对齐），≥64 MiB 的再读 1/3、2/3 处各 4 KiB，不经缓存。快速摘要 = BLAKE3(大小 ‖ 参数号 ‖ 各块) 的前 64 位，只用来拆组：碰撞的后果只是多读。读完在同一句柄上再取戳，变了就记 `changed`。每个文件 8 KiB（大文件 16 KiB）；冷打开约 5 ms（有卡巴斯基时）。

### 2.5 S3 全文（BLAKE3-256，分段，组内同步，一不同就停）

在 1、4、16、64、256 MiB 及之后每 256 MiB 处用 `finalize(&self)` 取中间摘要比对，变成单个的成员立刻停、关句柄；读到的字节数正好等于大小、再读是 EOF、关闭前戳不变，摘要才有效。最终 32 B 摘要相同的成员组成已核对的组。BLAKE3 约 4.76 GiB/s/核。

### 2.6 S4 账本、保留规则、文件夹汇总（不读盘）

见 §8。

### 2.7 细节与读取量

- **句柄交接**：SSD 上，S2 后还要进 S3 的成员把句柄留着，S3 从头接着读，S2 读过的头块直接喂给哈希器（不重读、不再冷打开一次）。HDD、SD 卡上不交接。
- **在途请求不跨下一个检查点**，所以每个被拆出去的成员读了多少字节是确定的：读取量 = Σ 已核对且没靠缓存认定的成员的大小 + S2 的头尾块 − 交接省下的头块 + Σ 被拆出去的成员的检查点（测试 `test_dupes_engine.py` 按这个公式精确核对）。
- **大组**（>32 份）：一次最多 32 份同时打开，每份最多打开 3 次（S2 一次；1 MiB 检查点一轮；没被这一轮分开的再读到结尾一轮，块与块之间关掉句柄）。32 份以内的组靠句柄交接，每份只打开 1 次。把大组改成「每 32 份一块走完所有检查点」能省掉中间那一次，但一块里的成员在别的块读完之前谁也不能提前停（可能和别的块相同），省下的只是一次冷打开，留在第二期。
- **句柄租期** 2 s：之后关掉，续读前重新打开并核对身份和戳，从偏移继续（不重读）。Windows 上文件夹里有打开的子项时用户改不了文件夹的名字，所以不长时间占着。
- 每块物理盘一个队列，用它自己的线程（按介质：NVMe 8、SATA SSD 4、HDD 2），每批约 30 ms（HDD 100 ms）拿一次调速器许可；读和哈希都在 Rust 里，不持 GIL（§9）。

## 3. 零误报

### 3.1 判定

两份被报告为「内容相同」，当且仅当：

1. 身份不同（本次运行内的 (卷, 128 位文件 ID) 不同；相同就是同一个文件）；
2. 不是块映射完全相同的「同一份数据」（那是另一档，从不给删）；
3. 大小相同，读到的字节数正好等于大小，之后是 EOF；
4. 全文 BLAKE3-256 相同；
5. 每一份的摘要来自一次一致的读取（同一句柄上读前读后的戳不变；租期重开时身份和戳也不变），或来自一条可以用来**认定相同**的缓存条目（§7.3）。

### 3.2 为什么用强哈希，不逐字节比较

- **偶然碰撞**：n 个文件时概率 ≤ n²/2²⁵⁷，10⁹ 个文件约 4×10⁻⁶⁰，比内存、总线、磁盘没被发现的错误低几十个数量级；逐字节比较同样暴露在这些错误下。
- **蓄意碰撞**：BLAKE3 有 128 位的抗碰撞强度，没有已知攻击。MD5、SHA-1 有同长度的碰撞实例，xxh3 之类不抗碰撞，所以非密码学哈希一律不用于判定（S2 的快速摘要只用来拆组：碰撞的后果只是多读）。
- **代价**：逐字节比较要把每一份再读一遍、几份同时打开（HDD 上来回寻道），结果还不能缓存，「第二次几乎不读盘」就做不到。
- 它也不解决真正的风险：核对之后文件又变了（§3.3）。

### 3.3 真正的风险怎么挡

- 读前读后在同一句柄上核对戳（大小、修改时间、更改时间）；长度正好、EOF。
- **刚改过的**（修改时间或更改时间在开始读之前 10 s 以内）：本次照常显示，缓存条目标 racy，以后永远不能用来认定相同。
- **缓存的不对称信任**（§7.3）：用来「分开」随便用，「认定相同」要全部戳对上；FAT、exFAT、网络盘上永远不能。
- **USN**（NTFS/ReFS，卷有日志时）：程序能把时间改回去，改不了 USN。存进缓存，认定相同和清理前都核对。
- **清理前核对**（§16.8、§16.9）：要处理的和保留的都重新取身份和戳；戳证明不了「没变过」时（Windows 上没有 USN、24 小时内改过、靠缓存认定的组）把两份重读一遍。
- 不经缓存的读能看到还没写回的数据（NTFS 在非缓存读前冲掉缓存的范围，Linux `O_DIRECT` 先写回），摘要对应文件当前的逻辑内容。
- **「相同」的范围**：只比较默认数据流。备用数据流（ADS）、扩展属性、ACL、时间戳都不比；界面上一律写「内容相同」。

### 3.4 接受的残余风险

- 没有 USN 日志的 Windows 卷上，有程序改了内容、又用原生 API 把修改时间和更改时间都改回原值时，缓存可能把不同的文件认成相同。查找本身只给信息；清理的核对方式「自动」在这种卷上执行前把两份重读一遍（§16.8），清除前也重读保留那份（§16.10.5），实机验证里这样改过的副本都被拦下了（§16.19）。
- 别的程序在核对之后、处理之前通过内存映射写入、而文件系统还没更新时间戳时，戳的核对可能看不出来。清理的预检查占用（这份或保留那份正被别的程序打开就跳过），Windows 上每一步在拒绝别人写的句柄下做；剩下的缺口见 §16.21。
- 第三方杀毒软件在打开时检查文件，可能改访问时间（本机的卡巴斯基就会）。SpaceKnife 挡不住，只能少打开，并在事后抽样数出来告诉用户（§5.6）。

## 4. 身份、硬链接、克隆、跨卷

### 4.1 卷键

本次运行内的身份是 (S1 的卷号, 128 位文件 ID)，精确比较：Windows 是 `FILE_ID_INFO` 的 64 位 VolumeSerialNumber，POSIX 是 `st_dev`（btrfs 的每个子卷各有各的）。缓存用的卷键要跨次稳定：Windows 64 位卷序列号 + 卷 GUID；Linux 文件系统 UUID（`FS_IOC_GETFSUUID`，6.5+）和 `f_fsid`（btrfs 上混进子卷）；macOS `f_fsid`（未验证）。卷键不稳只会让缓存认不出来，认定相同仍要所有戳对上。

### 4.2 各种情况

| 情况 | 怎么认出来 | 显示 | 可腾出 | 能不能清理 |
|---|---|---|---|---|
| 同一个文件的几个硬链接名字 | S1：身份相同（Windows 硬扫描存的 `ino` 是 0，所以靠 S1） | 同一个文件 | 0 | 不删，只能当保留方 |
| 同一个文件经两条路径看到（重叠的扫描、SUBST、挂载点、bind mount） | S1：身份相同 | 同一个文件 | 0 | 不删 |
| 链接数大于扫描里看到的名字数 | S1 | 不选 | 0 | 不选 |
| 块克隆、reflink（完全共享） | S1b：块映射完全相同 | 同一份数据 | 0 | 不删 |
| 部分共享 | S1b：共享字节 | 普通组，账本里分开写 | 私有部分 | 能 |
| 不同的物理文件，内容相同 | S3 | 内容相同（已读完全文核对） | 多余各份的分配大小 | 能 |

- 只有「一个名字、链接数等于扫描里的名字数」的物理文件才能是多余的副本。名字以点或空格结尾、按路径找到的可能不是它的，只能当保留方（清理方案里是锁定的，§16.4.1）。
- 两个不同的卷碰巧给出相同的卷号和文件 ID（克隆出来的盘）时，两个文件会被当成同一个文件：这只会藏掉一个重复，不会造出一个。

### 4.3 跨盘（选项，默认关）

- 抽屉里的「跨盘比较」（设置 `dupes.cross_volume`）：把所有打开的、已扫完的实时扫描放在一起比（最多 16 个）。同一卷经两条路径或两个扫描看到时只算一份。
- **物理事实**：硬链接不能跨卷（EXDEV），块克隆、reflink 不能跨文件系统，所以**跨卷的每一份都实占它自己卷上的空间**。btrfs 的子卷、挂载的快照是同一个文件系统，能共享盘区：S1b 按文件系统分组（文件系统 UUID，没有就按挂载的设备），不按 `st_dev`（每个子卷各有一个），FIEMAP 的地址在整个文件系统里可比。
- **保留**：默认每个卷至少留一份（`dupes.cross_keep_per_volume`）：每个卷上留一份，同卷的其余副本是多余的；可腾出按卷分开，清理方案把它当成底线（§16.4.6），执行时要求同卷的保留点完好。关掉它就是全部只留一份，别的卷上的备份也预选为多余。
- **重叠**：两个打开的扫描有重叠（C:\ 和 C:\Users\x\Downloads），或同一文件夹经两条路径，重叠部分的文件各有两条路径，但仍是一个名字：按 §8.1 的「视图」只算一份，真正的重复照样能处理一次。
- 网络盘默认不参加：ID 不可靠，`\\localhost\c$` 可能就是 C:。

## 5. 读盘：只读、不改访问时间、不触发云下载

### 5.1 守卫的顺序（三个系统都一样）

store 的 flags（S0，不发系统调用）→ S1 的新鲜属性和标记 → 数据打开（带「不召回」）→ 在句柄上核对属性、标记、身份等于 S1、大小等于组的大小，取打开时的戳 → 保持访问时间 → 读 → 在句柄上再取戳 → 关闭 → 按抽样规则查一次访问时间。

### 5.2 Windows

- S1 在只取属性的句柄上做（`FILE_READ_ATTRIBUTES`、`FILE_OPEN_REPARSE_POINT`、`FILE_OPEN_NO_RECALL`）：不碰数据，不召回、不改访问时间、杀毒软件也不扫内容。
- 数据打开：`FILE_READ_DATA | FILE_WRITE_ATTRIBUTES`、`FILE_FLAG_OPEN_NO_RECALL`，打开后立即在句柄上把 LastAccessTime 设成 −1（和硬扫描共用 `src/winio.rs` 的 `keep_access_time`），不经缓存读（不冲掉用户的文件缓存）。压缩、加密、稀疏、WOF、重复数据删除的文件经它们的过滤驱动缓冲读。
- `FILE_WRITE_ATTRIBUTES` 被拒绝时：按 `dupes.keep_access_time`，默认 `skip` 不读并计数（「保留不了访问时间」）；`read` 则照读、计数 `atime_unkept`。
- 别的程序没给共享读：跳过，记「被独占」。
- 只差大小写的同名项：在属性句柄上取规范化路径比对；只差大小写时，对每一级大小写不同的名字问一次它所在的文件夹（`FindFirstFileExW`，名字当模式，每个文件夹和名字记 2 s）：有两项能对上，或有一项恰好是问的那个名字（区分大小写的文件系统），才说明打开的可能是另一项，跳过（`ambiguous_name`）。用户手输的 `c:\users\x\downloads`、扫描后只改了大小写的文件夹不再整个被判成「只差大小写」（评审在 Windows 上实测：之前这样的根下每个候选都被跳过）。
- 根下挂在文件夹里的别的卷（开了 `scan.cross_mounts`）：S1 的 64 位卷序列号的低 32 位和根卷的序列号不同时，按路径重新查卷，信任、能否共享数据块、是不是网络盘按那个卷的文件系统定；查不到就当弱信任（FAT、exFAT 永远不能凭缓存认定相同）。

### 5.3 Linux

- `open(O_RDONLY | O_NOATIME | O_NOFOLLOW | O_CLOEXEC)`，全文阶段 `O_DIRECT`（设备拒绝对齐时改缓冲读）。
- `O_NOATIME` 被拒（不是文件主人）：卷以 `noatime` 挂载就照读；否则按 `dupes.keep_access_time`，默认跳过并计数。
- FUSE 和网络挂载默认不参加（rclone 之类的云 FUSE 一读就下载）。不只是扫描根：开了 `scan.cross_mounts` 时，本地根下面挂着的 NFS、SMB、FUSE 在 S1 按文件所在的卷认出来（`st_dev` 和根不同时重新查卷），原因记 `network_mount`，一个字节也不读（测试 `test_a_network_mount_below_a_local_root_is_not_read`）。

### 5.4 macOS（照写照标，本机测不了）

- `open(O_RDONLY | O_NOFOLLOW | O_CLOEXEC)`，`F_NOCACHE`；读盘线程调 `setiopolicy_np(IOPOL_TYPE_VFS_ATIME_UPDATES, IOPOL_SCOPE_THREAD, IOPOL_ATIME_UPDATES_OFF)`，失败就按 `dupes.keep_access_time` 处理。
- 读盘线程打开数据前调 `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, IOPOL_SCOPE_THREAD, IOPOL_MATERIALIZE_DATALESS_FILES_OFF)`：文件在 S1 之后、读之前变成无数据的，读会失败而不是把它下载下来；设不上就不读（记 `cloud`）。`SF_DATALESS`（无数据的云文件）照样在 S1 剔除。
- APFS 的克隆识别（`getattrlist` 的 clone id）还没做：APFS 上 S1b 当「不知道」，照常读，账本加注「可能共享数据块」。
- 以上都没在真机上跑过；CI 的 macOS 机器跑单元测试。

### 5.5 云占位为什么跳过

- 读占位文件会让云过滤驱动把它下载下来；删占位文件不腾本地空间，还会删掉云端那份。所以它们永远不是候选，抽屉里计数「云占位 N（读内容会触发下载）」。
- S0 用扫描时的 `CLOUD`/`OFFLINE`，S1 再核对属性（`RECALL_ON_OPEN`、`RECALL_ON_DATA_ACCESS`、`OFFLINE`、云重解析标记）。`FILE_OPEN_NO_RECALL` 只是第二道保险：它为 HSM 设计，云过滤驱动认不认没测过，不能只靠它。
- 已经完整下载、没有召回属性的文件是本地文件，照常读；保持访问时间也让「存储感知」不会因为我们读过而留着它。

### 5.6 杀毒软件和访问时间的抽样核对

每卷读过的前 32 个文件、之后每 64 个，关闭后再取一次访问时间与 S1 的比；变了的计 `atime_moved_by_others`，抽屉提示：「读取后有 N 个文件的访问时间变了。SpaceKnife 自己的读取不改访问时间，多半是杀毒软件在打开时检查文件」。测量工具可以 `--stop-on-atime` 停掉这块盘的内容读取。

### 5.7 每种介质的读法

- **SSD、NVMe、虚拟盘**：先对一波候选做 S1（便宜，先合并硬链接），再按可腾出从大到小处理组，每块盘同时最多 8 组、32 份在读；S2、S3 接着做，句柄交接；结果随时流出。
- **HDD、USB 机械盘、SD 卡**：不交接句柄（S3 每组一份一份地读），每步读 64 MiB，每批 100 ms。按物理位置排序在第二期，本机没有 HDD，这条路照写照标。
- **网络**（只在打开时）：缓冲读，同 SSD 的调度。

## 6. 内存

### 6.1 候选表

- 候选表：每个 40 B（numpy 结构化数组，`codes.CAND_DTYPE`：node i4、scan、vol、state、reason、nlink u2、flags、group i4、128 位文件 ID、64 位快速摘要），测试断言 `itemsize == 40`。不分配与 store 等长的数组。

### 6.2 其他结构

- 已核对成员：表里每个 64 B（`MEMBER_DTYPE`：文件 ID、mtime、更改时间、USN、分配、node i4、组 i4、扫描、卷、角色（低 4 位角色、高 4 位保留原因）、标记、`unit` i4——这份所属物理文件的代表行，任何行号都放得下；它曾经是 1 字节，第 257 份成员就让查找失败）。另有每份的路径字符串（S1 核对过的那个名字：删除篮和守卫要的正是它，监控改名后从 store 重拼的路径不是核对过的那个，所以不省）和 8 B 的创建时间。
- 组记录、文件夹汇总（有多余字节的文件夹，node i4 + bytes i8）、帧注释用的有序成员索引，都和已核对的数量成正比；每组的有效、同一份数据、可腾出另存成 numpy 数组，状态、账本、帧列都是向量运算。
- **实测**（评审时 2.3 万候选、2 万份已核对，tracemalloc）：作业峰值约 1.2 KB/候选，作业后保留约 0.7 KB/候选；其中 Results 每份约 480 B（路径字符串、组对象），缓存新条目原来每条约 350 B（0 维数组加元组键，已改成可增长的结构化数组，128 B/条），每卷缓存整表常驻（每条 128 + 16 B，上限 26.2 万条约 36 MiB）。40 B/候选只是候选表本身；TODO 里的 32–48 B 指的是它。按此推算 C:（5.2 万候选）峰值约 65 MB，跨盘 25.7 万候选约 300 MB。
- 读缓冲每盘一个池；在读成员在 Rust 里（BLAKE3 Hasher 约 1.9 KB）。渲染进程不持有 O(N) 的东西：组列表、文件夹列表都是分页切片，点亮只用帧里的两列。
- 数字见 [memory.md](memory.md) §11。

## 7. 哈希缓存

### 7.1 文件

- `cache_dir()/dupes/v1/<卷键>-a<算法号>.skh`，每卷一个，所有扫描和作业共用；不随快照走；**不存文件名**。64 B 头（魔数 `SKDH`、版本、算法号、快速摘要参数号、信任类、卷键、条数），正文是按文件 ID 排序的 128 B 条目（文件 ID、大小、mtime、更改时间、USN、哈希时间、快速摘要、摘要长度、32 B 摘要或 16 B 前缀摘要、标记、最后见到的日子）。

### 7.2 写入和淘汰

- 载入后就关上（Windows 上「清除缓存」照样能删）；作业结束时和长作业每 60 s 写一次：临时文件、fsync、改名，改名前和磁盘上的合并（CLI 和服务可能同时写，哈希时间新的赢）。坏文件丢弃后重建。
- 只在有新条目，或有条目今天第一次被见到时才写：当天已经见过的条目再被查到不算变化，第二次运行（同一天）一个字节也不写。文件自上次读或写以后没被别人动过（mtime、大小）就不再读回来合并，整表只拷一次。保存的代价仍然和整表大小成正比（满表 32 MiB 一次）；改成追加日志加定期压缩留在第二期。
- 淘汰：90 天没见过的删，每卷最多 26.2 万条。别的算法号的条目不混用：Python 回退用 BLAKE2b-256，和原生的 BLAKE3 各存各的。

### 7.3 信任类和不对称信任

| 信任类 | 文件系统 | 用来**分开** | 用来**认定相同** |
|---|---|---|---|
| 强 | NTFS、ReFS（有 USN 日志时再核对 USN）、WinBtrfs、ext4、xfs、btrfs、f2fs、bcachefs、APFS、HFS+ | 大小、mtime、更改时间对上 | 全文条目、不是 racy、算法和参数相同、所有戳（和 USN）对上 |
| 弱 | FAT、exFAT、网络盘、FUSE、未知；Windows 上的 Python 回退（没有更改时间） | 能 | 永远不能：要重读才能并入 |

用过期的条目去分开，最坏只是漏掉一个重复；认定相同必须证明字节就是当初哈希的那些。前缀条目（S3 在检查点被拆出去的成员）只能用来和同一偏移处摘要不同的伙伴分开。

### 7.4 第二次运行

- S1 对所有候选只做元数据查询，然后查缓存：**没变过的文件不读内容、不打开数据**（测试断言内容字节为 0、数据打开为 0）。
- **改名、移动会让缓存失效一次**：这些操作会更新更改时间，所以下次重读一次，之后又能命中。

### 7.5 监控与失效

- 实时监控只是提示，正确性靠戳：监控报告某个成员变了时（任何改动：大小不变的原地改写也算，事件里的每个文件都报给结果，重新列目录时比较大小和 mtime），它退出所在的组，组回到「待核对」，不会被删；抽屉提示「N 组因为文件变了退回『待核对』」，「再查一次」只读变过的文件。节点重映射（`_Remap`）照映射候选表和成员索引，映射成 −1 的成员记 `gone`。
- 第一期**不**自动在后台重新核对变过的成员，也不把监控新发现的同大小文件加进组（留在 TODO）。

### 7.6 上一次的摘要

- `last.json` 按扫描根记上一次的时间、组数、份数、可腾出，计划和命令面板里写「上次的结果（3 天前）」。结果本身不持久化（重跑靠缓存，只做元数据）。

## 8. 结果、保留规则、清理

### 8.1 组的角色

每个已核对的组里，每个物理单位一个角色：`keep`、`extra`（多余）、`alias`（同一个文件的其他名字）、`clone`（同一份数据）、`needed`（程序需要或受保护，永远保留）、`pinned`（必须保留）。

同一个文件经两条路径被看到（重叠的扫描、指向扫描里文件夹的符号链接或 bind mount），而它在盘上只有一个名字（链接数 1）时，另一条路径不是硬链接：它标成「视图」（`F_VIEW`，协议里 `view`），带着代表那份的角色，账本、份数、可腾出只算一次，清理方案里它跟着它代表的那份（§16.4.1），只处理一次。链接数大于 1 的还是只能保留。清理做完的名字标 `F_CLEANED`（§16.11.1）。

### 8.2 保留规则（按顺序，前面的先定）

1. 永远保留：受保护路径、程序需要的、`pinned`。
2. 优先的位置（`dupes.keep` 的 `prefer`）。
3. 基本规则（`dupes.keep_rule`，默认「最早创建」；另有「最新修改」「路径最短」）。
4. 文件夹一致（`dupes.folder_consistent`，默认开）：两份分别落在同一对文件夹里、且这对文件夹至少有 2 组时，这些组的保留方都在同一边，删完后另一边可以整个清空。
5. 跨盘时每个卷至少留一份。
6. 决胜：路径短的，再按字典序，结果确定。
7. 手动（「保留这一份」）：按 (内容摘要, 路径) 记在作业结果里，覆盖 2–5，不能覆盖 1。手动选择**累积**：对另一组点「保留这一份」不会丢掉前一组的；同一组再点一次，换成新点的那份。改规则、「再查一次」都带着它们（新查找从被替换的那次接过来；摘要保证只对同样的内容生效）；`reset_overrides` 才清掉。

后端强制的不变式：每组至少一份保留；跨盘且「每卷留一份」开着时每卷至少一份，清理执行时也按卷核对（某卷上的副本只有在**同一个卷**上的保留点完好时才处理）。关掉「每卷留一份」就是只留一份：别的卷上的备份照常预选为多余并计入可腾出（之前设计里的 `other_volume` 角色没有实现，已去掉）。规则一改，保留方、文件夹汇总、配色、可腾出都重算；全部组的重算在线程里对一份快照做，没有新组进来就提交，不占事件循环。

抽屉里的这一行规则和手动选择就是清理方案的底子：方案在它上面分层（§16.4）。判据链只有抽屉这一条时，每组的保留点和这里逐组相同（性质测试 `test_the_default_policy_keeps_what_the_drawer_keeps`）；方案默认的判据链在它后面还比「名字不像副本」「路径最短」（§16.4.4），第一项一样的组里可能挑另一份。

### 8.3 可腾出的账本

- 可腾出 = 多余各份的私有分配，减去块克隆共享的字节；别名、块克隆分开列；可克隆但查不到共享信息的卷加注「可能共享数据块，实际腾出的可能更少」。按卷分开。

### 8.4 文件夹层（第一期只给信息）

- **文件夹汇总**：每份多余的副本把它的字节加到所有祖先上，供帧的文件夹分档、悬停卡。
- **「按文件夹」页**：只列直接装着多余副本的文件夹，加上两条以上这样的分支汇合、而且多余字节占到 10% 以上的文件夹；一条单链（C:\Users → C:\Users\x → …）只列最深的那一层。每行写出它的**对应文件夹**：它的多余副本的保留方大多在哪个文件夹（「75% 在 Photos\2021 也有」），悬停时两边一起点亮；可以翻页。这是研究 #5「回声」的第一步：成对的文件夹，按已核对的内容算，不靠名字和大小猜。
- **覆盖**（「这个文件夹在别处有没有」）：文件夹里每个合格的文件归到「在别处有一份」「只在这里」（大小独一无二的不读盘就能确定）「同一份数据」「没核对」（小于下限、云占位、读不了……）之一，给一条按字节的覆盖条、别处的副本主要在哪几个文件夹（最多 5 个，可点击定位、悬停点亮）和「只在这里」最大的 50 个。整个扫描查过之后直接从结果回答，不另起作业。**第一期不给删整个文件夹的决定**：要删整个文件夹，得证明里面每个文件都核对过，出错就是丢数据。

### 8.5 清理（删除篮不再收重复文件）

- 第一期的「把多余的 N 份加入删除篮」、命令面板的同名命令、`dupes.to_basket`、`dupes.basket_members`、删除篮的 `dupes` 条目和它的守卫、条目状态 `blocked` 都去掉了（都没有发布过，删除篮又只在内存里，不需要兼容）。清理不提供一键删除：重复文件只经清理方案（§16）处理，逐组选保留点、逐份选处理，审阅、确认、批准之后才执行。
- 删除前的守卫（`dupes/guard.py` 的 `check`、按身份的 `Elsewhere` 和 `_Reach`）留着：清理的回收站步骤经 `ops/trash.move_to_trash` 带着它（§16.9.3），预检用同一套按身份的判断（§16.8）。`OpCode` 的 `changed`、`keeper_changed`、`last_copy`、`keeper_busy` 也留着，清理的回收站步骤会报它们。
- 删除篮和清理在两个方向上有关系（§16.11.4）：删除篮里的东西盖住的保留点或副本，清理时跳过；SpaceKnife 建的符号链接指向的文件进了删除篮，条目状态是 `link_target`，执行要先确认。

## 9. 调度、调速器、暂停、取消、GIL

### 9.1 磁盘队列

每块物理盘一个 `DiskQueue`：自己的线程池（按介质：NVMe 8、SATA SSD 4、HDD 2）、这块盘的 `IoGovernor`、一个原生读取器。

### 9.2 一批

每批（约 30 ms，HDD 100 ms）的 Rust 调用之前拿一次许可；测试断言没有绕过许可的 IO，许可次数等于 IO 调用次数。

### 9.3 负载档

作业自己的档（`dupes.load`，默认「安静」；计划里开始前就能选，运行中也能改），开始时设到这块盘的调速器上，作业结束后恢复成原来的值。

调速器按队列深度估负载，大块顺序读在它看来很轻：SATA SSD 上 1 MiB 的读排约 2.7 深的队列就把带宽占满了，调速器却只算 34%（评审实测 D:\「安静」档 active 97–99%、约 440 MB/s）。所以低于「最大」的档，S3 的大块读另外按**时间份额**走（`engine.DutyCycle`）：有 S3 批在跑的时间记成欠账，每秒按档位的份额（安静 35%）还掉，欠账超过 0.2 s 就等。它不需要知道盘有多快：S3 跑的时候盘就忙着它，其余时间留给别的程序。代价是快盘（读被哈希限住时）上也少读一些。「空闲」档不加这一层（它本来就在别人用盘时让开）。「空闲」档降线程的 I/O 优先级。同盘有扫描时作业让路（`waiting_scan`，抽屉写「等 D: 的扫描结束」），扫描结束后继续；作业从不调 `governor.pause`。

### 9.4 暂停、恢复、取消

- **暂停**：不再申请许可；正在排队等许可的请求撤回，暂停时才拿到的许可原样退回、不开句柄不读；等在途的一批结束，关掉所有句柄（哈希器和偏移留着）；恢复时重新打开并先核对身份和戳。
- **取消**：同样撤回许可、等在途的一批，已学到的写进缓存，没下结论的候选记「没来得及核对」（状态里 `stop_reason`、`undecided`）。
- 一批算「在途」直到它的线程真正结束（不是等它的协程被取消为止）：取消、到上限、出错之后读取器里不留句柄和成员（测试 `test_no_handle_outlives_a_budget_stop_or_a_failure`、`test_a_pause_while_permits_are_slow_stops_every_read`）。
- 一组出错时整个作业干净地结束（其余组取消并收回异常），状态是「出错」，给用户的是可读的一句话，异常原文只进日志。
- 预算：`budget_bytes`、`max_seconds`（测量工具和 Verify 用）到了就停，同取消。

### 9.5 GIL 和事件循环

读和哈希在 Rust 里做，不持 GIL；事件循环上只做调度和每批的小量 numpy；`dupes.progress` ≤4 Hz，`dupes.changed` ≤1 Hz，「重复」配色的视图重画 ≤1 Hz。

状态（每秒 4 次）、账本、帧列都是对成员表的向量运算：20 万份成员时账本约 4 ms、合计约 1.5 ms（之前是逐份的 Python 循环，评审测得状态 168 ms）。作业结束和改规则时的全部保留规则在线程里算（20 万份约 0.9 s，事件循环最长停顿约 14 ms）；组页、`under` 和名字筛选、覆盖、文件夹页都在计算线程里；前缀拆分是 O(n)（3,000 份同大小时原来 0.4 s 的平方算法）。进度按字节：做完的组按它的字节算，正在读的按已读的算，读一对 20 GB 的文件时也往前走。

### 9.6 一个后端一个作业

同时只有一个作业；再开一个报「已经有一个查找在进行」，除非 `replace`，或是 `file` 模式且文件在正在跑的作业里（那一组先做）。新作业替换同一批扫描的旧结果（手动选择接过来）；关掉扫描、或扫描为省内存被淘汰时，它的作业取消、结果丢掉、界面收到 `cleared`。清理方案跟着作业：作业被替换或丢掉时方案的草稿丢掉，已经开始的运行照样做完，日志和恢复区都留着（§16.11.5）。跨盘查找只取开着页签的扫描（有页签的扫描不会被淘汰），计划里列出要比较哪些、可以逐个去掉。

## 10. 界面与可视化

### 10.1 入口（从不自动开跑）

- **命令面板**：「查找重复文件…」（别名 duplicates、dupes、dedupe、same files、查重；先打开抽屉显示计划，用户点「开始查找」才读；已有查找时显示它的结果）、「重复文件面板」、「配色：重复」（只能输入调出）、「重复文件清理方案…」（要有已核对的结果）、「重复文件清理记录」（有过运行时）。没有任何能直接删除或执行清理的命令（§16.13.1）。需要已扫完的实时扫描；快照页签里禁用：「快照是过去的状态，不能核对内容」。
- **右键菜单**：文件夹「这个文件夹在别处有没有？」；文件「查找与它相同的文件」（只读它这一个大小组；有作业在跑时让这组先做），已核对的文件「另有相同内容的文件 · 点亮它们」。不能用时禁用并写原因。
- **详情面板**：文件加「相同内容」一节（其他几份、在图里找到它、保留这一份）；文件夹加「重复」一节（多余的副本有多少、「这个文件夹在别处有没有？」）。
- **状态栏**：作业运行中或当前扫描有结果时出现，点了打开抽屉。
- **工具栏**：不加按钮；当前扫描有结果时配色分段里才出现「重复」，C 键也只在那时轮到它。

| 文件 · 没参加或没有伙伴、跳过 | `treemap.class.other` | — |
| 文件 · 待核对 | `treemap.dupe.pending`（中性） | 细 135° 斜纹：还没结论，不叫「重复」 |
| 文件 · 多余 | `treemap.dupe.share.4`（品红） | 细 45° 斜纹 |

| 文件 · 同一份数据 | `treemap.dupe.shared`（灰） | — |
| 文件夹、折叠块、聚合块 | 分档 → `treemap.dupe.share.1–4` | 聚合块保留点阵；第 4 档（≥80%）的折叠文件夹也加点阵，和多余的文件（同色加斜纹）分得开 |

火焰图、火焰-极坐标图里文件同样带斜纹和保留方的描边，展开的文件夹条也用这个色阶，成为一张「每层文件夹的多余字节」热图。斜纹的第二色是填充色的深浅变化（亮的填充压暗 18%，暗的提亮 14%）；斜纹上的大小那一行改用名称的颜色（暗色主题下副标签色只有约 3.5:1）。浅色主题的「同一份数据」改成浅的中性色 #D2D5DA，删了不腾空间的块不再最显眼。

**图例**：抽屉里一块可以收起的图例；抽屉关着而视图在「重复」配色时，画面左下角也有一块：五种文件状态和四档文件夹，写明门槛（有一点、≥10%、≥40%、≥80%）。色值两个主题都**暂定，待用户评审**；色盲时靠图案区分。结果清除后，这个配色的视图回到「类别」。

### 10.3 点亮一组（所有窗格）

`classMarks` 推广成 `rowMarks(g, f, pick, scope, dpr)`，类别点亮是它的一个特例。抽屉里悬停组行、「重复」配色下悬停一个块（悬停卡出现时）、右键「点亮它们」设全局的焦点组：画面里的同组行按 `dupg` 立刻点亮；100 ms 后请求 `dupes.locate`，后端给出这一帧里每一份所在的行（藏在折叠文件夹或「N 个小项」里的给那一块），所以在别的配色下（帧里没有 `dupg`）悬停抽屉里的组也能点亮。最多点亮 2000 份，超出时抽屉写「只点亮最大的 2000 份」。画在呼吸画布上，不借用闪烁和呼吸，不画连接线。

### 10.4 悬停卡

`tree.node` 在扫描有结果时附 `dupe`：已核对的写「另有 N 份内容相同 · 删掉多余的能腾出 X」、最多 2 条路径、其他卷、画面里没画出来的份数、「这一份是多余的」或保留的原因；待核对的只写「同样大小的文件正在核对内容…」，不做身份断言；同一份数据写「删了不腾空间」；跳过的写原因；比较过而没有伙伴的（状态 `unique`）写「比较过：没有别的文件和它内容相同」；文件夹写「里面有多余的副本 X」。右键菜单打开时悬停卡隐藏。

### 10.5 「重复文件」抽屉

占据侧栏，优先级：删除篮 > 重复文件 > 过滤结果 > 扫描详情 > 详情面板。内容跟随当前页签。自上而下：范围、下限和负载档；开始前的计划（同大小的候选数；**最坏要读多少**、按上次在这里的速度大约多久、盘的类型、最多能腾出多少；头尾要读多少、大小独一无二的不读；没有比较的各类和原因，下限写成大小；上一次的结果；跨盘开关和要比较的扫描（只取开着页签的，可逐个去掉）；负载档和可选的上限：最多读多少 GB、最多多少分钟；估计失败时写原因并给「重试」）；可腾出（按卷）；漏斗即进度（同样大小 → 同一个文件的几个名字算一份后 → 缓存认出 → 读了头尾 → 内容相同 N 组）、已读多少、没有比较的原因；运行条（%、阶段、速率或「速度估计中」、「最多还要 N 分钟」、负载、暂停、停止；停下或出错时进度条停在实际位置并变灰，写「还有 N 个候选没核对，结果不完整」）；覆盖条（问过某个文件夹时）；图例；保留规则；「组 | 按文件夹」两页和排序，第二行是筛选（按名字或路径、只看当前文件夹、只看跨盘、也列同一份数据）；底部是「清理方案…」（带可腾出的大小），上面一行写「逐组选保留哪几份、其余的怎么处理（回收站、硬链接、符号链接、块克隆），看过风险、确认之后才会改动文件」；查找没完成、没有可以清理的组、后端不支持时它是灰的并写原因。点了当前标签进入清理模式（§16.13.2）。

组行是紧凑的：一行写名字、份数、单份大小和可腾出，结论是图标（悬停看文字），每份一行；路径按组里各份的公共前后缀缩写，只留互不相同的那一段和文件名（`C:\…\site-old\…\intro.mp4`），完整路径在提示里；保留方的原因在它的角色标签上；「保留这一份」在悬停、键盘聚焦、点亮时出现；别的扫描的那份点了切到它的页签并定位。运行中核对完的组随时插入：刷新时把显示过的组分页（每页 500）全部取回，新组插到它该在的位置，列表长度不变、不跳。

### 10.6 每帧成本

只在「重复」配色的视图里每行多 5 B；查找 O(行数 · log 成员数)（评审在 5 万行的帧上测得约 29 ms，之前写的 0.5 ms 不对；其中每行一次的 Python 列表推导已换成按组号取的 numpy 数组）；待核对、跳过、没有伙伴的节点表每 0.5 s 至多重建一次，不随每组完成都失效；`locate` 只对聚焦的组做，上限 2000。组列表和文件夹列表是预排序数组的分页切片。渲染进程不持有 O(N) 的东西；点亮复用呼吸画布，空闲时缩成 0×0。

## 15. 没在真机验证的

- macOS 的全部读法（§5.4）、APFS 克隆识别（没做）；
- WinBtrfs 上的块映射和文件 ID；
- 属性句柄上能不能取到 USN（取不到时按「没有 USN 的卷」处理）；
- `FILE_OPEN_NO_RECALL` 对云过滤驱动是否有效（所以先按属性剔除）；
- HDD 上的读盘顺序（本机没有 HDD；第一期 HDD 只是不交接句柄、每步读 64 MiB、每批 100 ms，按物理位置排序在第二期）；
- macOS 上关掉无数据文件下载的 `setiopolicy_np`（§5.4）；
- btrfs 上跨子卷的块映射比较（§4.3；本机 WSL 是 ext4，只有单元测试）；
- 根下挂的真实 NFS、SMB、FUSE 挂载（§5.3；测试用打桩的卷）；
- Windows 上只差大小写的同名项（WinBtrfs、区分大小写的 NTFS 文件夹）真的存在时判 `ambiguous`（§5.2；单元测试只覆盖了大小写不同但没有同名项的情况，有同名项的真实目录要设 `SPACEKNIFE_TEST_CASE_ROOT`）；
- 「安静」档时间份额在 SATA 盘上的实际 active% 和 MB/s（另一个流程在这台机器上计时，评审要求的验收没有做）。

清理的实机验证（§16.19）顺带验证了查找的几项：WinBtrfs 上 128 位文件 ID 作身份可靠（换成硬链接后再查一次，同一个文件的几个名字合成一份，读 0 字节）；WinBtrfs 的块映射不可信（`FSCTL_GET_RETRIEVAL_POINTERS` 没到文件末尾就返回「完成」，中间夹着零长度的 LCN −1 段），ReFS 上刚写下的数据块还没分配（LCN −1），这两种映射现在都算不完整，不用来认定「同一份数据」（`share.rs`，§16.20）；btrfs 嵌套子卷里的文件认得出文件系统（`scan/volume.py` 的 `_linux_volume`），子卷之间能块克隆。

## 16. 清理方案

查找只给信息；把重复文件变成腾出的空间，只经这里的清理方案。**没有一键删除**：每组自己选保留点，其余每份选一种处理（不动、移到回收站、换成硬链接、换成符号链接、块克隆），做不到的处理不给并写明原因；风险逐份、按处理写明，引用证据，分五级，高风险按类确认；方案先审阅、批准，执行前再核对每一份，执行后能撤销。唯一不可逆的一步是「清除恢复区」，要单独确认、等 5 秒，删之前再核对。

代码：后端 `packages/backend/src/spaceknife/dupes/cleanup/`（`policy.py` 规则、预设和像副本的名字，`keep.py` 保留引擎，`caps.py` 能不能做，`facts.py` 事实和风险核查，`risks.py` 风险目录，`plan.py` 方案、编辑、批准，`edits.py` 编辑和预览，`query.py` 筛选，`views.py` 给界面的页、摘要、导出，`persist.py` 存盘，`fsops.py`、`winfs.py` 文件原语，`execute.py` 预检、执行、撤销、清除、收尾，`journal.py` 日志，`recovery.py` 恢复区），服务 `server/dupes_cleanup.py`、`server/dupes_cleanup_handlers.py`，协议 `spaceknife_protocol/dupes_cleanup.py`（能力 `dupes.cleanup.v1`，要求同时声明 `dupes.v1`），前端 `apps/electron/src/renderer/src/state/cleanup.ts`、`shell/cleanup/`，测量工具 `spaceknife dupes-cleanup`（`cli_cleanup.py`）。

本节编号沿用设计稿：§16.N 对应设计的第 N 节，代码注释里的 `docs/dupes.md §16.x` 指这里。做法和设计不同的、还没做的，集中写在 §16.17。

| 清理之后检测结果照实，缓存不改 | §16.11 |

### 16.2 不变式（后端强制）

- **I1 内容在**：执行期间每一刻，每组的内容至少在一份核对过、这次运行不碰的保留点里。保留点从不是任何一步的对象。开着「每卷一份」时，跨卷的组要求同卷的保留点完好。
- **I2 不盖名字**：执行器从不覆盖已有的名字。POSIX 用交换（Linux `renameat2(RENAME_EXCHANGE)`，macOS `renameatx_np(RENAME_SWAP)`，没验证）；Windows 用两次按句柄、不覆盖的改名（`FileRenameInformation`，ReplaceIfExists = FALSE）；进恢复区用不覆盖的改名；临时名独占创建。原件每一刻至少有一个名字：原来的、临时名或恢复区里的。
- **I3 先核对再动**：动一个名字之前，在同一步里经句柄或文件夹描述符核对它的身份、戳、链接数。打开都相对于核对过的文件夹，不跟随链接；只有核对新建的符号链接指向哪里时才跟随。执行器只删它自己建的名字，删之前再核对身份。
- **I4 只有清除不可逆**：原件在恢复区、副本在回收站时，每一步都能撤销。
- **I5 执行的就是批准的**：执行要拿批准时的令牌，令牌对应一份冻结的步骤清单；批准之后的任何编辑都让它作废。
- **I6 只少不多**：预检和执行可以跳过某一步，从不加一步，也从不改一步（换目标、换处理、换保留点都算改）。做不了的那一步记跳过，原因写进结果。
- **I7 查不到就按有风险算**：风险核查还没看到的份记「还在核对」（中），核查没做完不能批准；读不到权限的按「所有者或权限不同」（高）。
- **I8 同一时间只做一件文件操作**：清理的运行和删除篮的执行共用 `OpsService` 的忙碌判断，两边都会拒绝「还有文件操作在进行，完成后再执行」。
- **I9 结果照实**：清理自己造成的变化直接写进结果（§16.11.1）；别人造成的变化照旧让组退回「待核对」。
- **I10 先写日志再动手，启动时先收尾**：每批的意图在动手前写进日志并落盘；中断的运行在后端接受任何会话之前，按日志和盘上的实际身份收尾。
- **I11 不低于底线**：每组至少留 `max(1, keep_n)` 份；开着「每卷一份」时跨卷组每卷一份。编辑时后端检查，违反的编辑被拒。
- **I12 只处理核对过的组**：只有读完全文、BLAKE3-256 相同的组进方案；失效、同一份数据、没有多余的、排除的组列在「不在方案里」，写明原因。
- **I13 沙箱**：设了 `SPACEKNIFE_CLEANUP_SANDBOX`（测试、测量工具、实机验证）时，执行、撤销、清除、收尾在每个文件原语调用之前核对涉及的每条路径（文件、文件夹、临时名、恢复区）都在沙箱里，否则这一项记「没有权限」，不发任何系统调用。
- **I14 能证明才清除**：清除的每一份原件，要证明它从移进恢复区以后没变过，并且它的内容此刻还在保留点里。

### 16.3 对象与术语

```
查找作业 → Results（内存，dupes/results.py）           成员表 64 B / 份
  └─ 清理方案 CleanupPlan（每个作业至多一个，用户打开时才建；按成员行建数组）
        ├─ 策略 Policy（规则、手动选择、选项、过目标记；可以存盘、导出）
        ├─ 编辑历史（撤回、重做，最多 200 步）、版本号、风险的确认
        └─ 批准 Approval：冻结的步骤清单 + 令牌
              └─ 运行（服务端）──▶ data_dir()/dupes/cleanup/runs/<运行号>/（重启后还在）
                    └─ 原件在恢复区、副本在回收站，直到清除或撤销
```

| 词 | 意思 |
|---|---|
| 保留点 | 留着不动、作为别的份的依据的那份；一组可以有几个 |
| 处理 | 对不保留的份做什么：不动、移到回收站、换成硬链接、换成符号链接、共用数据块（块克隆） |
| 原件 | 被换成链接的那份原来的文件 |
| 恢复区 | 和原件同一个卷的 SpaceKnife 文件夹，原件留在这里直到清除或撤销（§16.9.6） |
| 批准 | 冻结方案的一版，得到令牌；之后的编辑让它作废 |
| 运行 | 一次执行，有自己的日志；可以撤销、清除 |
| 清除 | 永久删除恢复区里的原件；唯一不可逆的一步 |

- 方案跟着作业活：关掉扫描、换了作业，方案的草稿丢掉，运行和日志留着。
- 手动选择按 (组的内容摘要, 路径) 记，所以同一批扫描再查一次之后照样对得上。

### 16.4 保留点

#### 16.4.1 层次（前面的先定；每份记下出自哪一层、哪一条）

| 层 | 内容 | 能不能被后面的层推翻 |
|---|---|---|
| 1 锁定 | 程序需要或受保护（`F_NEEDED`）；名字以点或空格结尾、另有扫描以外的硬链接（`F_PINNED`）；有几个名字的物理文件；网络盘上的；版本库内部（`.git`、`.hg`、`.svn` 里）的；「视图」行跟着它代表的那份 | 不能 |
| 2 每份手动 | 「保留这一份」（加一个保留点）、「不保留这一份」、这一份的处理和目标 | 只受底线约束 |
| 3 每组手动 | 整组的保留集合（「只留它」= 只保留这一份，其余不保留）、「这一组不动」（排除） | 不能 |
| 4 文件夹对规则 | (a, b) → 保留 a 那边 / b 那边 / 两边都留，另一边的处理可选 | 只被 1–3 推翻 |
| 5 保留规则（有顺序） | 选择器 + 效果（§16.4.3） | 只被 1–4 推翻 |
| 6 基本判据 | 一串判据，一样时看下一项（§16.4.4） | — |
| 7 安全兜底 | 每组至少留 `max(1, keep_n)` 份，开着时每卷一份 | 兜底定下的保留点单独标出 |

处理只看不保留的份，依次是：每份手动的处理 → 文件夹对规则给的另一边的处理 → 处理规则（从上往下第一条命中的；做不到时按这条规则的后备链往下试，最后是「不动」）→ 预设的默认处理。

#### 16.4.2 语义：保留集合只会因约束变多，规则只决定由谁补位

- 保留集合 = 锁定的 ∪ 手动保留的 ∪ 每组的保留集合 ∪ 文件夹对「两边都留」的 ∪ 命中 `keep_all` 的 ∪ **补位**。
- 补位来自约束，依次是：每卷一份（跨卷时，开着才算）、每个文件夹一份（`per_folder` 规则）、`keep_n`（命中的规则里要得最多的那个）、至少一份。补位时候选是还没保留、也不是手动「不保留」的份，一步步收窄，某一步会收窄成空时跳过这一步，剩一个时由这一步定下，记成理由：文件夹对的那一边 → `prefer` 规则（按规则顺序，规则里的文件夹也按顺序）→ `avoid` 规则（只要还有别的候选，就去掉在这里的）→ 文件夹一致的那一边 → 判据（带 `order` 的规则用它自己的判据，否则用基本判据链）→ 路径短的，再按字典序。
- **除了手动「不保留」，没有任何规则能减少保留点。** 文件夹对「保留 a 那边」只决定补位给谁：开着每卷一份时，b 的卷照样补一份。
- 手动把一组所有的份都设成「不保留」时，兜底留一份并标出来（`safety_net`，测试 `test_manual_not_keep_on_every_copy_uses_the_safety_net_visibly`）；取消最后一个保留点的编辑被后端拒绝（§16.4.6）。

#### 16.4.3 选择器和保留效果

选择器（`policy.Selector`）的各项都是「并且」：`under`、`not_under`（含子文件夹，卷根也行）、`volumes`、`fs`、`ext`、`classes`（文件类别）、`name_glob`、`path_glob`、`size_min`、`size_max`、`copies_min`、`cross`（组跨卷）、`same_folder`、`mtime_before`、`mtime_after`、`tags`（事实标签，任一）、`not_tags`、`can`（这些处理在这里都做得到）、`same_volume`（同卷有保留点），以及只给风险条件规则用的 `risk_at_least`、`risk_any`。选择器在方案的数组上算成掩码，`under` 和通配按父文件夹缓存。

| 保留效果 | 意思 |
|---|---|
| `keep_all` | 命中的份全部保留（加约束） |
| `prefer` | 补位时优先，参数是有顺序的文件夹列表 |
| `avoid` | 补位时尽量不选；全组都在这里时照样留一份，标「只能留在不想留的地方」 |
| `per_folder` | 每个文件夹各留一份（加约束） |
| `keep_n` | 至少留 N 份（加约束，N ≥ 1） |
| `order` | 这条命中的份补位时，先用它自己的判据 |

#### 16.4.4 基本判据

`oldest_created`（最早创建；文件系统没有创建时间时用修改时间）、`oldest_modified`、`newest_modified`、`shortest_path`、`longest_path`、`shallowest`、`deepest`（扫描根以下的层数）、`plain_name`（名字不像副本）。

- 默认判据链是「最早创建 → 名字不像副本 → 路径最短」（设置 `dupes.keep_criteria`；第一项跟着抽屉的「默认保留」`dupes.keep_rule`）。判据链只留抽屉那一条时，每组的保留点和抽屉逐组相同（§8.2）。
- `plain_name` 认这些样式：`x (1).jpg`、`x(2).jpg`、`x - Copy.jpg`（以及 copy、副本、コピー、Kopie、Copie、Copia，可带序号）、`Copy of x.jpg`、`x_copy.jpg`、`x 副本.jpg`、`x的副本.jpg`。只有去掉这个样式后的名字等于组里另一份的名字时，才算像副本（`x (1).jpg` 旁边有 `x.jpg`）。

#### 16.4.5 文件夹对与卷

- **对**：每组里每两份的父文件夹记一对，统计组数、字节和**双向覆盖率**（b 的文件有多少在 a 有一份，反过来也一样）。两边相对路径一致的子文件夹对合并到上一级。
- **对规则**：`{a, b, keep: a|b|both, other_action?}`，只对在 a、b 两边都有份的组生效。
- **文件夹一致**（`dupes.folder_consistent`，默认开）是自动生成的对规则，在规则栏里看得见、可以关。
- **卷**（跨盘时）：卷 × 卷，每格写组数和字节。

#### 16.4.6 手动选择和底线

- 每份能做的：「保留这一份」（另加一个保留点）、「只留它」、「不保留这一份」、选处理、选链接或块克隆的目标；每组能「这一组不动」（排除）。「清除手动」把选中的组（或整个方案）恢复成按规则。
- 手动选择按 (组摘要, 路径) 记，可以累积，改规则之后还在。
- 违反底线的编辑由**后端拒绝**并写明原因：「每组至少留一份：先选另一份做保留点」「{卷} 上至少要留一份（每卷一份开着）」「这一份必须保留」「核对之后文件变了，这一组要再查一次」。界面也把最后一个保留点的开关灰掉，写「唯一的保留点」，但以后端为准。

#### 16.4.7 冲突与兜底

- 同一层里两条规则对同一份给出不同的结论时，按顺序取第一条，这一组标「规则冲突」（筛选 `conflict:yes`）。
- `avoid` 让一组没有别的候选时，照样在不想留的地方留一份，标「只能留在不想留的地方」。
- 兜底定下的保留点，来源写「兜底」，审阅页「不做的和兜底的」写出组数。

#### 16.4.8 理由链

- 每份存保留和处理两个来源（层、规则号），界面上的话在显示时才生成：「你手动选的」「在优先保留的 {folder} 里（第 {rank} 位）」「{vol} 上至少留一份」「按『{判据}』保留」「一样时取路径短的」「这组本来一份都不留，按『每组至少留一份』留下这一份」「规则 {n}：{label}」「规则要{want}，做不到（{why}）→ 后备：{act}」「预设『{preset}』：{act}」「规则 {n}：有{risk}的 → 不动」等（`codes.TEXT` 的 `src_*`）。
- 检查器显示完整的链：每一层对这份说了什么、哪一层最终定下。组的抬头写「理由：路径」。

#### 16.4.9 风险条件规则（不会循环）

- 处理规则可以带 `risk_at_least` 或 `risk_any`（「任何高风险 → 不动」「会丢『来自网络』标记 → 不动」）。它们的效果**只能是「不动」**（后端拒绝别的：「带风险条件的规则只能改成『不动』」）。
- 先按其余规则定出每份的处理，再算风险，然后对带风险条件的规则逐条检查，命中的改成「不动」；「不动」没有风险，所以再算一遍就到头了。被拦下的份数写在审阅页和每次编辑的回执里。

#### 16.4.10 目标：链接或块克隆指向哪一份

- **硬链接**：同卷的保留点（btrfs 上还要同一子卷：卷是按 `st_dev` 分的，子卷各有各的）；保留点的名字数加上这次计划加的到了上限时不给（`link_limit`）。
- **块克隆**：同一个文件系统、能共用数据块的保留点（btrfs 的不同子卷可以，按文件系统分组）。
- **符号链接**：任何保留点。
- 有几个合格的保留点时，依次挑：同一个文件夹的、同卷的、不在可移动盘上的、路径公共部分最长的。规则可以写 `target_under`（「都指向 D:\Photos 里的那份」，「备份盘整理」预设用它指向备份盘）；每份可以手动换目标，只能在合格的保留点里选（「只能指向这组里合格的保留点」）。

### 16.5 处理

#### 16.5.1 五种

| 处理 | 这个路径上变成什么 | 什么时候腾出空间 | 怎么撤销 |
|---|---|---|---|
| 不动 | 什么都不做 | — | — |
| 移到回收站 | 经 `ops/trash.move_to_trash`（带守卫；从不永久删除）；卷上没有回收站时按设置放进恢复区（§16.9.6）或不动 | 清空回收站（SpaceKnife 不替你清空）或清除恢复区之后 | 从回收站还原；在恢复区的改名放回 |
| 换成硬链接 | 这个路径成为保留那份的另一个名字；原件进恢复区 | 清除恢复区之后 | 把原件换回来 |
| 换成符号链接 | 这个路径成为指向保留那份的链接（相对或绝对）；原件进恢复区 | 清除恢复区之后 | 把原件换回来 |
| 块克隆 | **就地**：文件名、身份、权限、时间、备用流都不变，数据块和保留那份共用 | 马上（快照占着的除外） | 不需要：内容、名字、属性都没变 |

不做的：永久删除（只有清除能删）；Windows 的 `.lnk` 快捷方式（程序不认）；目录联接；整个文件夹换成链接或删掉；设计里的「克隆加交换」（建一个和保留那份共用数据块的新文件再换上，§16.17）。

#### 16.5.2 哪里能做（`caps.py`）

卷的能力取自扫描的卷信息：Windows 看卷标志（`FILE_SUPPORTS_HARD_LINKS`、`FILE_SUPPORTS_REPARSE_POINTS`、`FILE_SUPPORTS_BLOCK_REFCOUNTING`），POSIX 看文件系统类型；回收站来自 `trash_status`。查不清的一律不给。

| 文件系统 | 回收站 | 硬链接 | 符号链接 | 块克隆（就地） | 换上替身的办法 |
|---|---|---|---|---|---|
| NTFS | ✓ | ✓（每个文件最多 1024 个名字） | 要「开发人员模式」或 `SeCreateSymbolicLinkPrivilege` | ✗ | 两次不覆盖的改名 |
| ReFS | ✓ | 卷报告硬链接标志时（测试用的 ReFS 3.14 卷报告了） | 同 NTFS | ✓ `FSCTL_DUPLICATE_EXTENTS_TO_FILE`，先逐段比较 | 同上 |
| WinBtrfs | ✓ | 看卷标志（测试用的卷上能） | 看卷标志（测试用的卷上能） | ✓ 同 ReFS | 同上 |
| FAT、exFAT | 看卷 | ✗ | ✗ | ✗ | — |
| ext4、f2fs 等 | ✓ freedesktop | ✓（同一挂载） | ✓ | ✗ | `RENAME_EXCHANGE` |
| btrfs | ✓ | ✓ 同一子卷 | ✓ | ✓ `FIDEDUPERANGE`，子卷之间也行；关掉写时复制（`chattr +C`）的不行 | `RENAME_EXCHANGE` |
| xfs | ✓ | ✓ | ✓ | 格式化时开了 reflink 才行：方案里读文件系统几何信息（`XFS_IOC_FSGEOMETRY`）判断，问不到时照常给、执行时第一次被拒就停用这个卷 | `RENAME_EXCHANGE` |
| bcachefs、ocfs2 | ✓ | ✓ | ✓ | 给（`FIDEDUPERANGE`），没在真机验证 | `RENAME_EXCHANGE` |
| APFS、HFS+（macOS） | 废纸篓 | 设置 `dupes.cleanup.macos_links` 打开才给（默认关，没验证） | 同左 | ✗（设计里的 `clonefileat` 没做） | `renameatx_np(RENAME_SWAP)`，没验证 |
| 网络盘、FUSE | 只能「不动」 | ✗ | ✗ | ✗ | — |

- **Linux 交换**：每个卷第一次用时拿两个不存在的名字试一次 `RENAME_EXCHANGE`（什么都不写），不支持的卷上替换类的处理都不给（`no_exchange`）。
- **Windows 符号链接权限**：开发人员模式看注册表 `AppModelUnlock` 的 `AllowDevelopmentWithoutDevLicense`，令牌里有没有 `SeCreateSymbolicLinkPrivilege` 用 `GetTokenInformation` 查；两者都没有时所有份的符号链接都不给（`no_symlink_right`）。
- **Linux `fs.protected_hardlinks`**：开着时，只能链到自己的文件或自己能写的文件（`protected_hardlinks`）。
- **Windows 上的替换和块克隆要原生读法**：查找没用原生扩展时，身份和执行器的对不上，这几种处理不给（`no_native`）。

#### 16.5.3 做不到时的原因码（`codes.NA_*`，31 个）

#### 16.5.4 预设

预设换的是处理规则，不碰手动选择和用户自己的保留规则，先预览再确认。设置 `dupes.cleanup.preset` 是新方案的预设。

| 预设 | 处理规则 |
|---|---|
| 只看，不动 | 全部「不动」 |
| 保守 | 不保留的 → 回收站 |
| **推荐**（默认，待用户确认） | ① 同步盘、版本库、应用、程序、游戏、媒体库、卷根的隐藏临时文件、链接目标 → 不动；② 能就地共用数据块 → 块克隆；③ 其余 → 回收站；④ 任何高风险 → 不动 |
| 链接优先 | 文档、表格、代码、数据库类 → 回收站；同卷的 → 硬链接；任何高风险 → 不动；其余不动 |
| 备份盘整理 | 每卷一份关；备份盘上的全部保留；其余 → 指向备份盘的符号链接，做不到时不动；任何高风险 → 不动（只经协议和测量工具选，设置里没有这一项） |
| 自定义 | 用户自己的规则 |

「推荐」里没有链接，默认方案里没有要确认的高风险；被 ④ 拦下的份数写在审阅页。

### 16.6 风险

#### 16.6.1 等级

| 等级 | 标记 | 意思 | 执行前要做什么 |
|---|---|---|---|
| 提示 | · | 值得知道，不会造成损失 | 无 |
| 低 | ○ | 小的意外，事后容易察觉、补救 | 无 |
| 中 | ■ | 可能出乎意料，补救费事 | 审阅页看得见、计数，不拦执行 |
| 高 | ▲ | 可能丢数据、泄露、程序出错，或者丢掉从没比较过的东西 | **按类确认**，确认的是当时看到的那批份；没确认完不能批准 |
| 不可用 | ⊘ | 在这里做这件事不安全 | 处理不给，写原因（§16.5.3），不能靠确认绕过 |

一份的等级是它当前处理下所有风险里最高的，一组的等级是组里各份里最高的。等级在界面上带文字，不只靠颜色。

#### 16.6.2 事实：从哪来、什么时候取

**便宜的事实**，建方案时从扫描和查找已有的东西算，不对每个文件发系统调用，每份一个 64 位的标签字：

- 扫描的属性位：隐藏、系统、只读、加密、稀疏、压缩、临时；
- 卷：可移动、网络、文件系统、能力、回收站；
- 文件夹：版本库工作区和内部（在扫描树里按名字找 `.git`、`.hg`、`.svn`）、工程（`package.json`、`Cargo.toml`、`pyproject.toml`、`*.sln`、`*.csproj`、`*.uproject`、`*.lrcat` 等）、Syncthing 的 `.stfolder`、媒体库（Lightroom 目录、iTunes 媒体、照片图库包）、macOS 的包、像备份（路径最后三级里有 backup、bak、备份、副本、归档、archive、old、旧、File History、Time Machine 之类）、已知文件夹（下载、桌面、临时、AppData、`~/.config`、`~/.local/share`、`~/.cache`、`~/Library`）、洞察规则库的 kind 和 cleanup（应用、聊天、虚拟机、游戏、缓存、构建、系统；`cleanup = "safe"` 会被自己的程序清理，`"keep"` 是程序要用的）、受保护的路径；
- 同步盘的根：Windows 的 `SyncRootManager` 登记、OneDrive 的账户文件夹和 `OneDrive*` 环境变量、Dropbox 的 `info.json`、Nextcloud 的 `nextcloud.cfg`、Syncthing 的 `config.xml`；Linux 上 Dropbox、Syncthing、Nextcloud、ownCloud、abraunegg onedrive 的配置；macOS（没验证）`~/Library/CloudStorage/*`、`~/Library/Mobile Documents`。几个小文件和注册表键，缓存 60 秒；读不了的配置不让方案失败；
- 名字：就地写的格式（虚拟盘、数据库、邮件库、`.psd`、`.blend`、`.kdbx` 等）、可执行文件和脚本、带宏的文档、压缩包和安装包、字体和驱动、文档类、媒体类；
- 时间：24 小时内改过、7 天内改过（修改时间和更改时间取新的）；
- 查找：组靠缓存认定、卷上没有 USN（Windows）；
- SpaceKnife 以前建的符号链接的目标（各次运行的日志汇总成的索引）；删除篮盖住的。

**风险核查**（`facts.probe`），每份一次只取元数据的查看，后台跑，走这块盘的调速器许可，每批 256 份；不打开数据、不召回云文件、不改访问时间：

- Windows：所有者、显式 ACE 和继承 ACE 的摘要、备用流的名字和大小（有没有 `Zone.Identifier`）、属性、链接数、文件夹能不能写、ReFS 完整性流；所有者的 SID 写成账户名；
- Linux：uid、mode、POSIX ACL、SELinux 标签、扩展属性（`user.xdg.origin.url` 算「来自网络」）、inode 标志（不可改、只追加、不写时复制）、链接数、能不能写；
- macOS（没验证）：标志、ACL、扩展属性（`com.apple.quarantine`）。

核查的对象是有处理的份和它们对照的保留点，先查这些，再查其余的。顶栏写「风险核查 {pct}%」。一对（这份和它对照的保留点）的差别（所有者、两种 ACE、mode、SELinux、「来自网络」、EFS、附加数据、修改和创建时间差 2 秒以上、只读和隐藏、名字）在决定变了时现算，不再查盘。

#### 16.6.4 计算

风险是对方案数组的向量运算：每条一个函数，给出每份的等级（证据不在就是 0）。每次编辑后重算，话只为显示出来的份生成。

#### 16.6.5 一般说明

没有逐份证据的写在处理的说明里一次，不算风险：硬链接「很多程序保存时先写新文件再改名，这会悄悄断开硬链接」，块克隆「改动任何一份，改动的部分会重新占用空间」，回收站「清空回收站后才腾出空间」。

#### 16.6.6 确认

- 审阅页按类列出高风险：标题、份数、组数、字节；「看这些」展开分页的份列表（每份带证据），确认的勾选框在列表下面：不看到具体的份就确认不了。另一种走法是这一类对应的批量改法（「改成不动」），同样先看预览。
- 确认记成 (风险编号, 当时这一类里各份的键)。集合变小时确认仍然有效；多了一份，这一类显示「又有 {n} 份落进这类风险，要再确认」。确认算进令牌，也写进运行日志（哪几类、多少份）。存盘的编辑不带确认，接着改时要重新确认。

### 16.7 审阅、批准、导出

#### 16.7.1 摘要（顶栏，随编辑变）

腾出（马上 / 清空或清除之后）、组数和份数、各级风险的份数、风险核查的进度、方案的版本和状态（编辑中 / 已批准）。

#### 16.7.2 审阅页（清理模式里的「审阅并执行…」）

按处理（份、组、马上腾出、清空或清除之后）、按卷（「{vol} 马上 {now}，之后 {later}」，恢复区在哪：只在真有原件要放进恢复区的卷上写，位置和执行器的选择相同）；核对方式和出错时的做法；风险分桶（要你确认（高）、值得看一眼（中）、低和提示）；「不做的和兜底的」（必须保留、文件变了、同步盘里不建链接、被风险条件规则拦下、兜底保留、规则冲突）；抽查（「抽查：每类随机 10 组」，分层抽样 `dupes.cleanup_sample`）、已过目多少组；导出 JSON、CSV（写明不提供「导出成脚本」：脚本没有执行前的核对）；「只预检」「批准」「执行…」。按钮灰着时写出差什么（§16.7.5）。

#### 16.7.3 筛选（`query.py`）

| 写法 | 意思 |
|---|---|
| `risk:high`、`risk:motw_lost`、`risk:H05`、`sev:>=medium` | 按等级或风险 |
| `action:hardlink`、`action:!leave`、`avail:symlink`、`-avail:hardlink` | 按处理、按能不能做 |
| `vol:D:`、`fs:refs`、`cross:yes` | 卷、文件系统、组是否跨卷 |
| `in:"D:\Photos"`、`name:*.psd`、`ext:jpg,png`、`class:document` | 位置、名字、类别 |
| `size:>100MB`、`copies:>=3`、`mtime:<2020-01-01` | 数值 |
| `source:manual`、`source:rule:3`、`source:fallback`、`source:safety_net`、`source:pair`、`source:preset`、`source:risk`、`source:forced`、`conflict:yes` | 来源 |
| `reviewed:no`、`changed:yes`（过目后决定变了）、`acked:no`、`state:stale` | 审阅状态 |
| `tag:sync`、`tag:vcs`、`tag:backup` … | 事实标签 |
| 其他文字 | 路径里含这段 |

几项之间是「并且」，前面加 `-` 是取反。**读不懂的项（打错的键、对不上的值）不会被悄悄忽略**：这样的筛选一组也不列，并在筛选框下面写出读不懂的部分；否则打错字可能让「符合筛选的全部」的批量改波及更多组。后端另有分面计数（`dupes.cleanup_facets`），界面还没用。

#### 16.7.4 批量编辑和预览（`edits.py`）

- 编辑的范围是组、份，或筛选条件（「符合筛选的全部 {n} 组」，Ctrl+A 勾选显示出来的组）。编辑的种类：保留（加、减、只留、整组集合、清掉）、处理、目标、排除和恢复、清除手动、规则（加、改、删、移动）、文件夹对、预设、选项、过目、确认。
- **批量改一律先预览**（`dupes.cleanup_preview`：应用、量出差别、退回，不提交）：各种处理改前改后的份数，腾出改前改后，做不到的份按原因（保持原来的决定），新增和不再有的风险（写名称不写编号），被风险条件规则拦下的份数，有手动选择的份数（默认不改，可以勾「也改你手动选过的 {n} 份」），前几份的例子。
- 每次编辑版本号 +1、批准作废；`base_version` 对不上时报「方案已经变了（第 {now} 版）：刷新后再改」（乐观并发）。撤回、重做最多 200 步。每次编辑的回执写做了什么，例如「已改 3 份（3 组），其中 3 份有高风险，按规则改成了不动」。

#### 16.7.5 执行门槛（按钮灰着时写出差什么）

风险核查做完了；每个高风险类都确认了；方案在批准之后没再改；涉及的扫描没有查找作业在跑、没有扫描在跑；没有别的文件操作在跑；没有中断后要你看一下的项；方案里有要做的事。日志写不进去时执行被拒：「写不了清理日志 {path}，没有动任何文件」。

#### 16.7.6 批准与令牌

- `dupes.cleanup_approve` 把方案冻结成步骤清单，按执行顺序排（§16.9.8）。每一步记：序号、组和内容摘要、处理、路径、卷、副本的身份和戳（大小、修改时间、更改时间、USN）、父文件夹和它的身份、这组要保持完好的保留点（开着每卷一份时是同卷的）和它们的戳、目标保留点、符号链接的文字、风险、要不要重读内容。
- 令牌是 BLAKE2b-128（规范化的步骤 ‖ 确认 ‖ 选项）。批准之后任何编辑都清掉批准。
- 监控报来的变化让组失效（方案的版本因此变了）。设计要求这时不清掉批准、只让预检跳过那几步；现在的实现里版本变了，界面在用户点「执行…」确认后自动重新批准当前的版本（确认框里写的是当前的数字），是否改成后端保留批准待评审（§16.17）。
- 「只预检」先批准，再做一遍不写任何东西的预检，批准保留。

#### 16.7.7 导出、导入、存盘

- **JSON**（`spaceknife.dupes-cleanup.v1`）：规则、选项、每组每份的决定和来源、风险（编号、等级）、腾出。能导回（`dupes.cleanup_import`）：按 (摘要, 路径) 对上的采用文件里的决定，对不上的列出来；导入的只是编辑，照样要审阅、确认、批准。界面还没有导入的入口。
- **CSV**：一份一行。**运行报告**：JSON 和 CSV，逐项写结果、原因、恢复区里的名字、腾出。导出写到用户在保存对话框里选的位置，只存在本地。
- **存盘**：离开清理模式（`dupes.cleanup_close`）时把规则、选项、手动选择（摘要 hex、路径）、过目标记写进 `data_dir()/dupes/cleanup/plans/<扫描根的指纹>.json`，**不存确认**。同一批扫描根再打开方案时问「接着上次的清理方案？」（写出时间、手动选择和规则的数目），对上的照用，对不上的列出来。

### 16.8 预检（执行的第一阶段，只读）

在工作线程里对整次做一遍，不写任何东西（「只预检」就是只做这一步）：

1. 每个要处理的份和每个保留点做一次元数据查询，用查找的读法（Windows 在只取属性的句柄上），每批 256 个名字；
2. **要处理的那份**：存在、身份和戳（大小、修改时间、更改时间、有 USN 时也比 USN）和批准时一样（否则 `skipped_changed` / `skipped_missing`）；替换和块克隆要求链接数还是 1；没有被删除篮盖住（`skipped_in_basket`）；现在不受保护（`skipped_protected`）；按路径找到的就是它（Windows 去掉末尾点和空格的、只差大小写到了另一项的 → `skipped_ambiguous_name`）；没被别的程序打开（`skipped_locked`）；所在的卷没被这次运行判成做不了；
3. **保留点**：目标保留点（链接、块克隆），或回收站步骤这组里要保持完好的保留点（至少一个完好）：存在、身份和戳没变、没被删除篮盖住（按路径，也按身份：`guard.Elsewhere`、`_Reach`）、没被别的程序打开（`skipped_keeper_lost` / `skipped_keeper_changed` / `skipped_keeper_busy`）；
4. **硬链接名额**：目标的链接数加上这次要加的不超过上限（Windows 1024，其余按 65000 估，真正的上限由执行时的错误决定，`skipped_link_limit`）；
5. **内容**（按核对方式）：「自动」（默认）在戳证明不了「没变过」时把这份和它的保留点用查找的读法重读（不改访问时间、读前读后核对戳），摘要要等于组的摘要：Windows 上没有 USN、任一份 24 小时内改过、组靠缓存认定。「全部重读」每一步都读；「只核对文件信息」不读，原来要读的那些份带高风险 R11，要确认。块克隆不在这里读：Windows 执行时逐段比较，Linux 由内核比较。

有跳过的步骤时，界面列出清单（按原因分组），只问一次「执行其余的」；这次运行什么都没做，记一条「没有改动任何文件」的记录，后端保留批准；用户确认后重读方案，再执行其余的。

### 16.9 执行

#### 16.9.1 结构

- 同一时间只有一次运行（I8）。工作线程按批走：一批是相邻的、同一个卷上的回收站步骤（最多 64 个），替换和块克隆一步一批；从不把步骤挪出顺序，所以没有一步被跳过或做两次。
- 每批：拿这块盘的调速器许可（块克隆每段拿一次）；把这批的意图写进日志并落盘；逐步做；把结果写进日志，批末落盘；把做完的写进结果表（§16.11.1）。
- 暂停和停止只在两步之间生效，一步从不做到一半。进度 `dupes.cleanup_progress` 最多每秒 4 次。
- 关掉窗口或界面断开时后端照样做完。后端进程被结束时，下次启动先收尾（§16.10.4）。

#### 16.9.2 替换的骨架（硬链接、符号链接）

记号：副本 C 在文件夹 D 里叫 p；目标保留点 K；临时名 T = `.sk-<运行号后 6 位>-<序号>.tmp`，在 D 里；恢复区里的名字 R = `<序号>-<原名>`（§16.9.6）。

```
R1 打开 D           不跟随；身份 == 批准时的父文件夹                                  否则 skipped_parent_changed
R2 打开 C（相对 D）  不跟随，按原样的名字；Windows 只给别人共享读；
                    是普通文件、链接数 1、身份和戳没变                                否则 skipped_changed / skipped_locked
R3 打开 K           身份和戳没变（同一次运行里前面的步骤给它建过链接的，
                    更改时间、USN、链接数按那一步之后的值核对）                       否则 skipped_keeper_changed / skipped_keeper_busy
    Windows、没有 USN、要核对内容：在拒绝别人写的两个句柄下把两份再读一遍              不同 → skipped_changed / skipped_keeper_changed
R5 建替身 T          独占创建（名字被占 → skipped_name_taken）；
                    硬链接：T 的身份 == K；符号链接：是链接、文字对、跟随后是 K       不对 → 删掉 T，failed_rolled_back
R6 再核对 C          戳从 R2 起没变                                                   否则删掉 T，skipped_changed
R7 换上（不盖名字）   POSIX：交换 D/T 和 D/p，核对换出来的是 C；不是（别人刚换了 p）→ 再交换一次换回去，删掉 T，skipped_raced
                    Windows：按句柄把 C 不覆盖地改名进恢复区，再按句柄把 T 不覆盖地改名到 p；
                    后一次失败 → 按句柄把 C 改回 p（不覆盖）
R8 原件进恢复区      POSIX：D/T（现在是 C）不覆盖地改名到 R，核对是 C
R9 最终核对          p 上是替身、能指到 K；R 是 C，记下它此刻的戳（清除时用）
```

- `failed_rolled_back`：回滚之后核对过，和开始前完全一样（p 是 C、戳相同，没有 T、没有 R）。
- `failed_attention`：回滚证明不了原样。这时**整次一定停下**，不管失败策略；清理记录里写出准确的状态（「原件在 {R}，{p} 现在是……，没有删任何东西」）。例：Windows 上两次改名之间别人在 p 存了文件，C 改不回去：C 安全地留在恢复区，p 上是别人的文件，T 删掉。
- 硬链接一步做完、句柄都关了以后再取一次保留点的戳（NTFS 在关掉建链接用的句柄时又记一条 USN），只在身份、大小、修改时间都没变时采用，别人的改动照样能发现。

#### 16.9.3 每个系统的调用（`fsops.py`、`winfs.py`）

原语都在 Python 里，经 `os` 的 `dir_fd` 系列和 ctypes 调系统；没有设计里的原生 `dupes/clean/` 模块（§16.17）。

| 原语 | Windows（`winfs.py`） | Linux | macOS（没验证） |
|---|---|---|---|
| 打开文件夹 | 不跟随重解析点，取 `FILE_ID_INFO` | `O_PATH`、`O_DIRECTORY`、`O_NOFOLLOW` | `O_RDONLY`、`O_DIRECTORY`、`O_NOFOLLOW` |
| 在文件夹里按名字打开 | `NtCreateFile`（RootDirectory = 文件夹句柄，原样的名字，名字长度按 UTF-16 单元算），`FILE_OPEN_REPARSE_POINT`、不召回；身份是卷序列号加 128 位文件 ID（和查找的原生读法一样），戳是 `FILE_BASIC_INFO` 的修改和更改时间加 USN | `openat`（`O_PATH` 或读数据时 `O_NOATIME`，不是主人时不带它） | `openat` |
| 建硬链接 | 保留点句柄上 `FileLinkInformation`（不覆盖，RootDirectory = D） | `linkat("/proc/self/fd/<K>", D, T, AT_SYMLINK_FOLLOW)`，没有 `/proc` 时相对 K 的文件夹 | `linkat` |
| 建符号链接 | `CreateSymbolicLinkW`（按路径；开发人员模式下带 `ALLOW_UNPRIVILEGED_CREATE`），建好后相对 D 打开核对：找不到说明文件夹被换了 → 要你看一下 | `symlinkat` | `symlinkat` |
| 交换 | 没有：两次不覆盖的改名 | `renameat2(RENAME_EXCHANGE)` | `renameatx_np(RENAME_SWAP)` |
| 不覆盖的改名 | 带 DELETE 的句柄上 `FileRenameInformation`，ReplaceIfExists = FALSE | `renameat2(RENAME_NOREPLACE)` | `renameatx_np(RENAME_EXCL)` |
| 删自己建的名字 | 刚核对过身份的句柄上 `FileDispositionInfoEx`（POSIX 语义，忽略只读属性）；WinBtrfs 不认忽略只读，先去掉只读、删除，再给还有别的名字的文件恢复只读；不支持时用经典的待删除 | `fstatat` 核对身份后 `unlinkat` | 同 Linux |
| 保持访问时间 | 数据句柄上 LastAccessTime = −1 | `O_NOATIME` | — |
| 沙箱 | 每个原语调用前核对涉及的每条路径 | 同 | 同 |

Windows 上从不用覆盖式改名。回收站步骤每批调现有的 `ops/trash.move_to_trash(paths, guards=…, roots=…, also_doomed=…)`：从不永久删除；没有回收站时不动它；Linux 用 `RENAME_NOREPLACE` 移进 freedesktop 回收站；守卫由这一步现建（这份和它这组要保持完好的保留点，删除篮和这次运行要删的东西作为 `Elsewhere`）。Windows 上没有 USN、要核对内容时，进回收站之前把这份和保留点再读一遍。卷上没有回收站时按 `dupes.cleanup.no_trash`：不覆盖地改名进恢复区，或者不动。

#### 16.9.4 块克隆（就地）

**Linux（btrfs、xfs 等）**：打开 K 只读；打开 C 先只读（内核允许文件主人或有写权限的人对只读描述符去重），被拒时改用读写打开（只打开，不写数据）。从头到尾每段 ≤ 16 MiB 调 `FIDEDUPERANGE`，每段拿一次许可；内核锁住两段、逐字节比较，相同才共享。返回 `FILE_DEDUPE_RANGE_DIFFERS` → `skipped_changed`（内容在核对之后变过；已经共享的段本来就相同）。做完用 FIEMAP 核对两份的块映射：完全相同 → `done`，否则 `done_partial`（写共享了多少）。没有原件，也不进回收站或恢复区。

**Windows（ReFS、WinBtrfs）——强制逐段比较**：

1. 打开 K 和 C，两个句柄都**只给别人共享读**（有人正以写方式开着就打不开 → 跳过），不跟随、不召回、保持访问时间；核对身份和戳。
2. C 只读、两份稀疏或加密不同、C 加密、完整性流设置不同 → 这一步做不了（只读、稀疏、加密在方案里就不给）。
3. 在 C 的句柄上关掉时间更新。
4. 按簇对齐分段，每段 ≤ 64 MiB：在这两个句柄上读 K 和 C 的这一段，逐字节比较，**不同就停**（`skipped_changed`）；相同就马上对这一段调 `FSCTL_DUPLICATE_EXTENTS_TO_FILE`。末尾不满一簇的部分**不克隆**（ReFS 上实测末簇不能共用，§16.20）。
5. 修改时间变了就改回原值。用 retrieval pointers 核对两份的簇号段：完全相同、而且整个文件都克隆了 → `done`，否则 `done_partial`。
6. `ERROR_BLOCK_TOO_MANY_REFERENCES` → `skipped_fs_limit`；别的错误停下这一步，内容不变。

这样是安全的：每一段在共享之前，都在两个别人写不进的句柄下逐字节比较过，比较和克隆之间只隔微秒。代价是要读两份（审阅页写出要读多少，风险 C04）。剩下的缺口见 §16.21。

#### 16.9.5 Windows 上没有链接能力的卷

卷不报告硬链接标志时硬链接不给；不报告重解析点时符号链接不给。Windows 的替换靠两次改名，不需要硬链接；删自己的临时对象在不支持 POSIX 删除的卷上用经典的待删除。

#### 16.9.6 恢复区（`recovery.py`）

被换成链接的份的原件、没有回收站的卷上「移到回收站」的那份，都放在这里，直到清除或撤销。恢复区必须和原件在同一个卷上（只改名，从不复制），每个卷按顺序试：

1. `data_dir()/dupes/cleanup/recovery/<运行号>/`，数据文件夹和原件在同一个卷时；
2. 设了沙箱时：这个卷上的沙箱根下的 `.SpaceKnife-recovery/<运行号>/`；
3. 卷的顶层：Windows 是卷根的 `.SpaceKnife-recovery\<运行号>\`（隐藏），POSIX 往上走到 `st_dev` 变化的地方（挂载点或 btrfs 子卷的根）建 `.SpaceKnife-recovery-<uid>/<运行号>/`（0700）；设置 `dupes.cleanup.recovery_at_root` 关掉或设了沙箱时跳过；
4. 原件自己的文件夹，隐藏的名字 `.~sk-<运行号后 6 位>-<序号>.orig`（风险 X02）。

- 里面的名字是 `<序号>-<原名>`，人看得懂，手动也能放回去；`README.txt` 写这是什么、怎么在 SpaceKnife 里撤销或清除、也可以手动改名放回；运行结束时写 `manifest.json`（序号 → 原路径、恢复区里的名字）。
- 恢复区在三处特殊处理：查找的 S0 不把它当候选（和回收站一样，`select.excluded_trees`）；删除篮里受保护（「SpaceKnife 的恢复区：在『重复文件清理记录』里还原或清除」）；树图里照实显示，它确实还占着空间。
- 审阅页只在真有原件要放进恢复区的卷上写恢复区的位置，算法和执行器相同。

#### 16.9.7 结果码与失败策略

| 结果 | 意思 | 会不会让整次停下 |
|---|---|---|
| `done` / `done_partial` | 做了并且核对过（块克隆只共用了一部分时是后者，写共用了多少） | — |
| `skipped_changed`、`skipped_keeper_changed`、`skipped_keeper_lost`、`skipped_keeper_busy`、`skipped_locked`、`skipped_denied`、`skipped_missing`、`skipped_protected`、`skipped_ambiguous_name`、`skipped_in_basket`、`skipped_parent_changed`、`skipped_name_taken`、`skipped_raced` | 文件、保留点或它们的文件夹和批准时不一样，或者碰不得 | 否 |
| `skipped_unavailable`、`skipped_no_right`、`skipped_link_limit`、`skipped_fs_limit`、`skipped_trash_full`、`skipped_error` | 到这里才发现这个处理做不了 | 否 |
| `failed_rolled_back` | 中途出错，已经恢复原样并核对过 | 按策略：「这一项回到原样，继续下一项」（默认，待确认）或「整次停下」 |
| `failed_attention` | 回滚证明不了原样 | **一定停** |
| `cancelled` | 没有开始（用户停了，或整次停了） | — |

不管选的是什么策略，下面这几种都会让整次停下：磁盘满、读写出错（`ENOSPC`、`EIO`）、日志写不进去、要你看一下、符号链接指到了别处（说明对那里路径的理解有误）、连着 10 步同一个失败码（「看起来是系统性的问题」）。跳过从不让整次停下。进程失去建符号链接的权限（`ERROR_PRIVILEGE_NOT_HELD`）时，这次剩下的符号链接步骤都记 `skipped_no_right`；某个卷上一种处理被证明做不了时，这个卷上后面的步骤记 `skipped_unavailable`。

#### 16.9.8 顺序

一个卷做完再做下一个；卷里按文件夹（同一个文件夹的步骤连着做），一组里先做替换和块克隆，再做回收站（中途失败时冗余不会先少掉），大的先做。保留点从不是任何一步的对象。

### 16.10 日志、中断收尾、撤销、清除、清理记录

#### 16.10.1 位置与格式（`journal.py`）

`data_dir()/dupes/cleanup/runs/<运行号>/`，运行号形如 `r-20261023-181502-7f3a`：

- `plan.json`：执行的那份冻结的步骤、确认、选项、沙箱，在第一步之前写好并落盘；
- `journal.jsonl`：只追加，一行一个 JSON 对象（`run`、`skip`、`intent`、`step`、`done`、`fail`、`undo`、`purged`、`resolved`、`end`），每行带 `"c"`：这一行去掉 `c` 之后的 BLAKE2b 前 8 字节（hex）。校验不过的行（写到一半崩溃）当它不存在；
- `report.json`：运行结束时写计数和每一步的结果；
- 路径只存在本地；后端日志里只写运行号和计数。

#### 16.10.2 持久性

一批的 `intent` 在这批第一步之前写入并落盘：这次运行可能建的每个名字（临时名、恢复区里的名字），在它出现之前就已经记在盘上。`step`、`done`、`fail` 边做边写，批末落盘一次。收尾从不只依赖 `step` 记录，它看文件系统上实际是什么。

#### 16.10.3 撤销（「撤销这次清理」，可以只撤销其中几项）

撤销是一个任务，倒着一步一步做，有自己的进度和结果，写进同一份日志：

| 原来的处理 | 撤销的做法 | 拦住的情况 |
|---|---|---|
| 回收站 | `trash.restore`：从不覆盖，原路径被占了就报「原来的位置已经有东西，没有覆盖」 | — |
| 回收站（没有回收站的卷，在恢复区里） | 不覆盖地改名放回 | 原处有东西时不覆盖 |
| 硬链接、符号链接 | 核对 p 上还是我们放的东西（硬链接：身份是 K，K 的大小和修改时间和运行结束时一样；符号链接：是链接、文字没变）；核对恢复区里的是 C；POSIX：把 C 不覆盖地改名到临时名、和 p 交换、核对、删掉换下来的替身；Windows：按句柄把替身改名走，再按句柄把 C 改回 p，后一步失败就把替身改回去，最后删掉替身 | p 在清理之后被改过：「这一项清理之后被改过，撤销会丢掉这些改动，没有撤销」；这时可以选「把原件还原到旁边」：不覆盖地改名成 `<主名> (原件)<扩展名>` |
| 块克隆 | 不需要：「共用数据块（没有可撤销的：内容、名字和属性都没变）」 | — |

清除之后，那几步显示「已清除」，不能撤销；回收站里的那几步还能还原。撤销回来的文件更改时间变了，下次查找会重读一次。空了的恢复区文件夹删掉。

#### 16.10.4 中断收尾（后端启动时，接受任何会话之前）

没有 `end` 记录的运行算中断了。对每个有 `intent` 而没有结果的步骤，相对记下的文件夹、用不跟随的打开看实际的身份：

| 处理 | 盘上的状态 | 做法 |
|---|---|---|
| 替换 | p 是 C，没有 T、没有 R | 没开始 → `cancelled` |
| 替换 | p 是 C，T 是我们的替身 | 删掉 T → `failed_rolled_back` |
| 替换 | p 是 C，T 上是认不出的东西 | 不删；POSIX 上不覆盖地移进恢复区的 `quarantine` 文件夹 → `failed_attention` |
| 替换（POSIX） | p 是替身，T 是 C | 交换做完了、原件还没移走：把 T 移进 R → `done` |
| 替换 | p 是替身，R 是 C | 做完了只是没记 → `done` |
| 替换（Windows） | p 不在，R 是 C | 两次改名之间中断了：按句柄把 C 改回 p，删掉我们的 T → `failed_rolled_back` |
| 替换 | 别的任何组合 | 不动；C 在 T 或 R 上就留在那里（它是安全的），写出每个名字上现在是什么 → `failed_attention` |
| 块克隆 | C 的身份和大小没变 | 按块映射记 `done` 或 `done_partial`（内容从没变过）；身份或大小变了 → `failed_attention` |
| 回收站 | p 还是 C | `cancelled` |
| 回收站 | p 不在了 | 在回收站里按原路径和文件身份找回：Windows 找原路径是它的 `$I` 记录、核对对应 `$R` 的身份，freedesktop 找 `Path` 指向它的 `.trashinfo`、核对身份（免得认成同名的旧项）；没有回收站的卷看恢复区 → `done`；都找不到 → `failed_attention` |

- 收尾是幂等的：收尾时又崩了，下次再收一遍，结果相同（实机验证里每个注入点收尾两遍）。
- 收尾的结果写进同一份日志，补上 `end`（`recovered`），并推给第一个声明了 `dupes.cleanup.v1` 的会话：「上次的清理在第 {seq} 项时中断了（SpaceKnife 退出或系统重启）。已核对：{n} 项恢复原样，{m} 项已完成，{k} 项要你看一下」。
- 有「要你看一下」的项没处理完时，拒绝新的运行。清理记录里每个这样的项给两个按钮：「把原件放回原处」（原处空着时，一次核对过身份的不覆盖改名）和「保留现状」。两个按钮都只是改名或什么都不做，从不删东西。

#### 16.10.5 清除（「清除恢复区」，唯一不可逆的一步）

先给「清除的预检」（哪些能清、哪些不能、为什么），确认框写「永久删除恢复区里的 {n} 份原件（{size}）？删除之前会核对每一份原件没有变过、保留的那份还在而且没有变；对不上的不删。这一步不能撤销」；确认后倒数 5 秒，可以取消。然后对每份原件：

1. 原件还是记下的那个文件：身份、大小、修改时间、更改时间等于移进恢复区时记下的戳。变了就不清除：「原件在清理之后变过：没有清除」。换上替身时恰好有别的程序写进了原件，那几笔会在这里被发现（I14）。
2. 内容此刻还在别处：目标保留点（硬链接时就是 p 上的那个文件）的身份、大小、修改时间等于运行结束时的值；核对方式「自动」时，Windows 上没有 USN 就把原件和保留点都重读一遍、要等于组的摘要（重读按保留点**现在**的更改时间：这次运行后面的步骤可能又给它建了链接）；「全部重读」时总是重读。哪一条不成立都不清除：「保留的那份改过了或不在了：恢复区里的这份可能是唯一的一份，没有清除」。
3. 有没比较过的附加数据（备用流、扩展属性）的原件，要在确认框里单独勾选。
4. 删除：相对恢复区文件夹按名字打开，核对身份，在句柄上删除；记 `purged`。空了的恢复区文件夹删掉。

回收站里的份不归清除管（「回收站里的 {n} 份要清空回收站才腾出（SpaceKnife 不替你清空回收站）」）。被拒绝的原件留在恢复区，没有「仍然清除」。**从不自动清除**；恢复区里的原件放了 `dupes.cleanup.purge_reminder_days`（默认 7 天）以上时，清理记录提醒一次。

#### 16.10.6 清理记录

`dupes.cleanup_runs` 列出每次运行，新的在前：时间（按本机时区）、各种处理多少份、状态（完成、部分完成、停下了、出错停下、已撤销、中断后已收尾）、恢复区还占多少、能不能撤销和清除。打开一次运行看逐项结果，能按结果筛选；撤销、清除的进度和结果写在记录上方。恢复区里还有原件的运行一直保留；其余的运行超过 90 天、而且不在最近 50 次里时才删掉记录（只删记录，不动文件）。命令面板的「重复文件清理记录」在没有查找结果时也能打开它。

### 16.11 和结果、缓存、监控、删除篮、扫描树的关系

#### 16.11.1 结果

执行器每做完一批，就在 `Results.lock` 下直接改成员表（`Results.apply_cleanup`），不等监控：

| 处理 | 成员行的变化 | 组的变化 |
|---|---|---|
| 回收站、符号链接 | 标 `F_CLEANED`，不再计入单位、账本、帧列 | 只剩一份时不再算重复 |
| 硬链接 | 文件 ID 和所属单位改成保留点的，角色「同一个文件」，戳用执行器核对过的新值 | 可腾出变少；悬停卡写「同一个文件」 |
| 块克隆 | 角色「同一份数据」 | 每份都共享时整组变成「同一份数据」 |

- 保留点的更改时间、USN 改成执行器取到的新值，以后的核对不会把我们自己的改动当成别人的。只改结果，不改缓存。
- **预期的变化**：每批做完后，把这批改到的路径（副本和目标保留点）登记 30 秒；这期间监控报来的这些路径的变化不让组退回「待核对」。别的路径的变化照常让组失效。设计要求的「再查一次元数据、和预期一致才认」没有做（§16.17）。
- 运行结束后方案按新的结果重建（批准随之作废，什么都不会执行两次）；没有监控的扫描，重读改过的父文件夹，树跟着变。

#### 16.11.2 缓存

清理不写、也不改哈希缓存。下一次查找时：硬链接的几个名字在 S1 合成一个物理文件，不读；块克隆在 S1b 认出块映射相同，是「同一份数据」，不读（Linux 上；ReFS 末簇不共用、WinBtrfs 的映射不可信，这两处的克隆会被重读一次，§16.20）；符号链接不是普通文件，不是候选；恢复区不是候选。保留点的更改时间因为多了一个名字变了，它的缓存条目对不上，只有它在组里还有别的伙伴时才重读一次。实机验证里，运行前后缓存文件逐字节不变，第二次查找读 0 字节（§16.19）。

#### 16.11.3 扫描树和配色

换成硬链接的那份在树里还是文件；换成符号链接的变成链接；恢复区照实显示；「重复」配色里已清理的组不再画多余。设计里在图上叠加方案的帧列 `dupa` 没有做。

#### 16.11.4 删除篮（两个方向）

- **删除篮不再收重复文件**（§8.5）。
- **删除篮 → 方案**：预检把删除篮里的一切都当成要删的（`OpsService.basket_elsewhere()`）。保留点被删除篮里的条目盖住（它自己，或它上面的文件夹，按路径也按身份），这组跳过（`skipped_keeper_lost`）；副本被盖住，这一份跳过（`skipped_in_basket`）。方案在建的时候就把这些标成不可用（`in_basket`：「它或保留那份在删除篮里：先从删除篮里拿掉」）。
- **方案 → 删除篮**：服务端从各次运行的日志里汇总出「SpaceKnife 建的符号链接指向哪些文件」。往删除篮里加的东西是其中某些链接的目标（或它们上面的文件夹）时，条目状态是 `link_target`，写「SpaceKnife 建的符号链接指向它：删了它，这些链接都打不开」；执行时要先勾「我知道 SpaceKnife 建的符号链接指向其中 {n} 项：删了它们，这些链接都会失效」（`BasketExecuteParams.ack_link_targets`）。以后的方案里，要把这样的文件移到回收站算高风险 R12，「推荐」预设不动它。
- **同一时间只做一件**（I8）。

#### 16.11.5 关掉扫描、换了作业

关掉扫描、扫描被淘汰：作业和方案草稿丢掉，运行不丢；正在跑的运行接着跑完（每一步都带着路径和身份，不需要扫描树），结果进清理记录。同一批扫描的新查找：手动选择接着用（按摘要），批准作废。

#### 16.11.6 检测不变

引擎、读法、缓存格式、零误报的判定（§3）、帧列 `dup` / `dupg` 都不变。清理只读已核对的组；方案只在用户打开时建；风险核查只取元数据，走调速器。查找路径上只多两处：S0 排除恢复区，成员表多一个 `F_CLEANED` 位（只在清理之后出现）。查找本身因为实机验证改了两处，影响的是「同一份数据」的认定（`share.rs` 不完整的块映射）和 btrfs 嵌套子卷认文件系统（`scan/volume.py`），见 §15 末尾和 §16.20。

### 16.12 协议（能力 `dupes.cleanup.v1`，要求同时声明 `dupes.v1`）

方法（模型在 `spaceknife_protocol/dupes_cleanup.py`，列表见 [protocol.md](protocol.md) §3）：

- 方案：`dupes.cleanup_open`（建立或接上一个已完成查找的方案，开始风险核查；可带预设）、`_resume`（采用或放弃存档的编辑）、`_state`、`_close`（离开，编辑存盘）；
- 编辑：`_preview`（不提交）、`_edit`（带 `base_version`）、`_undo_edit`、`_redo_edit`、`_import`；
- 读：`_groups`（组表的一页，≤ 500）、`_group`（一组的全部份：事实、可用性和原因、风险和证据、理由链）、`_facets`、`_pairs`、`_volumes`、`_summary`、`_risk_copies`（一类高风险的份，确认前要能看到）、`_sample`（抽查用的组号）、`_who_uses`（按需查占用）、`_export`；
- 执行：`_approve`（冻结，得到令牌、步骤数）、`_preflight`（只预检）、`_execute`（令牌、失败策略、核对方式、`proceed_after_drops`）、`_pause`、`_resume_run`、`_cancel`；
- 记录：`_runs`、`_run`、`_undo_plan`、`_undo`、`_purge_plan`、`_purge`（`delay_s = 5`）、`_resolve`（`put_back` / `keep_as_is`）、`_recover_report`。

事件：`dupes.cleanup_changed`（`{plan_id, version, reason}`：edit、facts、results、approved、basket、closed、run）、`dupes.cleanup_progress`（任务的进度，最多每秒 4 次，结束时一次）、`dupes.cleanup_interrupted`（启动时收尾的结果，推给第一个会话）。

去掉的：`dupes.to_basket`、`dupes.basket_members` 和它们的模型；`BasketItemKind` 的 `"dupes"`；`BasketItemStatus` 用 `"link_target"` 换掉 `"blocked"`。没有任何方法能不经方案把查找结果变成删除。

### 16.13 界面

#### 16.13.1 入口

- **重复文件抽屉**底部的「清理方案…」（带可腾出），上面一行写「逐组选保留哪几份、其余的怎么处理（回收站、硬链接、符号链接、块克隆），看过风险、确认之后才会改动文件」。查找没完成、没有可以清理的组、后端不支持清理方案时灰着并写原因。
- **命令面板**：「重复文件清理方案…」（别名 cleanup、dedupe plan、hard link；要有结果）、「重复文件清理记录」（有过运行时）。
- 快照页签里照旧不能用。
- **命令面板、右键菜单、按键、工具栏，都没有能执行方案的入口。** 设计里右键菜单、悬停卡、详情面板上的方案入口还没做（§16.17）。

#### 16.13.2 清理模式

按「清理方案…」后，当前标签进入清理模式（和快照对比一样是标签的一种模式），视图切到「重复」配色。顶栏写版本、状态、风险核查进度、马上和清空或清除之后腾出、各级风险的份数；工具栏有预设、页（组、文件夹对、卷、审阅并执行、执行、清理记录）、筛选、撤回和重做、「退出清理模式」。组页是三栏：规则 | 组表 | 检查器和图。窗口窄于 1280 px 时规则收成抽屉、检查器和图叠成页签；窄于 900 px 时只留组表，检查器从下方弹出。

#### 16.13.3 组表

- 组行：勾选框、名字、份数、单份大小、腾出、处理摘要、最高风险的标记和个数、来源、过目。一页 200 组，「再显示一些」往下取；没有虚拟滚动和分组显示（§16.17）。
- 展开后每份一行：前面标 1–9 的序号（和数字键对应）；保留开关（最后一个保留点灰掉，写「唯一的保留点」）；处理（按钮加列表：做不到的留在列表里灰着，原因写在下面；可以用键盘 ↑↓ Home End 回车 Esc 操作）；链接或块克隆的目标（只写保留那份的名字）；路径（按组里各份不同的那一段缩写）；风险标签（最多两个，其余计数）；来源（短语，整句在提示里）。
- 失效的组灰着，写「核对之后文件变了，要再查一次」，不能编辑，不执行。空表写为什么空、怎么回到查找结果；已清理和失效的组在表下计数。

#### 16.13.4 规则栏

按 §16.4.1 的层排：锁定（说明）、保留规则（基本判据链、每卷一份、文件夹一致、规则卡片）、处理规则、文件夹对和手动的计数。每张卡片写命中多少份、多少字节，可以开关（直接生效，回执写明，能撤回）、上移、删除（先预览）；能加（先预览）保留规则（优先保留在这些文件夹、尽量不留在这些文件夹、这里的全部保留、每个文件夹各留一份、至少留 2 份）和处理规则（文件夹、事实标签、名字的通配，处理，后备）。卡片的拖动排序和编辑表单还没做。

#### 16.13.5 文件夹对和卷

文件夹对页：每行从两边分开的那一段路径写起，组数、字节、两边各自的覆盖率、当前的决定，「保留这边」「两边都留」，先预览。卷页（跨盘时）：卷 × 卷。

#### 16.13.6 键盘（组表有焦点时）

| 键 | 作用 |
|---|---|
| ↑ ↓ / j k | 上下一组 |
| → ← | 展开、收起 |
| 1–9 / Shift+1–9 | 这组只保留第 n 份 / 第 n 份也设为保留点 |
| t h s c l | 这组不保留的份：回收站 / 硬链接 / 符号链接 / 块克隆 / 不动（做不到的保持原样，回执写明） |
| x | 这一组不动（排除） |
| r | 标为已过目，跳到下一组没过目的 |
| Space / Ctrl+A / `/` | 勾选这一组 / 勾选显示出来的全部组 / 到筛选框 |
| Ctrl+Z / Ctrl+Shift+Z | 撤回 / 重做 |
| Enter / ? | 到检查器 / 按键一览 |

每次编辑都有回执，能撤回。**执行、撤销、清除都没有按键。**

#### 16.13.7 检查器

#### 16.13.9 预检、执行、结果、撤销、清除

- 「执行…」打开确认框：每种处理多少份、每个卷腾出多少，按这次实际有的处理说明（只有回收站时不提恢复区）；焦点默认在「取消」上。
- 预检有跳过的项时只问一次（§16.8），执行页写「等你确认」；「执行其余的」等上一次运行结束、重读方案后再执行。
- 执行页：阶段、计数（完成、跳过、出错、回到原样、要你看一下）、当前项、「暂停」「做完当前这一项就停」；结束和暂停时列出逐项结果。
- 结果之后：「撤销这次清理」「清除恢复区…」「导出清理报告」。撤销的确认框写要换回多少、从回收站还原多少，清理之后改过的不换回（可以还原到旁边）；清除的确认框和 5 秒倒数见 §16.10.5。

#### 16.13.10 防误操作的规则

1. 没有一次点击就能执行的控件：只在审阅页、批准之后、经过确认框（焦点默认「取消」）才执行；执行、撤销、清除都没有快捷键。
2. 默认是稳妥的处理：「推荐」里没有链接；换成链接是一次批量改，先看预览，相应的高风险变成待确认。
3. 每个决定都看得见：每份的理由链、每组的抬头、不在方案里的组和原因；导出列出每一步。
4. 批量改一律先预览；「清除手动选择」写明要清多少处。
5. 最后一个保留点不能取消（开关灰掉，后端也拒绝）。
6. 不看到具体的份就确认不了高风险。
7. 清除之前一直能撤销；清除单独做、要等 5 秒、删前再核对，从不自动。
8. 做不到的处理写明原因；执行时从不悄悄换成别的处理，做不了的那一步算跳过，原因写进结果。
9. 颜色从不是唯一的信号：等级有标记和字，处理有文字。两个主题下量过的文字对比度都 ≥ 4.5。

### 16.15 性能与内存

- 方案只在用户打开时建，没有方案时零开销。方案按成员行建数组：决定、来源、目标、每种处理的可用性和目标、等级、差别、标签等约 0.2 KB / 份，加上成员表的一份拷贝（64 B）和名字字符串；没有实测（§16.17）。
- 保留、处理、风险都是对数组的计算，在计算线程里做；编辑只重算动到的组；风险核查每份一次只取元数据的查看，每批 256 份走许可。
- 执行：替换每步约 10 个元数据调用加 2 次改名；就地块克隆按字节，Windows 要读两遍再克隆，Linux 由内核比较；都按负载档拿许可。

### 16.17 和设计的差别、还没做的

**做法不同的**：

- 文件原语用 Python（`os` 的 `dir_fd` 系列、ctypes 调 `NtCreateFile` 等），不是原生模块；原生只改了 `share.rs`（块映射的完整性）。Windows 上的替换和块克隆要求查找用的是原生读法（身份一致），否则不给。
- 日志每行的校验和令牌用 BLAKE2b（设计写的是 BLAKE3）。
- 预期的变化只是把路径登记 30 秒，期间这些路径的变化一律不让组失效，没有再查一次元数据确认（§16.11.1）。
- 预检没有重新做风险核查（设计的 `skipped_risk_rose` 不会出现），也不按回收站的容量预先跳过（回收站放不下时由 `move_to_trash` 报，记 `skipped_trash_full`）。
- 监控让方案版本变了以后，界面在用户确认执行时自动重新批准当前版本；设计要求这种情况下后端保留批准、只在预检跳过（待评审）。
- 预检拦下、什么都没做的那次在清理记录里留一条「停下了 · 没有改动任何文件」，没有并进「执行其余的」那次（待评审）。
- 沙箱以外的步骤逐项记「没有权限」，其余照常；设计写的是整次拒绝（待评审）。
- 后端进程退出时不等当前这一批做完，靠下次启动收尾。

**还没做的**：

- 块克隆的「克隆加交换」（Linux `FICLONE`、macOS `clonefileat`），所以 C06–C08 三条风险没有；bcachefs、ocfs2 的就地去重没有真机验证。
- 风险证据：SMB 共享（H12、S09）和 Windows 重复数据删除（H13）的标签没接上，这三条现在不会出现；「谁在用」（R09）不是风险，只在预检查占用；相对链接经过链接的文件夹（S11）不算风险，「自动」时直接改用绝对路径；卷上的快照没有查（C02 只看组里已有的共享字节和 btrfs）。
- 界面：规则卡片的拖动排序和编辑表单；组表的虚拟滚动、按文件夹对 / 卷 / 扩展名分组显示；分面计数（后端 `dupes.cleanup_facets` 有）；抽查的大检查器（现在「抽查」只跳到第一组）；右键菜单、悬停卡、详情面板里的方案入口；图上的方案叠加（帧列 `dupa`）；导入 JSON；删除篮抽屉里「恢复区里有 {size}」的提示行；「谁在用」按需查。
- 撤销以后的结果不反向更新（被撤销的组要再查一次才回到方案里，界面这样写明）。
- 方案的内存没实测。
- 删除篮旧测试里的几个场景还没改成清理的测试：两次查找互为保留方、同一文件夹经两条路径查两次、跨盘经两条路径看到的同一个文件只处理一次。

### 16.19 实机验证（2026-10-24，只用合成数据）

**规矩**：只在自己建的测试文件夹里执行：Windows 测试目录（NTFS）、W:（ReFS）、H:（WinBtrfs）上各一个新建的文件夹，WSL 的 ext4，以及自己建、自己挂的回环镜像（btrfs 1 GB、xfs reflink=1 1 GB、xfs reflink=0 320 MB；写满用的 ext4 64 MB、btrfs 160 MB）；数据全部由固定种子的脚本生成，每个位置约 350 MB；每次执行都设沙箱。开始前先做越界尝试：硬链接、符号链接、块克隆、回收站、保留点在沙箱外，五种全部被拒，清单一项没变。用完删掉测试文件夹，卸载并删除镜像。没有卸载或锁定任何用户的卷。

**核对**：一套和 SpaceKnife 不共用代码的脚本记下清单（路径、大小、SHA-256、128 位文件 ID、链接数、属性、备用流、FIEMAP 或 retrieval pointers 的块位置），每一步之后都和它比：

- 执行后：每组的内容都能从没变的保留点拿到；原件在恢复区，身份和 SHA-256 不变；回收站里的数据对得上；没动的文件逐项不变；没有遗留的临时名；
- 撤销后：和执行前逐项一致，包括文件 ID；
- 清除：只删记下的原件，该拒的都拒了（有备用流的原件没确认不删，保留点被删后不删）；
- 其他：恢复区的 README 和 manifest 对得上；日志每行校验都通过；保留点的访问时间不变；运行前后哈希缓存逐字节不变；运行后第二次查找读 0 字节。

**结果**（最终代码）：

- Windows：NTFS 12 个场景、ReFS 12 个、WinBtrfs 11 个；之后用最终代码重跑 NTFS 和 ReFS 的「改过」「主流程」、WinBtrfs 的「改过」，另加一次访问时间的分阶段测量。共 41 次，约 4.7 万条核对，**1 条没过**：WinBtrfs 上以点开头、设了隐藏属性的文件放进回收站约 30 秒后丢了隐藏属性，撤销后回不来。不经 SpaceKnife、只做一次普通改名也能复现，是 WinBtrfs 自己的行为（§16.20）。
- Linux：ext4 10 个场景、btrfs 7 个、xfs 4 个、xfs（reflink=0）2 个、写满的 ext4 和 btrfs 小镜像各 1 个，共 25 次，约 61 万条核对，全部通过。

| WinBtrfs | 四种处理都通过；块克隆只能报 `done_partial`（它的块映射不全） | 同 ReFS；没有 USN 时两种时间都改回去的改动被重读发现 |
| ext4 | 硬链接、符号链接、回收站都通过；块克隆不给 | `protected_hardlinks`、只读文件夹在方案里就不给；19 个注入点崩溃都通过；跨卷 ext4 + btrfs；交换前别人用改名存了新文件 → 换回原样，`skipped_raced` |
| btrfs、xfs | `FIDEDUPERANGE` 就地去重全部 `done`，包括不满一块的尾巴 | 写入竞争：内核比较后拒绝，写入的数据还在；子卷之间硬链接写「另一个子卷」、块克隆可以；关掉写时复制的不给块克隆；xfs reflink=0 在方案里就不给块克隆；21 个注入点崩溃都通过 |
| 写满的小镜像 | — | 这一项回滚，整次停下，什么都没丢 |

**没测到的**：Windows 上磁盘满（没有能写满的小卷，建、挂 VHD 会改系统）；ACL 不同（`icacls`）的风险提示；`ERROR_BLOCK_TOO_MANY_REFERENCES`（照写，没量）；btrfs 快照占着数据块时腾出的空间偏少；macOS 全部。

**实测发现并修好的**（都在这次验证里发现，补了测试）：同一个保留点上后面的步骤都被判成「保留的那份变了」（NTFS 关句柄时的 USN）；名字里有表情符号等 BMP 以外字符的副本都报「不在了」（名字长度按 UTF-16 单元算）；只读的原件清除不掉、连到只读保留点的链接撤销时删不掉；沙箱外的回收站步骤让整次运行抛异常中断；放进回收站后、日志记下前崩溃，收尾找不到；ReFS 上还没分配数据块的新文件被当成「同一份数据」而不读内容；Windows 块克隆逐段比较发现不同时写成「完成，部分数据块已共用」；没有 USN 的卷上两种时间都改回去的改动照样被处理；清除时重读用了旧的保留点更改时间而误拒；嵌套的 btrfs 子卷认不出文件系统；xfs reflink=0 在方案里也给块克隆。界面截图评审时另修了：一批回收站步骤之间夹着别的处理时，夹着的那步被跳过、后面一步做两次；给同一个保留点建第二个硬链接被误判为「保留的那份变了」；「只留它」之后「也保留这一份」被忽略。

### 16.20 实测确定的系统行为

- **ReFS（W:，3.14）**：克隆长度在文件末尾向上取整到簇，系统接受，但末簇实际上不共用。所以末簇不克隆，大小不是簇整数倍的文件克隆后是 `done_partial`，下一次查找也不会认成「同一份数据」，会再出现在「可腾出」里（是否把「整簇都共用了」算作完成，待评审）。报告支持硬链接。刚写入的数据要过一阵才分配（retrieval pointers 全是 LCN −1）：这样的块映射现在不算完整。
- **WinBtrfs（H:）**：文件系统名报成 NTFS（SpaceKnife 认出是 btrfs）；没有 USN；备用流放在扩展属性里，100 KiB 的写不进去；写备用流后约 3 秒修改时间会自己变（在这之前做的方案会在预检时被跳过，这是安全的）；只读文件用任何删除标志都删不掉（所以先去掉只读再删）；`FSCTL_GET_RETRIEVAL_POINTERS` 不到文件末尾就返回「完成」，中间还夹着零长度的 LCN −1 段，所以多段文件的块克隆只能报 `done_partial`，查找也不会认成「同一份数据」（克隆本身成功，内容核对过）；以点开头、设了隐藏属性的文件改名成不以点开头（比如进回收站）约 30 秒后会丢掉隐藏属性。
- **NTFS**：关掉建链接用的句柄时会再记一条 USN。大规模运行时偶尔有 1–2 个保留点的访问时间变了，每次是不同的文件；单独分阶段测量时预检和执行都不改访问时间，推测是系统的扫描程序读了新名字，没有确认。
- **btrfs、xfs**：`FIDEDUPERANGE` 连不满一块的尾巴也共享；内容不同时内核返回 `FILE_DEDUPE_RANGE_DIFFERS`。嵌套子卷的设备号在子卷处变化，那里不是挂载点：算作上面挂载的 btrfs。

### 16.21 残余风险与没在真机验证的

- **Windows 的回收站按路径工作**：从守卫到壳移走之间，恶意的本地进程可以换掉名字（删除篮原有的残余风险）。
- **Windows 的就地克隆**：别的程序在我们打开之前就建好、句柄关了但视图还映射着的可写映射，写入恰好落在某一段的比较和克隆之间那几微秒里，共享方式管不住；克隆后核对块映射证明不了那几笔写入有没有被盖掉，就地克隆也没有原件可留。
- **Windows 的两次改名**：原路径有几微秒不存在（X01）。
- **Windows 的符号链接按路径建**：建之前文件夹被换掉时链接会建到别处；建好后相对文件夹句柄核对，能发现，交给用户。
- **POSIX 不能拒绝别人写**：核对和交换之间有程序写进了副本，写入落在原件上，原件留在恢复区；清除时戳对不上就不删。
- **清理之后**：就地写的程序会通过硬链接改到两处（风险 H01 写明）；按「写新文件再改名」保存的程序会悄悄断开硬链接（不丢数据）。
- **认不出的同步工具**：只能给一般说明。
- **预期变化的 30 秒**：这期间别人改了刚处理过的路径，组不会退回「待核对」（下一次运行的核对仍按戳）。
- **macOS 全部没验证**：`renameatx_np`、ACL 和扩展属性、废纸篓的还原、APFS 克隆识别（没做），所以 `dupes.cleanup.macos_links` 默认关。bcachefs、ocfs2 的就地去重也没在真机上试过。
