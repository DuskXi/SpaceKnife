# 重复文件检测 —— 设计与接口约定

找出内容完全相同的文件，按能腾出的空间排序，用户选好保留哪一份后放进删除篮。**只读**：作业本身从不改、移、删用户的文件；删除只经删除篮，由用户确认，执行前再核对一遍（§8.5）。

代码：引擎 `packages/backend/src/spaceknife/dupes/`，服务 `server/dupes.py`、`server/dupes_handlers.py`，协议 `spaceknife_protocol/dupes.py`（能力 `dupes.v1`），原生读取 `packages/native/src/dupes/`（feature `dupes`，默认开），前端 `apps/electron/src/renderer/src/state/dupes.ts`、`shell/DupesDrawer.tsx`，测量工具 `spaceknife dupes`（`cli_dupes.py`）。

## 1. 总体

入口在 §10.1。查找从不自动开跑；它只读和别的文件大小相同的文件，先读头尾几 KB，只有几份还一样时才读完整个文件；只有读完全文、内容一致的才叫「内容相同」。硬链接、块克隆、同一个文件经两条路径看到的，都是「同一份数据」，删了不腾空间，从不给删。云占位文件不读（读它会触发下载）。

## 2. 流水线

```
store ─S0 选候选（不读盘）─▶ 大小组 ─S1 身份（只读元数据）─▶ 物理文件 ─S1b 块映射（只在可克隆的卷）─▶ 不同的数据
         已核对 ◀─S3 全文 BLAKE3-256（组内同步、分段比对、一不同就停）◀─S2 头尾（每个文件一次数据打开）
           └─▶ S4 账本 · 保留规则 · 文件夹汇总 · 覆盖（不读盘）──▶ 删除篮（dupes 条目 + 守卫）
```

只有 S2、S3 读内容；每一步只处理前一步解决不了的。组按「可能腾出的空间」（(份数 − 1) × 大小）从大到小、一波一波地做，结果随时流出。

### 2.1 S0 选候选（不读盘）

合格的文件：普通文件、≥ 下限（默认 1 MiB，`dupes.min_size`），不是云占位、离线、出错、已不在、待扫、MFT 伪目录里的；排除受保护的系统和程序文件夹、回收站、网络盘、FUSE（设置可以打开）。按大小稳定排序，去掉大小独一无二的（不读盘就知道它们没有伙伴）。模式：`all`（整个范围）、`inside`（只看某个文件夹里的组）、`against`（组里至少一份在某个文件夹里，伙伴在整个范围里找）、`file`（只看某个文件的大小组）。路径按父文件夹缓存拼，不逐个调 `store.path()`；在锁下做，不分配与 store 等长的数组。`dupes.plan` 只做这一步。本机 C:（865 万行）分组 26 ms、排除树上溯 4.8 ms、拼全部候选的路径 48 ms（Understand 阶段实测）。

### 2.2 S1 身份（只读元数据）

每个候选一次只读元数据的查询（Rust 里批量做，每批 ≤256 个名字或约 30 ms，释放 GIL）：卷、128 位文件 ID、链接数、纳秒时间、属性、重解析标记，Windows 有 USN 日志时取 USN。身份相同的几个名字合并成一个物理文件；剔除云占位、名字被换成链接的、只差大小写的、名字不能用的；按新鲜大小重新分组（目录项里的大小可能过期：大小变了只会漏掉重复，不会误报）；查缓存（§7）：一组里所有物理成员都有可用于认定相同的全文摘要时，整组不读盘。只取属性的打开 + FileIdInfo 约 14 µs（暖缓存）。

### 2.3 S1b 块映射（只在可克隆的卷，只读元数据）

ReFS 等带 `FILE_SUPPORTS_BLOCK_REFCOUNTING` 的卷，Linux 的 btrfs、xfs、bcachefs、ocfs2：块映射从头到尾完全相同的两份判为「同一份数据」（块克隆、reflink），可腾出记 0，不读内容，永远不给删——这是关于存储的判断，不是关于内容的。部分共享的照常读，共享字节记进账本；查不到映射的当「不知道」，照常读，账本加注「可能共享数据块，实际腾出的可能更少」。估计 20–40 µs/个。

### 2.4 S2 头尾（每个文件一次数据打开）

在句柄上读第一个字节前，核对属性和标记、身份等于 S1、大小等于组的大小，取打开时的戳。读头 [0, 4 KiB)、尾（4 KiB 对齐），≥64 MiB 的再读 1/3、2/3 处各 4 KiB，不经缓存。快速摘要 = BLAKE3(大小 ‖ 参数号 ‖ 各块) 的前 64 位，只用来拆组：碰撞的后果只是多读。读完在同一句柄上再取戳，变了就记 `changed`。每个文件 8 KiB（大文件 16 KiB）；冷打开约 5 ms（有卡巴斯基时）。

### 2.5 S3 全文（BLAKE3-256，分段，组内同步，一不同就停）

在 1、4、16、64、256 MiB 及之后每 256 MiB 处用 `finalize(&self)` 取中间摘要比对，变成单个的成员立刻停、关句柄；读到的字节数正好等于大小、再读是 EOF、关闭前戳不变，摘要才有效。最终 32 B 摘要相同的成员组成已核对的组。BLAKE3 约 4.76 GiB/s/核。

### 2.6 S4 账本、保留规则、文件夹汇总（不读盘）

见 §8。

### 2.7 细节与读取量

- **句柄交接**：SSD 上，S2 后还要进 S3 的成员把句柄留着，S3 从头接着读，S2 读过的头块直接喂给哈希器（不重读、不再冷打开一次）。HDD、SD 卡上不交接。
- **在途请求不跨下一个检查点**，所以每个被拆出去的成员读了多少字节是确定的：读取量 = Σ 已核对且没靠缓存认定的成员的大小 + S2 的头尾块 − 交接省下的头块 + Σ 被拆出去的成员的检查点（测试 `test_dupes_engine.py` 按这个公式精确核对）。
- **大组**（>32 份）：一次最多 32 份同时打开，每份最多打开 3 次（S2 一次；1 MiB 检查点一轮；没被这一轮分开的再读到结尾一轮，块与块之间关掉句柄）。32 份以内的组靠句柄交接，每份只打开 1 次。把大组改成「每 32 份一块走完所有检查点」能省掉中间那一次，但一块里的成员在别的块读完之前谁也不能提前停（可能和别的块相同），省下的只是一次冷打开，留在第二期。
- **句柄租期** 2 s：之后关掉，续读前重新打开并核对身份和戳，从偏移继续（不重读）。Windows 上文件夹里有打开的子项时用户改不了文件夹的名字，所以不长时间占着。
- 每块物理盘一个队列，用它自己的线程（按介质：NVMe 8、SATA SSD 4、HDD 2），每批约 30 ms（HDD 100 ms）拿一次调速器许可；读和哈希都在 Rust 里，不持 GIL（§9）。

## 3. 零误报

### 3.1 判定

两份被报告为「内容相同」，当且仅当：

1. 身份不同（本次运行内的 (卷, 128 位文件 ID) 不同；相同就是同一个文件）；
2. 不是块映射完全相同的「同一份数据」（那是另一档，从不给删）；
3. 大小相同，读到的字节数正好等于大小，之后是 EOF；
4. 全文 BLAKE3-256 相同；
5. 每一份的摘要来自一次一致的读取（同一句柄上读前读后的戳不变；租期重开时身份和戳也不变），或来自一条可以用来**认定相同**的缓存条目（§7.3）。

### 3.2 为什么用强哈希，不逐字节比较

- **偶然碰撞**：n 个文件时概率 ≤ n²/2²⁵⁷，10⁹ 个文件约 4×10⁻⁶⁰，比内存、总线、磁盘没被发现的错误低几十个数量级；逐字节比较同样暴露在这些错误下。
- **蓄意碰撞**：BLAKE3 有 128 位的抗碰撞强度，没有已知攻击。MD5、SHA-1 有同长度的碰撞实例，xxh3 之类不抗碰撞，所以非密码学哈希一律不用于判定（S2 的快速摘要只用来拆组：碰撞的后果只是多读）。
- **代价**：逐字节比较要把每一份再读一遍、几份同时打开（HDD 上来回寻道），结果还不能缓存，「第二次几乎不读盘」就做不到。
- 它也不解决真正的风险：核对之后文件又变了（§3.3）。

### 3.3 真正的风险怎么挡

- 读前读后在同一句柄上核对戳（大小、修改时间、更改时间）；长度正好、EOF。
- **刚改过的**（修改时间或更改时间在开始读之前 10 s 以内）：本次照常显示，缓存条目标 racy，以后永远不能用来认定相同。
- **缓存的不对称信任**（§7.3）：用来「分开」随便用，「认定相同」要全部戳对上；FAT、exFAT、网络盘上永远不能。
- **USN**（NTFS/ReFS，卷有日志时）：程序能把时间改回去，改不了 USN。存进缓存，认定相同和删除前都核对。
- **删除前核对**（§8.5）：被删的和保留的都重新取身份和戳。
- 不经缓存的读能看到还没写回的数据（NTFS 在非缓存读前冲掉缓存的范围，Linux `O_DIRECT` 先写回），摘要对应文件当前的逻辑内容。
- **「相同」的范围**：只比较默认数据流。备用数据流（ADS）、扩展属性、ACL、时间戳都不比；界面上一律写「内容相同」。

### 3.4 接受的残余风险

- 没有 USN 日志的 Windows 卷上，有程序改了内容、又用原生 API 把修改时间和更改时间都改回原值时，缓存可能把不同的文件认成相同。设置「执行前重读内容」（`dupes.recheck_content`）能堵上。
- 别的程序在核对之后、删除之前通过内存映射写入、而文件系统还没更新时间戳时，删除前的戳核对可能看不出来。占用检测（被删的那份正被打开就跳过）和 `keeper_busy`（保留的那份正被别的程序打开就跳过）挡住大多数情况。
- 第三方杀毒软件在打开时检查文件，可能改访问时间（本机的卡巴斯基就会）。SpaceKnife 挡不住，只能少打开，并在事后抽样数出来告诉用户（§5.6）。

## 4. 身份、硬链接、克隆、跨卷

### 4.1 卷键

本次运行内的身份是 (S1 的卷号, 128 位文件 ID)，精确比较：Windows 是 `FILE_ID_INFO` 的 64 位 VolumeSerialNumber，POSIX 是 `st_dev`（btrfs 的每个子卷各有各的）。缓存用的卷键要跨次稳定：Windows 64 位卷序列号 + 卷 GUID；Linux 文件系统 UUID（`FS_IOC_GETFSUUID`，6.5+）和 `f_fsid`（btrfs 上混进子卷）；macOS `f_fsid`（未验证）。卷键不稳只会让缓存认不出来，认定相同仍要所有戳对上。

### 4.2 各种情况

| 情况 | 怎么认出来 | 显示 | 可腾出 | 能不能删 |
|---|---|---|---|---|
| 同一个文件的几个硬链接名字 | S1：身份相同（Windows 硬扫描存的 `ino` 是 0，所以靠 S1） | 同一个文件 | 0 | 不删，只能当保留方 |
| 同一个文件经两条路径看到（重叠的扫描、SUBST、挂载点、bind mount） | S1：身份相同 | 同一个文件 | 0 | 不删 |
| 链接数大于扫描里看到的名字数 | S1 | 不选 | 0 | 不选 |
| 块克隆、reflink（完全共享） | S1b：块映射完全相同 | 同一份数据 | 0 | 不删 |
| 部分共享 | S1b：共享字节 | 普通组，账本里分开写 | 私有部分 | 能 |
| 不同的物理文件，内容相同 | S3 | 内容相同（已读完全文核对） | 多余各份的分配大小 | 能 |

- 只有「一个名字、链接数等于扫描里的名字数」的物理文件才能是多余的副本。名字以点或空格结尾、删除篮删不了的，只能当保留方。
- 两个不同的卷碰巧给出相同的卷号和文件 ID（克隆出来的盘）时，两个文件会被当成同一个文件：这只会藏掉一个重复，不会造出一个。

### 4.3 跨盘（选项，默认关）

- 抽屉里的「跨盘比较」（设置 `dupes.cross_volume`）：把所有打开的、已扫完的实时扫描放在一起比（最多 16 个）。同一卷经两条路径或两个扫描看到时只算一份。
- **物理事实**：硬链接不能跨卷（EXDEV），块克隆、reflink 不能跨文件系统，所以**跨卷的每一份都实占它自己卷上的空间**。btrfs 的子卷、挂载的快照是同一个文件系统，能共享盘区：S1b 按文件系统分组（文件系统 UUID，没有就按挂载的设备），不按 `st_dev`（每个子卷各有一个），FIEMAP 的地址在整个文件系统里可比。
- **保留**：默认每个卷至少留一份（`dupes.cross_keep_per_volume`）：每个卷上留一份，同卷的其余副本是多余的；可腾出按卷分开，进删除篮时每卷一个条目，删除前的守卫要求同卷的保留方完好。关掉它就是全部只留一份，别的卷上的备份也预选为多余。
- **重叠**：两个打开的扫描有重叠（C:\ 和 C:\Users\x\Downloads），或同一文件夹经两条路径，重叠部分的文件各有两条路径，但仍是一个名字：按 §8.1 的「视图」只算一份，真正的重复照样能删一次。
- 网络盘默认不参加：ID 不可靠，`\\localhost\c$` 可能就是 C:。

## 5. 读盘：只读、不改访问时间、不触发云下载

### 5.1 守卫的顺序（三个系统都一样）

store 的 flags（S0，不发系统调用）→ S1 的新鲜属性和标记 → 数据打开（带「不召回」）→ 在句柄上核对属性、标记、身份等于 S1、大小等于组的大小，取打开时的戳 → 保持访问时间 → 读 → 在句柄上再取戳 → 关闭 → 按抽样规则查一次访问时间。

### 5.2 Windows

- S1 在只取属性的句柄上做（`FILE_READ_ATTRIBUTES`、`FILE_OPEN_REPARSE_POINT`、`FILE_OPEN_NO_RECALL`）：不碰数据，不召回、不改访问时间、杀毒软件也不扫内容。
- 数据打开：`FILE_READ_DATA | FILE_WRITE_ATTRIBUTES`、`FILE_FLAG_OPEN_NO_RECALL`，打开后立即在句柄上把 LastAccessTime 设成 −1（和硬扫描共用 `src/winio.rs` 的 `keep_access_time`），不经缓存读（不冲掉用户的文件缓存）。压缩、加密、稀疏、WOF、重复数据删除的文件经它们的过滤驱动缓冲读。
- `FILE_WRITE_ATTRIBUTES` 被拒绝时：按 `dupes.keep_access_time`，默认 `skip` 不读并计数（「保留不了访问时间」）；`read` 则照读、计数 `atime_unkept`。
- 别的程序没给共享读：跳过，记「被独占」。
- 只差大小写的同名项：在属性句柄上取规范化路径比对；只差大小写时，对每一级大小写不同的名字问一次它所在的文件夹（`FindFirstFileExW`，名字当模式，每个文件夹和名字记 2 s）：有两项能对上，或有一项恰好是问的那个名字（区分大小写的文件系统），才说明打开的可能是另一项，跳过（`ambiguous_name`）。用户手输的 `c:\users\x\downloads`、扫描后只改了大小写的文件夹不再整个被判成「只差大小写」（评审在 Windows 上实测：之前这样的根下每个候选都被跳过）。
- 根下挂在文件夹里的别的卷（开了 `scan.cross_mounts`）：S1 的 64 位卷序列号的低 32 位和根卷的序列号不同时，按路径重新查卷，信任、能否共享数据块、是不是网络盘按那个卷的文件系统定；查不到就当弱信任（FAT、exFAT 永远不能凭缓存认定相同）。

### 5.3 Linux

- `open(O_RDONLY | O_NOATIME | O_NOFOLLOW | O_CLOEXEC)`，全文阶段 `O_DIRECT`（设备拒绝对齐时改缓冲读）。
- `O_NOATIME` 被拒（不是文件主人）：卷以 `noatime` 挂载就照读；否则按 `dupes.keep_access_time`，默认跳过并计数。
- FUSE 和网络挂载默认不参加（rclone 之类的云 FUSE 一读就下载）。不只是扫描根：开了 `scan.cross_mounts` 时，本地根下面挂着的 NFS、SMB、FUSE 在 S1 按文件所在的卷认出来（`st_dev` 和根不同时重新查卷），原因记 `network_mount`，一个字节也不读（测试 `test_a_network_mount_below_a_local_root_is_not_read`）。

### 5.4 macOS（照写照标，本机测不了）

- `open(O_RDONLY | O_NOFOLLOW | O_CLOEXEC)`，`F_NOCACHE`；读盘线程调 `setiopolicy_np(IOPOL_TYPE_VFS_ATIME_UPDATES, IOPOL_SCOPE_THREAD, IOPOL_ATIME_UPDATES_OFF)`，失败就按 `dupes.keep_access_time` 处理。
- 读盘线程打开数据前调 `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, IOPOL_SCOPE_THREAD, IOPOL_MATERIALIZE_DATALESS_FILES_OFF)`：文件在 S1 之后、读之前变成无数据的，读会失败而不是把它下载下来；设不上就不读（记 `cloud`）。`SF_DATALESS`（无数据的云文件）照样在 S1 剔除。
- APFS 的克隆识别（`getattrlist` 的 clone id）还没做：APFS 上 S1b 当「不知道」，照常读，账本加注「可能共享数据块」。
- 以上都没在真机上跑过；CI 的 macOS 机器跑单元测试。

### 5.5 云占位为什么跳过

- 读占位文件会让云过滤驱动把它下载下来；删占位文件不腾本地空间，还会删掉云端那份。所以它们永远不是候选，抽屉里计数「云占位 N（读内容会触发下载）」。
- S0 用扫描时的 `CLOUD`/`OFFLINE`，S1 再核对属性（`RECALL_ON_OPEN`、`RECALL_ON_DATA_ACCESS`、`OFFLINE`、云重解析标记）。`FILE_OPEN_NO_RECALL` 只是第二道保险：它为 HSM 设计，云过滤驱动认不认没测过，不能只靠它。
- 已经完整下载、没有召回属性的文件是本地文件，照常读；保持访问时间也让「存储感知」不会因为我们读过而留着它。

### 5.6 杀毒软件和访问时间的抽样核对

每卷读过的前 32 个文件、之后每 64 个，关闭后再取一次访问时间与 S1 的比；变了的计 `atime_moved_by_others`，抽屉提示：「读取后有 N 个文件的访问时间变了。SpaceKnife 自己的读取不改访问时间，多半是杀毒软件在打开时检查文件」。测量工具可以 `--stop-on-atime` 停掉这块盘的内容读取。

### 5.7 每种介质的读法

- **SSD、NVMe、虚拟盘**：先对一波候选做 S1（便宜，先合并硬链接），再按可腾出从大到小处理组，每块盘同时最多 8 组、32 份在读；S2、S3 接着做，句柄交接；结果随时流出。
- **HDD、USB 机械盘、SD 卡**：不交接句柄（S3 每组一份一份地读），每步读 64 MiB，每批 100 ms。按物理位置排序在第二期，本机没有 HDD，这条路照写照标。
- **网络**（只在打开时）：缓冲读，同 SSD 的调度。

## 6. 内存

### 6.1 候选表

- 候选表：每个 40 B（numpy 结构化数组，`codes.CAND_DTYPE`：node i4、scan、vol、state、reason、nlink u2、flags、group i4、128 位文件 ID、64 位快速摘要），测试断言 `itemsize == 40`。不分配与 store 等长的数组。

### 6.2 其他结构

- 已核对成员：表里每个 64 B（`MEMBER_DTYPE`：文件 ID、mtime、更改时间、USN、分配、node i4、组 i4、扫描、卷、角色（低 4 位角色、高 4 位保留原因）、标记、`unit` i4——这份所属物理文件的代表行，任何行号都放得下；它曾经是 1 字节，第 257 份成员就让查找失败）。另有每份的路径字符串（S1 核对过的那个名字：删除篮和守卫要的正是它，监控改名后从 store 重拼的路径不是核对过的那个，所以不省）和 8 B 的创建时间。
- 组记录、文件夹汇总（有多余字节的文件夹，node i4 + bytes i8）、帧注释用的有序成员索引，都和已核对的数量成正比；每组的有效、同一份数据、可腾出另存成 numpy 数组，状态、账本、帧列都是向量运算。
- **实测**（评审时 2.3 万候选、2 万份已核对，tracemalloc）：作业峰值约 1.2 KB/候选，作业后保留约 0.7 KB/候选；其中 Results 每份约 480 B（路径字符串、组对象），缓存新条目原来每条约 350 B（0 维数组加元组键，已改成可增长的结构化数组，128 B/条），每卷缓存整表常驻（每条 128 + 16 B，上限 26.2 万条约 36 MiB）。40 B/候选只是候选表本身；TODO 里的 32–48 B 指的是它。按此推算 C:（5.2 万候选）峰值约 65 MB，跨盘 25.7 万候选约 300 MB。
- 读缓冲每盘一个池；在读成员在 Rust 里（BLAKE3 Hasher 约 1.9 KB）。渲染进程不持有 O(N) 的东西：组列表、文件夹列表都是分页切片，点亮只用帧里的两列。
- 数字见 [memory.md](memory.md) §11。

## 7. 哈希缓存

### 7.1 文件

- `cache_dir()/dupes/v1/<卷键>-a<算法号>.skh`，每卷一个，所有扫描和作业共用；不随快照走；**不存文件名**。64 B 头（魔数 `SKDH`、版本、算法号、快速摘要参数号、信任类、卷键、条数），正文是按文件 ID 排序的 128 B 条目（文件 ID、大小、mtime、更改时间、USN、哈希时间、快速摘要、摘要长度、32 B 摘要或 16 B 前缀摘要、标记、最后见到的日子）。

### 7.2 写入和淘汰

- 载入后就关上（Windows 上「清除缓存」照样能删）；作业结束时和长作业每 60 s 写一次：临时文件、fsync、改名，改名前和磁盘上的合并（CLI 和服务可能同时写，哈希时间新的赢）。坏文件丢弃后重建。
- 只在有新条目，或有条目今天第一次被见到时才写：当天已经见过的条目再被查到不算变化，第二次运行（同一天）一个字节也不写。文件自上次读或写以后没被别人动过（mtime、大小）就不再读回来合并，整表只拷一次。保存的代价仍然和整表大小成正比（满表 32 MiB 一次）；改成追加日志加定期压缩留在第二期。
- 淘汰：90 天没见过的删，每卷最多 26.2 万条。别的算法号的条目不混用：Python 回退用 BLAKE2b-256，和原生的 BLAKE3 各存各的。

### 7.3 信任类和不对称信任

| 信任类 | 文件系统 | 用来**分开** | 用来**认定相同** |
|---|---|---|---|
| 强 | NTFS、ReFS（有 USN 日志时再核对 USN）、WinBtrfs、ext4、xfs、btrfs、f2fs、bcachefs、APFS、HFS+ | 大小、mtime、更改时间对上 | 全文条目、不是 racy、算法和参数相同、所有戳（和 USN）对上 |
| 弱 | FAT、exFAT、网络盘、FUSE、未知；Windows 上的 Python 回退（没有更改时间） | 能 | 永远不能：要重读才能并入 |

用过期的条目去分开，最坏只是漏掉一个重复；认定相同必须证明字节就是当初哈希的那些。前缀条目（S3 在检查点被拆出去的成员）只能用来和同一偏移处摘要不同的伙伴分开。

### 7.4 第二次运行

- S1 对所有候选只做元数据查询，然后查缓存：**没变过的文件不读内容、不打开数据**（测试断言内容字节为 0、数据打开为 0）。
- **改名、移动会让缓存失效一次**：这些操作会更新更改时间，所以下次重读一次，之后又能命中。

### 7.5 监控与失效

- 实时监控只是提示，正确性靠戳：监控报告某个成员变了时（任何改动：大小不变的原地改写也算，事件里的每个文件都报给结果，重新列目录时比较大小和 mtime），它退出所在的组，组回到「待核对」，不会被删；抽屉提示「N 组因为文件变了退回『待核对』」，「再查一次」只读变过的文件。节点重映射（`_Remap`）照映射候选表和成员索引，映射成 −1 的成员记 `gone`。
- 第一期**不**自动在后台重新核对变过的成员，也不把监控新发现的同大小文件加进组（留在 TODO）。

### 7.6 上一次的摘要

- `last.json` 按扫描根记上一次的时间、组数、份数、可腾出，计划和命令面板里写「上次的结果（3 天前）」。结果本身不持久化（重跑靠缓存，只做元数据）。

## 8. 结果、保留规则、删除篮

### 8.1 组的角色

每个已核对的组里，每个物理单位一个角色：`keep`、`extra`（多余，可删）、`alias`（同一个文件的其他名字）、`clone`（同一份数据）、`needed`（程序需要或受保护，永远保留）、`pinned`（必须保留）。

同一个文件经两条路径被看到（重叠的扫描、指向扫描里文件夹的符号链接或 bind mount），而它在盘上只有一个名字（链接数 1）时，另一条路径不是硬链接：它标成「视图」（`F_VIEW`，协议里 `view`），带着代表那份的角色，账本、份数、可腾出只算一次，进删除篮也只用它自己那条路径删一次。链接数大于 1 的还是只能保留。

### 8.2 保留规则（按顺序，前面的先定）

1. 永远保留：受保护路径、程序需要的、`pinned`。
2. 优先的位置（`dupes.keep` 的 `prefer`）。
3. 基本规则（`dupes.keep_rule`，默认「最早创建」；另有「最新修改」「路径最短」）。
4. 文件夹一致（`dupes.folder_consistent`，默认开）：两份分别落在同一对文件夹里、且这对文件夹至少有 2 组时，这些组的保留方都在同一边，删完后另一边可以整个清空。
5. 跨盘时每个卷至少留一份。
6. 决胜：路径短的，再按字典序，结果确定。
7. 手动（「保留这一份」）：按 (内容摘要, 路径) 记在作业结果里，覆盖 2–5，不能覆盖 1。手动选择**累积**：对另一组点「保留这一份」不会丢掉前一组的；同一组再点一次，换成新点的那份。改规则、「再查一次」都带着它们（新查找从被替换的那次接过来；摘要保证只对同样的内容生效）；`reset_overrides` 才清掉。

后端强制的不变式：每组至少一份不在删除选择里；跨盘且「每卷留一份」开着时每卷至少一份，删除前的守卫也按卷核对（某卷上的多余副本只有在**同一个卷**上的保留方完好时才删）。关掉「每卷留一份」就是只留一份：别的卷上的备份照常预选为多余并计入可腾出（之前设计里的 `other_volume` 角色没有实现，已去掉）。规则一改，保留方、文件夹汇总、配色、可腾出都重算；全部组的重算在线程里对一份快照做，没有新组进来就提交，不占事件循环。

### 8.3 可腾出的账本

- 可腾出 = 多余各份的私有分配，减去块克隆共享的字节；别名、块克隆分开列；可克隆但查不到共享信息的卷加注「可能共享数据块，实际腾出的可能更少」。按卷分开。

### 8.4 文件夹层（第一期只给信息）

- **文件夹汇总**：每份多余的副本把它的字节加到所有祖先上，供帧的文件夹分档、悬停卡。
- **「按文件夹」页**：只列直接装着多余副本的文件夹，加上两条以上这样的分支汇合、而且多余字节占到 10% 以上的文件夹；一条单链（C:\Users → C:\Users\x → …）只列最深的那一层。每行写出它的**对应文件夹**：它的多余副本的保留方大多在哪个文件夹（「75% 在 Photos\2021 也有」），悬停时两边一起点亮；可以翻页。这是研究 #5「回声」的第一步：成对的文件夹，按已核对的内容算，不靠名字和大小猜。
- **覆盖**（「这个文件夹在别处有没有」）：文件夹里每个合格的文件归到「在别处有一份」「只在这里」（大小独一无二的不读盘就能确定）「同一份数据」「没核对」（小于下限、云占位、读不了……）之一，给一条按字节的覆盖条、别处的副本主要在哪几个文件夹（最多 5 个，可点击定位、悬停点亮）和「只在这里」最大的 50 个。整个扫描查过之后直接从结果回答，不另起作业。**第一期不给删整个文件夹的决定**：要删整个文件夹，得证明里面每个文件都核对过，出错就是丢数据。

### 8.5 删除篮

- `dupes.to_basket`：每个 (扫描, 卷) 一个 `dupes` 条目，成员是各组多余副本的路径；后端另存每个成员的**守卫**（不进协议）：成员和它这组保留方的身份、大小、mtime、更改时间、USN。提交时去掉不能删的名字；保留方已经是删除篮的目标的组拒绝（「本组保留的那份已在删除篮里」），不计入份数和可腾出。
- **执行前**（`ops/trash.py`，在已有的只差大小写、已不在、受保护、占用检查之后）：
  - 成员重新取身份和戳，不同 → `changed`「核对之后这个文件变过，没有动」；
  - 保留方不存在、戳变了、或和成员成了同一身份 → `keeper_changed`；
  - 保留方在这次要删的任何路径下（包括别的条目，按整次执行的路径集合判断，与顺序无关）→ `last_copy`；
  - **按身份**：保留方的 (卷, 文件 ID) 是这次或删除篮里任何一份要删的多余副本，或者保留方所在的文件夹（及以上各级，按 `stat` 的身份）是删除篮里要删的文件夹 → `last_copy`。同一个文件夹经两条路径（符号链接或 bind mount、SUBST、8.3 短名、macOS 的 firmlink）各扫一次、两次查找选了不同的保留方时，靠这一条不会两份都删；只比路径时会。
  - 开着占用检测时保留方正被别的程序打开 → `keeper_busy`；
  - 打开了「执行前重读内容」的，两份用作业同一套读法重读（不改访问时间，按系统能接受的名字打开，读前读后核对身份和戳），不同 → `changed`。
- 之后用户把保留方所在的文件夹也加进删除篮：不拦用户自己的条目，而是把 `dupes` 条目标成 `blocked`（「有几组保留的那份也在删除篮里，执行时这些组跳过」），执行时这些组记 `last_copy`。加入和标 `blocked` 时同样按身份比：保留方是删除篮里另一个 `dupes` 条目的多余副本（另一条路径）就拒绝或标 `blocked`。
- 删除篮里的 `dupes` 条目可以展开（`dupes.basket_members`）：逐份列出要删的和它的保留方，以及涉及的主要文件夹——删除前最后一处能逐份复核的地方。
- 撤销（回收站的恢复）把条目和守卫一起放回删除篮。放回的文件更改时间变了，所以要再删它得先再查一次（守卫会记 `changed`）。
- 删除篮只在内存里，守卫也一样。

## 9. 调度、调速器、暂停、取消、GIL

### 9.1 磁盘队列

每块物理盘一个 `DiskQueue`：自己的线程池（按介质：NVMe 8、SATA SSD 4、HDD 2）、这块盘的 `IoGovernor`、一个原生读取器。

### 9.2 一批

每批（约 30 ms，HDD 100 ms）的 Rust 调用之前拿一次许可；测试断言没有绕过许可的 IO，许可次数等于 IO 调用次数。

### 9.3 负载档

作业自己的档（`dupes.load`，默认「安静」；计划里开始前就能选，运行中也能改），开始时设到这块盘的调速器上，作业结束后恢复成原来的值。

调速器按队列深度估负载，大块顺序读在它看来很轻：SATA SSD 上 1 MiB 的读排约 2.7 深的队列就把带宽占满了，调速器却只算 34%（评审实测 D:\「安静」档 active 97–99%、约 440 MB/s）。所以低于「最大」的档，S3 的大块读另外按**时间份额**走（`engine.DutyCycle`）：有 S3 批在跑的时间记成欠账，每秒按档位的份额（安静 35%）还掉，欠账超过 0.2 s 就等。它不需要知道盘有多快：S3 跑的时候盘就忙着它，其余时间留给别的程序。代价是快盘（读被哈希限住时）上也少读一些。「空闲」档不加这一层（它本来就在别人用盘时让开）。「空闲」档降线程的 I/O 优先级。同盘有扫描时作业让路（`waiting_scan`，抽屉写「等 D: 的扫描结束」），扫描结束后继续；作业从不调 `governor.pause`。

### 9.4 暂停、恢复、取消

- **暂停**：不再申请许可；正在排队等许可的请求撤回，暂停时才拿到的许可原样退回、不开句柄不读；等在途的一批结束，关掉所有句柄（哈希器和偏移留着）；恢复时重新打开并先核对身份和戳。
- **取消**：同样撤回许可、等在途的一批，已学到的写进缓存，没下结论的候选记「没来得及核对」（状态里 `stop_reason`、`undecided`）。
- 一批算「在途」直到它的线程真正结束（不是等它的协程被取消为止）：取消、到上限、出错之后读取器里不留句柄和成员（测试 `test_no_handle_outlives_a_budget_stop_or_a_failure`、`test_a_pause_while_permits_are_slow_stops_every_read`）。
- 一组出错时整个作业干净地结束（其余组取消并收回异常），状态是「出错」，给用户的是可读的一句话，异常原文只进日志。
- 预算：`budget_bytes`、`max_seconds`（测量工具和 Verify 用）到了就停，同取消。

### 9.5 GIL 和事件循环

读和哈希在 Rust 里做，不持 GIL；事件循环上只做调度和每批的小量 numpy；`dupes.progress` ≤4 Hz，`dupes.changed` ≤1 Hz，「重复」配色的视图重画 ≤1 Hz。

状态（每秒 4 次）、账本、帧列都是对成员表的向量运算：20 万份成员时账本约 4 ms、合计约 1.5 ms（之前是逐份的 Python 循环，评审测得状态 168 ms）。作业结束和改规则时的全部保留规则在线程里算（20 万份约 0.9 s，事件循环最长停顿约 14 ms）；组页、`under` 和名字筛选、覆盖、文件夹页都在计算线程里；前缀拆分是 O(n)（3,000 份同大小时原来 0.4 s 的平方算法）。进度按字节：做完的组按它的字节算，正在读的按已读的算，读一对 20 GB 的文件时也往前走。

### 9.6 一个后端一个作业

同时只有一个作业；再开一个报「已经有一个查找在进行」，除非 `replace`，或是 `file` 模式且文件在正在跑的作业里（那一组先做）。新作业替换同一批扫描的旧结果（手动选择接过来）；关掉扫描、或扫描为省内存被淘汰时，它的作业取消、结果丢掉、界面收到 `cleared`。已经进删除篮的多余副本留在删除篮里：每份带着自己的守卫，执行前照样全部核对。跨盘查找只取开着页签的扫描（有页签的扫描不会被淘汰），计划里列出要比较哪些、可以逐个去掉。

## 10. 界面与可视化

### 10.1 入口（从不自动开跑）

- **命令面板**：「查找重复文件…」（别名 duplicates、dupes、dedupe、same files、查重；先打开抽屉显示计划，用户点「开始查找」才读；已有查找时显示它的结果）、「重复文件面板」、「配色：重复」（只能输入调出）、「把多余的副本加入删除篮」。需要已扫完的实时扫描；快照页签里禁用：「快照是过去的状态，不能核对内容」。
- **右键菜单**：文件夹「这个文件夹在别处有没有？」；文件「查找与它相同的文件」（只读它这一个大小组；有作业在跑时让这组先做），已核对的文件「另有相同内容的文件 · 点亮它们」。不能用时禁用并写原因。
- **详情面板**：文件加「相同内容」一节（其他几份、在图里找到它、保留这一份）；文件夹加「重复」一节（多余的副本有多少、「这个文件夹在别处有没有？」）。
- **状态栏**：作业运行中或当前扫描有结果时出现，点了打开抽屉。
- **工具栏**：不加按钮；当前扫描有结果时配色分段里才出现「重复」，C 键也只在那时轮到它。

### 10.2 「重复」配色

`ColorModeName` 的 `"dupes"`。只发给这个配色的视图两列可选的帧列（协议 §4.1「加可选列是兼容的」）：

- `dup` u1：文件行是状态（0 没参加、1 待核对、2 保留、3 多余、4 同一份数据、5 跳过、6 比较过而没有伙伴——画法同 0，右键菜单据此只对真正比较过的文件说「没有和它内容相同的」）；文件夹、折叠块、聚合块是「多余字节 / 这一行的大小」的分档（0 没有、1 >0、2 ≥10%、3 ≥40%、4 ≥80%）。
- `dupg` u4：文件行的组号 + 1，悬停时不用往返就能点亮画面里的同组副本。
- 每行 5 B，5 万行 250 KB，在 [visuals.md](visuals.md) §12 的帧预算内。

| 行 | 填充 | 图案 |
|---|---|---|
| 文件 · 没参加或没有伙伴、跳过 | `treemap.class.other` | — |
| 文件 · 待核对 | `treemap.dupe.pending`（中性） | 细 135° 斜纹：还没结论，不叫「重复」 |
| 文件 · 多余 | `treemap.dupe.share.4`（品红） | 细 45° 斜纹 |
| 文件 · 保留 | 中性 | 1.5 px `treemap.dupe.keepRim` 内描边 |
| 文件 · 同一份数据 | `treemap.dupe.shared`（灰） | — |
| 文件夹、折叠块、聚合块 | 分档 → `treemap.dupe.share.1–4` | 聚合块保留点阵；第 4 档（≥80%）的折叠文件夹也加点阵，和多余的文件（同色加斜纹）分得开 |

火焰图、火焰-极坐标图里文件同样带斜纹和保留方的描边，展开的文件夹条也用这个色阶，成为一张「每层文件夹的多余字节」热图。斜纹的第二色是填充色的深浅变化（亮的填充压暗 18%，暗的提亮 14%）；斜纹上的大小那一行改用名称的颜色（暗色主题下副标签色只有约 3.5:1）。浅色主题的「同一份数据」改成浅的中性色 #D2D5DA，删了不腾空间的块不再最显眼。

**图例**：抽屉里一块可以收起的图例；抽屉关着而视图在「重复」配色时，画面左下角也有一块：五种文件状态和四档文件夹，写明门槛（有一点、≥10%、≥40%、≥80%）。色值两个主题都**暂定，待用户评审**；色盲时靠图案区分。结果清除后，这个配色的视图回到「类别」。

### 10.3 点亮一组（所有窗格）

`classMarks` 推广成 `rowMarks(g, f, pick, scope, dpr)`，类别点亮是它的一个特例。抽屉里悬停组行、「重复」配色下悬停一个块（悬停卡出现时）、右键「点亮它们」设全局的焦点组：画面里的同组行按 `dupg` 立刻点亮；100 ms 后请求 `dupes.locate`，后端给出这一帧里每一份所在的行（藏在折叠文件夹或「N 个小项」里的给那一块），所以在别的配色下（帧里没有 `dupg`）悬停抽屉里的组也能点亮。最多点亮 2000 份，超出时抽屉写「只点亮最大的 2000 份」。画在呼吸画布上，不借用闪烁和呼吸，不画连接线。

### 10.4 悬停卡

`tree.node` 在扫描有结果时附 `dupe`：已核对的写「另有 N 份内容相同 · 删掉多余的能腾出 X」、最多 2 条路径、其他卷、画面里没画出来的份数、「这一份是多余的」或保留的原因；待核对的只写「同样大小的文件正在核对内容…」，不做身份断言；同一份数据写「删了不腾空间」；跳过的写原因；比较过而没有伙伴的（状态 `unique`）写「比较过：没有别的文件和它内容相同」；文件夹写「里面有多余的副本 X」。右键菜单打开时悬停卡隐藏。

### 10.5 「重复文件」抽屉

占据侧栏，优先级：删除篮 > 重复文件 > 过滤结果 > 扫描详情 > 详情面板。内容跟随当前页签。自上而下：范围、下限和负载档；开始前的计划（同大小的候选数；**最坏要读多少**、按上次在这里的速度大约多久、盘的类型、最多能腾出多少；头尾要读多少、大小独一无二的不读；没有比较的各类和原因，下限写成大小；上一次的结果；跨盘开关和要比较的扫描（只取开着页签的，可逐个去掉）；负载档和可选的上限：最多读多少 GB、最多多少分钟；估计失败时写原因并给「重试」）；可腾出（按卷）；漏斗即进度（同样大小 → 同一个文件的几个名字算一份后 → 缓存认出 → 读了头尾 → 内容相同 N 组）、已读多少、没有比较的原因；运行条（%、阶段、速率或「速度估计中」、「最多还要 N 分钟」、负载、暂停、停止；停下或出错时进度条停在实际位置并变灰，写「还有 N 个候选没核对，结果不完整」）；覆盖条（问过某个文件夹时）；图例；保留规则；「组 | 按文件夹」两页和排序，第二行是筛选（按名字或路径、只看当前文件夹、只看跨盘、也列同一份数据）；提交按钮「把多余的 N 份加入删除篮」和始终看得见的大小，下面「执行前会再核对每一份没有变过」。

组行是紧凑的：一行写名字、份数、单份大小和可腾出，结论是图标（悬停看文字），每份一行；路径按组里各份的公共前后缀缩写，只留互不相同的那一段和文件名（`C:\…\site-old\…\intro.mp4`），完整路径在提示里；保留方的原因在它的角色标签上；「保留这一份」在悬停、键盘聚焦、点亮时出现；别的扫描的那份点了切到它的页签并定位。运行中核对完的组随时插入：刷新时把显示过的组分页（每页 500）全部取回，新组插到它该在的位置，列表长度不变、不跳。

### 10.6 每帧成本

只在「重复」配色的视图里每行多 5 B；查找 O(行数 · log 成员数)（评审在 5 万行的帧上测得约 29 ms，之前写的 0.5 ms 不对；其中每行一次的 Python 列表推导已换成按组号取的 numpy 数组）；待核对、跳过、没有伙伴的节点表每 0.5 s 至多重建一次，不随每组完成都失效；`locate` 只对聚焦的组做，上限 2000。组列表和文件夹列表是预排序数组的分页切片。渲染进程不持有 O(N) 的东西；点亮复用呼吸画布，空闲时缩成 0×0。

## 11. 协议

Electron 在 `session.hello` 里声明 `dupes.v1`；没有声明的会话收不到 `dupes.*` 事件、`tree.node` 不带 `dupe`、帧里没有 `dup`/`dupg`，「重复」配色也不可用。配色分段在当前扫描有查找时出现：视图状态的 `has_dupes`，或界面自己记着的这次查找（比下一次视图状态先到）。
方法、事件和模型见 [protocol.md](protocol.md) §3 的 `dupes.*` 一节。要点：`dupes.plan` 不读盘（它还带回覆盖这个扫描的作业，界面重连后据此接上）；`dupes.start` 在后台跑；`dupes.groups`/`dupes.folders` 分页；`dupes.locate` 给出帧里的行；`dupes.keep` 改保留规则；`dupes.to_basket` 进删除篮。

## 13. 测量工具

```
spaceknife dupes PATH... [--min-size 1M] [--cross] [--load quiet] [--budget-bytes 4G] [--max-seconds 180]
                 [--no-cache] [--include-system] [--include-network] [--keep-atime skip|read]
                 [--stop-on-atime] [--python] [--threads N] [--json [--groups]]
```

先走 CLI 的扫描路径，再跑作业，打印每一步的个数、字节、数据打开和元数据打开、重开、时间、CPU、峰值内存、缓存命中、许可数、跳过原因、访问时间计数。它是成本模型和 Verify 的测量工具；对用户的盘只读，真实数据上要设 `--budget-bytes` 和 `--max-seconds`。

## 15. 没在真机验证的

- macOS 的全部读法（§5.4）、APFS 克隆识别（没做）；
- WinBtrfs 上的块映射和文件 ID；
- 属性句柄上能不能取到 USN（取不到时按「没有 USN 的卷」处理）；
- `FILE_OPEN_NO_RECALL` 对云过滤驱动是否有效（所以先按属性剔除）；
- HDD 上的读盘顺序（本机没有 HDD；第一期 HDD 只是不交接句柄、每步读 64 MiB、每批 100 ms，按物理位置排序在第二期）；
- macOS 上关掉无数据文件下载的 `setiopolicy_np`（§5.4）；
- btrfs 上跨子卷的块映射比较（§4.3；本机 WSL 是 ext4，只有单元测试）；
- 根下挂的真实 NFS、SMB、FUSE 挂载（§5.3；测试用打桩的卷）；
- Windows 上只差大小写的同名项（WinBtrfs、区分大小写的 NTFS 文件夹）真的存在时判 `ambiguous`（§5.2；单元测试只覆盖了大小写不同但没有同名项的情况，有同名项的真实目录要设 `SPACEKNIFE_TEST_CASE_ROOT`）；
- 「安静」档时间份额在 SATA 盘上的实际 active% 和 MB/s（另一个流程在这台机器上计时，评审要求的验收没有做）。
