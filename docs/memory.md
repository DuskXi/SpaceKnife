# 内存模型

后端把一次扫描存成按列的节点表（numpy 数组）加一个名字堆，不为每个文件建 Python 对象。本文给出每项（一个文件或文件夹）的内存开销、规模估算、两种存储模式，以及防止内存失控的机制。数字来自 `tools/bench_memory.py`，在一个 845 万项的 C: 盘快照上实测（Windows 11，2026-10-18）。

## 1. 每项开销

| 结构 | 每项 | 说明 |
|---|---|---|
| 节点列 | 89 B | parent 4 · depth 2 · kind 1 · flags 4 · name_off 4 · name_len 2 · ext 2 · size 8 · alloc 8 · mtime/ctime/atime 12 · ino 8 · nlink 2 · child_start/child_count 8 · tot_size/tot_alloc 16 · tot_files/tot_dirs 8 |
| 名字 | 名字字节数 + 1 | 每个名字前一个 NUL（`\0name`），按节点 id 顺序连续存放；C: 实测 24.7 B |
| 名字索引 | 12.5 B | 分隔偏移 int32 4 B + 64 位字符集签名 8 B + 少量结果缓存；名字本身零拷贝引用名字堆 |
| **合计（常驻）** | **≈ 126 B** | 名字平均 24 B 时 |

面积基准（文件夹的子树占用、文件自己的占用）不再按 store 版本缓存成每项 8 B 的整列：树图、火焰图、火焰-极坐标图和命令面板都只算用到的节点（`Basis.sizes_of`、`LazySizes`）。原来每次文件变化后整列重算一遍（C: 约 66 MB、50 ms）。

`name_off` 平时是 uint32；名字总量超过 4 GiB（约 1.7 亿项）时自动加宽成 int64（每项多 4 B）。

有固定上限、不随项数线性增长的缓存：

- ASCII 小写副本：命令面板和子串过滤用，**所有扫描合计 ≤ 256 MiB**（`LOWER_CACHE_BYTES`）。超出部分在查询时临时生成，不留驻；代价是那部分的全量子串搜索约慢一倍。
- 名字索引的查询结果缓存：每个扫描 ≤ 16 条、≤ 256 MiB。
- 开着过滤器的视图：每项约 20–25 B（每个文件夹的匹配计数、占用、大小），关掉过滤即释放。
- 计算中的临时内存：遍历整次扫描的请求（渲染、过滤、汇总、搜索）最多同时 4 个（`server/compute.py`），每个约 40–80 B/项，用完即释放；同一会话里被新请求取代、还在排队的旧请求直接丢弃。汇总（详情面板、「本机磁盘」）分块遍历，不随项数增长，见第 5 节。

## 2. 规模估算

| 项数 | 内存模式（常驻） | 映射模式（私有提交） |
|---|---|---|
| 100 万 | ≈ 0.13 GB | ≈ 0.01 GB |
| 1000 万 | ≈ 1.3 GB | ≈ 0.13 GB |
| 5000 万 | ≈ 6.3 GB | ≈ 0.6 GB |
| 1 亿 | ≈ 12.6 GB | ≈ 1.3 GB |

两列都另加上面那些有上限的缓存（主要是 ≤ 256 MiB 的小写副本）。映射模式下的私有部分是名字索引（约 12.5 B/项，搜索或过滤过才有）；节点列和名字在映射文件里，由系统按需留在内存。打开「大扫描存进映射文件」（默认关）后，约 200 万项以上的扫描都用映射模式（第 3 节）。

C: 盘实测（845 万项，名字平均 24 B）：

| | 加载后 | 建好索引并搜索后 | 每项 |
|---|---|---|---|
| 内存模式 | +918 MB | +1289 MB（含 199 MB 小写副本） | 160 B |
| 映射模式 | +2 MB | +368 MB | 46 B |
| 改造前 | | | 183 B |

查询速度（热数据，两种模式相同）：命令面板 2–25 ms；未缓存的全量通配 `*.dll` 655 ms、`*cache*` 215 ms、`win*` 145 ms，比改造前慢 3–14%（名字改为原地搜索、小写副本按需生成）。

## 3. 两种存储模式

- **内存模式**（默认）：列在普通内存里。
  - 硬扫描开始时，按同一位置最新一次完整快照的项数（多留 5% 加 4096 行）一次分配好列（`NodeStore.reserve`，`scans.RESERVE_SHARE`），扫描中不再扩容复制；超出时仍按 1.5 倍扩容。
  - 扫描过程中列按 1.5 倍扩容（`nodes.GROWTH`；原来 2 倍，最多一半空着），扫描结束后收缩到实际大小（`NodeStore.compact`）。
  - 收缩以后（快照加载、MFT 建树之后也一样）再有文件变化，每次只多留 1/16 或 6.5 万行，取大者（`SETTLED_SHARE`、`SETTLED_MIN_STEP`），不再整份翻倍：原来扫完后第一次文件变化就把列翻倍，325 万项的盘多提交约 280 MB，C: 那样的盘约 0.75 GB。
- **映射模式**：列和新的名字块放进 `<缓存目录>/columns/` 下的临时文件，用共享映射访问。文件映射的页面由文件本身做后备，**不计入私有提交**（Windows 的「已提交」、Linux/macOS 的匿名内存）。常用页面由系统留在内存里，访问速度和普通内存一样；写进这些文件以后，冷页面可以直接丢弃，不进页面文件，再访问时从 SSD 读回（一次全列扫描约多 0.1–0.4 秒）。
  - 切换条件，满足其一即可（`mapped.Policy`）：
    - 这个扫描的列（含扩容余量）加名字达到 256 MiB（`LARGE_BYTES`，约 200 万项）：「设置 → 高级 → 内存 → 大扫描存进映射文件」（`advanced.map_large_scans`，**默认关**：扫完要把数据写盘一次，见下）；
    - 所有打开的扫描在普通内存里的列和名字，加上这次扩容或加载需要的量，超过「物理内存 × `advanced.memory_budget`」（同一页，默认 25%）。
  - **写盘**：系统会把填过的页写进映射文件（以后才能直接丢掉），所以每页应该只写一次：
    - 列的文件原地加长（`mapped.grow`，新旧映射共用同一批页面），不再复制到新文件；
    - 扫描结束时映射的列不再收缩复制：没碰过的尾部既不占内存也不写盘，只在缓存文件夹里占磁盘空间（最多约为列本身的一半）；
    - Windows 上加长文件不用 `os.ftruncate`：C 运行库的 `_chsize` 会把新加的每个字节写成零，整套列平白多写一遍；改由映射本身加长文件，不写任何数据（有测试）。
    - W: 325 万项实测：一次扫描约写 665 MB（每项约 215 B），扫完后半分钟内写完；之后实时监控的文件变化几乎不再写盘。改之前约 1.3 GB。
  - 扫描速度和内存模式相同（同一块盘 5–6 秒）。
  - 文件自动清理：Windows 以「关闭即删除」打开，映射持有最后一个句柄；POSIX 创建后立即 unlink。进程崩溃也不会留下文件；启动时再清一次残留。
  - 磁盘空间不足、建不了文件时，自动退回内存模式。
  - 测试和实验可以用 `SPACEKNIFE_MAP_ABOVE=<字节>` 强制切换阈值，`SPACEKNIFE_MAP_ABOVE=1` 即全部映射；整套后端测试在这种模式下也全部通过。

## 4. 名字的存放与索引

- 名字堆（`store/heap.py`）：名字以 `\0name` 形式写进固定大小、永不移动的块，块从 64 KiB 起翻倍到 8 MiB。块不会被改写或挪动，所以名字索引直接持有零拷贝视图，扫描可以同时追加。
- 名字索引（`filter/names.py`）：正则和 numpy 直接跑在这些视图上；大小写不敏感用 ASCII 小写副本（有上限的缓存）和大小写折叠后的字符签名。
- 快照格式 2 原样保存名字堆（按 id 顺序的 `\0name` 序列），加载时零拷贝使用（C: 1.0 秒）；格式 1（名字首尾相接）仍可读取，加载时重排（1.4 秒）。
- 打开快照时，文件以只读方式映射，每一块直接解压进节点表最终使用的数组（`snapshot.load`）。原来先整个读进内存，每列先解成只读的 bytes、再复制一份成列：C: 快照打开时峰值 +1812 MB，最后只留 945 MB；现在峰值就是 945 MB，耗时不变（0.9 秒）。
- 保存快照（0.3.4，`snapshot.save`）：每一列、然后名字，各是一个 zstd 帧，按 100 万行一段（`SAVE_ROWS`）交给压缩器、边压缩边写进文件（`stream_writer`），压好的数据不留在内存里；`name_off` 按段换基到名字图像（`NodeStore.export_pieces`，名字跨几个堆块时照旧是 int64），不再整列转换；zstd 最多 4 个工作线程（`SAVE_THREADS`）。文件头先按占位数字（10^15）留出位置，写完再回填、用空格补齐，格式 2 不变（`json.loads` 接受结尾的空白，旧版本照样读），各块解压后与原来的写法逐列相同（测试与 0.3.3 的写法比较，含多个名字块和比一列更小、更大的分段）。
  - 原来的写法有三处尖峰（第一轮拆分）：python-zstandard 的一次性 `compress()` 按 `ZSTD_compressBound` 分配输出、压完只改长度不缩容，20 个块全部留到写文件，几乎等于各列的原始字节数（Windows 上约 1 MB 以上的堆块整块计入提交）；`threads=-1` 在 32 个逻辑 CPU 上的 ZSTDMT 缓冲（round buffer 约 280 MiB，外加几十个 8 MiB 的输出缓冲）；`export_columns` 把 `name_off` 整列转成 int64。
  - 实测（2026-10-23，Windows，同一份 C: 快照 883 万行加载后保存，两种写法各一个进程、按轮交替各 3 次）：耗时 3.05 s [2.49–3.75] → 0.77 s [0.75–0.82]；提交尖峰 +1366 MB [1362–1372] → +113 MB [105–113]；工作集尖峰 +477 MB → +92 MB；文件都是 126.9 MB。整盘扫描（`bench\run_scan.py`，扫完即保存）的保存阶段峰值私有内存：C: 2612 / 2603 MB → 1355 MB（扫完时约 1210 MB），W:（321 万项）1248 / 1245 → 660 MB，K:（191 万项）882 / 875 → 427 MB，I:（150 万项）744 / 747 → 363 MB，F:（107 万项）603 / 599 → 292 MB；这些扫描的整个过程的峰值本来都在保存阶段。

## 5. 防止内存失控

- **有界计算池**：遍历整次扫描的请求最多 4 个同时运行，同类请求只算最新的（`server/compute.py`）。
- **监控整理**（`mutate.compact`）：实时监控下删掉和重列的行累计到 25%（至少 10 万行）时，整棵树重新编号一次。
  - 原来重排名字时给每个名字字节建一个 int64 下标（加上中间数组约 600 B/项），整理一次 C: 瞬间多占 +6278 MB（每项 759 B）。
  - 现在列按 26 万行一块、名字按 4096 行一块，从名字堆的各块直接拼进新的 `\0name` 图像，新节点表原样接管；新编号和映射表用 int32。C: 实测峰值 +1024 MB，其中 980 MB 就是整理出来的新副本，耗时不变（3.1 秒）。结果与旧算法逐列一致（随机树对照测试）。
- **后端基线**：命令面板的拼音（「qhps」找到「切换配色」）改为读开发时生成的 `palette/pinyin.json`（`tools/gen_pinyin.py`，测试检查是否最新），运行时不再导入 pypinyin，空闲后端少约 50 MB（导入它就要 50 MB 词典）。
- **整盘汇总**（`tree.summary`：详情面板的类别、最大文件、最近修改；「本机磁盘」的类别构成）：
  - 分块遍历子树，每块约 26 万项（`subtree.SUMMARY_CHUNK`、`subtree_chunks`），临时内存不超过几十 MB；原来每次整棵子树一次性展开，约 100 B/项（C: 约 0.85 GB）。结果与分块大小无关（随机树对照测试）。
  - 后端按「节点、store 版本、类别表、文件夹类别选择」缓存（`scans.cached_summary`，每个扫描 8 条），同一扫描的汇总一次只算一个：详情面板、「本机磁盘」和扫描结束时几乎同时要的同一份汇总只算一次，原来三份同时算。扫描进行中不缓存（扫描先改版本号、后写入行）。
  - 前端（`lib/throttle.ts` 的 `summaryInterval`）：扫描结束后，原来每来一帧就重算一次；现在 20 万项以下立即刷新，更大的子树每百万项约 1.5 秒最多一次、最长 10 秒；换选中项总是立即取。
- **扫描中的读写一致性**：扫描线程写目录的子项区间时，按「行 → 节点数 → 起点 → 数量」的顺序发布；读取方先读数量、后读起点，并校验「子项 id 大于父目录」（`NodeStore.child_range`、`store/subtree.py`）。否则读到半写入的区间会让子树遍历反复重走整棵树，内存几秒内涨到几十 GB（2026-10-18 的事故）。
- **不被弱缓存钉住**：以 store 为键的弱引用缓存，值里不得强引用回 store；关闭扫描后节点表和名字索引会真正释放（有测试）。
- **无效提交**：后端入口把 OpenBLAS / OpenMP / MKL 线程数设为 1。numpy 自带的 OpenBLAS 原本在 32 线程的机器上每个进程（后端和每个扫描 worker）一 import 就提交约 750 MB，现在约 38 MB。
- **内存看门狗**（`server/diag.py`）：每 15 秒比较本进程的私有内存和扫描数据应占的量；超过「2 × 应占 + 1.5 GiB」时，在日志面板提示，并把明细写进日志文件（各扫描的列和名字、视图、计算池队列、会话发送队列）。设置 `SPACEKNIFE_MEMTRACE=1` 后还会附上占用内存最多的代码行（tracemalloc）。

## 6. MFT 快扫的内存

- **助手**：`scan_mft` 按 32 MiB 窗口边读边解析，峰值约等于结果表（每行约 100 B 加名字）。C: 实测 837 万项峰值 1.58 GB；旧的「整块读入再解析」要 10.6 GB。
- **后端接收**：表按 `begin` 里的行数一次预分配，各批直接拷进去（列约 100 B/行，加上名字；C: 实测整张表约 160 B/行）。
- **后端建树**（`table_to_store`）：在表之外的峰值约 85 B/行（860 万行合成表实测 +691 MB；上一版 325 B/行，即 +2663 MB；更早 516 B/行）。做法：
  - 行下标（父目录、子项分组、广度优先的层、节点号）一律 int32；
  - 表的每一列按块（每块 100 万行）直接拷进最终的节点列，用节点表自己的类型（时间直接截成 uint32）；`consume=True` 时这一列随即释放，任何时候都不会同时存在「整张表 + 整份节点顺序副本」；
  - 父节点、深度、子项起点和数量、名字偏移直接按节点表的类型生成，`NodeStore.from_columns` 原样接管，不再转换复制；
  - 扩展名分两遍、每块 26 万个名字计算：第一遍收集全部不同的扩展名并按原来的顺序编号，第二遍填入；名字块只补齐复制一次。结果与分块大小无关（有测试）。
  - 建好后常驻约 100 B/项（节点列 + 名字，见第 1 节；打开「大扫描存进映射文件」时，约 200 万项以上随即转进映射文件，见第 3 节）；耗时与之前相同（860 万行约 6 秒）。
- 实测（2026-10-21，C: 862 万项，上一版）：助手解析时峰值 1.38 GB；后端接收完整张表约 1.4 GB，建树时冲到 3.62 GB（整个应用 3.80 GB），约 1 秒后回落，扫完稳定在约 1.14 GB。按新的建树开销估算，同一块盘后端峰值约 2.2 GB（表约 1.4 GB + 85 B/行），整个应用约 2.4 GB；尚未在真实 C: 上复测。
- **看门狗**：MFT 扫描的接收与建树阶段，按每行 280 B 计入「应占」（`ScanHandle.transient`；表约 160 B 加建树约 85 B），不会把这段正常峰值误报为异常。

## 7. 可视化的布局

- **树图**和另外两种可视化一样，只算画出的节点和被合并兄弟的尺寸（`SizeSource.of`），每帧没有 O(N) 的分配；C: 上首帧之后每帧约 11 ms。
- **火焰图和火焰-极坐标图**的分区引擎按需计算：尺寸用 `sizes.of(ids)`、类别用 `basis.cls_of(ids)`、子项用 `basis.children(node)`，只访问画出的行和被合并的兄弟，每帧没有 O(N) 的分配。每帧最多 `MAX_ROWS` = 5 万行，每行 53 B（通用列 37 B 加 4 个几何列）另加名字，一帧的列不超过约 2.7 MB；4K、层级 15 下实测约 900 行。行缓冲每帧新建，不跨帧持有 store 的引用。
- 隐藏模式每次渲染仍按全长数组构造尺寸（每项 8 B，渲染完即释放，已知的遗留项）；对比视图只看增长或减少时同样如此。
- 引擎在计算池里运行（第 5 节），三种可视化共用同一个池和「只算最新」规则。契约见 [visuals.md](visuals.md)。

## 8. 关掉扫描之后

起因：用户在 Windows 上连扫三次 C:（每次约 870 万项：硬扫、MFT、再硬扫），全部关掉后，看门狗报「后端内存占用异常：1.9 GB（扫描数据约 0.0 GB）」，日志里是私有 1.87 GiB、常驻 1.16 GiB，此时没有视图，计算池也空着。

**不是泄漏。** 在进程内起真实的服务端（2026-10-20，Windows 11），走完整条路径：开始扫描 → 打开视图 → 过滤（建名字索引）→ 切到火焰-极坐标图 → 关视图 → 关扫描。弱引用显示 `NodeStore` 和 `ScanHandle` 在 `scan.close` 之后立即释放，连 `gc.collect()` 都不需要。

- 硬扫描（`C:\Program Files` 36 万项，`C:\Windows` 41 万项）和 MFT 路径（假的提权助手，合成的 400 万行表）都一样。
- `test_memory.py` 的 `test_closing_a_scan_frees_its_store_and_name_index` 守着这一点。

**留下的是 C 堆的空闲空间。**

- **规模与规律**：`C:\Windows` 第一次扫完关掉，常驻比开始时多约 34 MB，约每项 60–80 B，按这个比例 870 万项约 0.5–0.7 GB。之后同样的扫描每次只再多几 MB，因为下一次扫描会复用这部分空间。
- **用 tracemalloc 排查**：还活着的 Python 和 numpy 分配前后都是 73 MB，没有增加。
- **用 `PYTHONMALLOC=malloc` 排查**：绕开 Python 的小对象分配器后，留存不变，所以不是 pymalloc 的 arena。
- **把扫描线程降到 2 个**：留存只少了五六 MB，线程栈不是主因。
- **结论**：是进程堆（Python 对象、numpy 的中等数组、原生扩展共用）的碎片。扫描期间大量中等大小的分配和少量长期存活的小块交错，空出来的页还不回去。
- **Windows 的私有内存（提交量）**还包括已被系统移出工作集的部分，所以私有内存比常驻内存大。

**现在的做法：**

- **主动归还**：`scan.close` 之后约 1 秒，`memory.release()` 让堆归还能还的部分。
  - Windows 用 `HeapSetInformation(HeapOptimizeResources)`，实测只多还回去几 MB；`HeapCompact` 和 `_heapmin` 没有效果。
  - glibc 用 `malloc_trim(0)`；macOS 用 `malloc_zone_pressure_relief`。
- **看门狗**（`server/diag.py`）：
  - 限额在 `2 × 应占 + 1.5 GiB` 之上，再加「最近一小时关掉的最大那次扫描的大小」（`ScanManager.closed`，按关闭时的 `ram_bytes()` 记），这部分是堆留给下一次扫描复用的；
  - 超限时先调一次 `release()` 再量，仍超才报警。
  - 真正的泄漏（每关一次都留下整份数据）照样会在第二、三次时超限。

**Linux（glibc）的 arena 设置**（0.3.4，`memory.tune_allocator`、`memory.trim`）：

- 起因：Linux 上扫完稳定后每项约 320–430 B，比 Windows（136–165 B）多一倍多，多出来的不是我们自己的数据。glibc 的 mmap 阈值是动态的：一个 mmap 出来的块释放后，阈值就升到这个块的大小（最高 32 MiB），此后 128 KiB–32 MiB 的分配（numpy 临时数组、名字块、原生切片的 Vec）都进各线程的 arena，夹在长期存活的块之间，空出来的还不回去。扫描时有三十来个 arena（列目录线程、rayon 线程、主线程），`malloc_trim` 只还得回一小部分（第一轮实验室：空闲 77–100 MB，还回 23–35 MB）。
- 做法：后端入口（`cli.main`，在任何扫描线程之前）调 `mallopt(M_MMAP_THRESHOLD, 4 MiB)` 和 `mallopt(M_ARENA_MAX, 4)`：固定阈值关掉动态调整（man mallopt），4 MiB 以上的块单独映射、释放即归还；arena 最多 4 个，碎片不再分散在三十几个 arena 里。扫描结束后（`_finish` 末尾，另起一个任务，不耽误扫描的完成）和看门狗看到没有扫描在跑、而私有内存比上次整理后又多了 32 MiB 时（`diag.TRIM_GROWTH`，每 15 秒看一次）调一次 `malloc_trim(0)`。
- 只对 glibc：用 `gnu_get_libc_version`、`mallopt`、`malloc_trim` 三个符号都在来认；musl 等其他 C 库、macOS、Windows 什么都不做，也不报错（有测试）。`SPACEKNIFE_GLIBC_DEFAULTS=1` 保留 glibc 自己的设置（回退开关）。
- 实测（2026-10-23，WSL2 根分区约 67–72 万项，真实后端按 Electron 的方式驱动：`bench/mem_backend.py --idle 5 --settle 30`，三臂按轮交替各 3 次，中位数 [最小–最大]；WSL 1 分钟负载 0.8–1.6）：

  | | 扫完稳定后每项 | 峰值私有内存 | 后端里的扫描用时 |
  |---|---|---|---|
  | dev 565d4db | 411 B [342–430] | 313 MiB [307–327] | 0.88 s [0.60–1.40] |
  | 这一版，`SPACEKNIFE_GLIBC_DEFAULTS=1`（原生归并和扫描后的 trim 在，glibc 设置不在） | 263 B [259–290] | 267 MiB [244–289] | 0.67 s [0.67–0.70] |
  | 这一版 | 185 B [178–198] | 220 MiB [202–238] | 0.66 s [0.57–0.83] |

  稳定后的私有内存 313 MiB [268–326] → 169 MiB [162–184]（后端空闲时 48 MiB），每项少约 55%，其中 glibc 设置单独约 −30%；扫描没有变慢。第一轮在同一台机器上量到 4 MiB 阈值、arena 上限 4 时热扫描在噪声之内，1 MiB 阈值慢 5–15%、128 KiB 慢 25–40%，所以不用更小的阈值。
- arena 上限 4 不随列目录线程数变：今天最多 16 个列目录线程，测下来没问题；第二步的载体池会把并发提高很多，落地时要在大并发下重测 `M_ARENA_MAX=4`，需要时改成随载体数变化、再定一个上限（TODO「第二步」）。

**可选：Windows 段堆。** 给后端 exe 的清单加 `<heapType>SegmentHeap</heapType>`（Windows 10 2004+；PyInstaller 打包时嵌入，或构建后用 `mt.exe` 写入）。

- 同样的实验，关掉 8 秒后，三轮累计留存从 +46 MB 降到 +30 MB，少了约三分之一，增长也更慢。
- 还没做：要先比较两种堆的扫描速度，并在 Windows 10 上验证。

## 9. 扫描后的实时监控（实测）

起因：扫完一块盘、开着实时监控时，文件一直在变（下载、编译、浏览器缓存），后端内存每隔几秒冒 0.5–0.75 GB 又落下，C: 上最高到约 2.1 GB。原因有两个：

- 详情面板每来一帧（每批文件变化一帧）就重新要一次整盘汇总，每次约 100 B/项的临时数组，几个请求还会同时算；
- 扫完收缩以后，第一次文件变化让所有列按 2 倍扩容，多出的一半一直占着。

**实测**（2026-10-21，Windows 11，W: 硬扫描 325 万项；用无界面的客户端驱动：扫描 → 静置 20 秒 → 60 秒持续文件变化（每 0.5 秒新建 3 个、改 1 个、删 1 个文件）→ 静置 20 秒，按前端的规则要汇总；数字是后端的私有内存，扫描前空闲 102 MB）：

| | 改之前 | 汇总和扩容改好（默认） | 再打开大扫描映射 |
|---|---|---|---|
| 扫描中的峰值 | 748 MB | 756 MB | 397 MB |
| 扫描结束时的峰值 | 833 MB | 599 MB | 255 MB |
| 文件变化期间的峰值 | 1298 MB | 662 MB | 303 MB |
| 文件变化之后稳定在 | 835 MB | 606 MB | 246 MB |
| 每项（稳定，减去空闲） | 225 B | 155 B | 44 B |
| 工作集（稳定） | 572 MB | 598 MB | 418 MB |
| 文件变化期间算的汇总 | 260 次 | 13 次 | 13 次 |
| 扫描写盘（C:） | — | — | 约 665 MB，一次 |
| 扫描耗时 | 6.0 秒 | 6.3 秒 | 5.1 秒 |

- 汇总分块、缓存加前端节流，让文件变化期间的锯齿基本消失（260 次整盘汇总 → 13 次，每次的临时内存从约 300 MB 降到几十 MB）；扩容不再翻倍，去掉了第一次文件变化后的那 280 MB。
- 大扫描映射把扫描数据移出私有内存。工作集也更小：扩容余量从没碰过，已经写进文件的页系统可以随时丢掉。代价是扫描后约每项 215 B 的一次写盘。
- 按每项的数字估算 C:（860 万项）：默认扫完稳定约 1.4 GB（改之前约 2 GB）；打开大扫描映射后，扫描中峰值约 0.9 GB、扫完稳定约 0.5 GB，代价是每次扫描约写盘 1.8 GB。未在真实 C: 上复测。
- 因为这次写盘，大扫描映射默认关，开关留在「设置 → 高级 → 内存」。

## 10. 前端（Electron）的内存

实测（2026-10-22，Windows 11，3840×2160 显示器、125% 缩放，窗口最大化，打开 C: 快照的树图；每个进程的私有工作集 / 私有提交，GPU 进程的显存来自 Windows 的 GPU 计数器）：

| 进程 | 私有工作集（真正占的内存） | 私有提交 | 显存 |
|---|---|---|---|
| 主进程 | 约 30 MB | 约 75 MB | — |
| 渲染进程 | 55–90 MB | 65–100 MB | — |
| GPU 进程 | 40–70 MB | 250–390 MB | 45–300 MB（跳动很大），最小化后约 13 MB |
| 网络进程 | 约 7 MB | 约 12 MB | — |

- **画面本身已经在显存里。** 每个视图有 3 张和视图一样大的画布（WebGL 画形状，两张 2D 画布画标签和叠加层），最大化时各 3440×1955 物理像素。按每像素约 28–40 B，在显存里约 190–270 MB。
- **GPU 进程那 250–390 MB「提交」大多不是内存。** 它主要是 Windows 为显存分配记的提交额度（显存被换出时要有地方放），真正占用的物理内存是它的私有工作集，只有 40–70 MB。任务管理器「详细信息」里的「内存」列就是私有工作集。
- **改进（`visual/Host.tsx`、`visual/glContext.ts`、`treemap/gl.ts`、`treemap/paint.ts`）：**
  - WebGL 不要深度和模板缓冲（`depth: false, stencil: false`），它们本来就没用到，每像素省 4–5 B 显存；
  - 叠加层（呼吸、回收站标记、类别高亮）没有东西可画时缩成 0×0，不再一直占着一张全尺寸画布；
  - 视图卸载时两张 2D 画布立刻缩成 0×0，不等垃圾回收；
  - 窗口隐藏（最小化或被完全挡住）时交还 WebGL 上下文、2D 画布缩成 0×0，再显示时恢复上下文并重画最后一帧；
  - 树图每次悬停重画时复用同一个实例数组和同一块 GPU 缓冲（只增不减，`bufferSubData` 原地更新），和火焰-极坐标图一样；原来每次悬停都新建一个数组、重新分配一次 GPU 缓冲。
- **实测效果在噪声范围内。** 同一流程（打开 C:、静止、9 秒内 315 次悬停、最小化）新旧构建对比，各进程的私有工作集和提交都在 ±10% 的波动里，显存读数在 45 MB 和 190–300 MB 之间来回跳（Chromium 合成器自己的分配和回收），看不出稳定的差别。这些改动的作用是不再白占、不再反复分配，不是降低总量。
- **为什么不能更多地挪进显存**：画布、纹理已经在显存里；留在内存里的是 Chromium 本身（V8 堆、Skia、合成器的共享内存、驱动的用户态部分），不由应用控制。关掉硬件加速不可行（三种可视化都依赖 WebGL2），只会把画面挪回内存。

## 11. 插件

插件代码默认在自己的进程里跑（[plugins.md](plugins.md)），不占后端的内存；后端为插件多占的只有下面几样，都算进看门狗的「应占」（`server/diag.py` 的 `plugin_bytes`），明细里单列一行。

- **树的只读镜像**（`plugins/image.py`）：插件要整列读树时，宿主把用到的列拷进一段共享内存，插件只读映射。约 37 B/节点（7 列）加名字；每个扫描最多留 2 个版本，没有插件在用的旧版本随即释放，插件进程停了也释放。共享内存在 Linux 上不算进程的私有内存，在 Windows 上是页面文件支撑的段：计入「应占」只是放宽看门狗的上限，不会误报。
- **插件打开的快照**（`ctx.snapshots.open`）：整份快照解压进后端，和打开一个快照一样大。每个插件同时最多 2 个，第三个回 `PLUGIN_LIMIT`；调用结束、插件调 `close()` 或插件进程停止时释放。
- **缓存**：节点字段、节点集合的掩码（每节点 1 B）、代码可视化的权重（每节点 8 B，按扫描版本只留一份）、对比原因（最多 2 万条，满了整体清空）。
- **没有插件进程在跑时**，插件系统只有注册表条目和 `plugins.json`。
- **内置插件**（`builtin.export`、`builtin.insights`）不起进程：它们的声明在第一次用到时注册（几十个注册表条目），导出格式在导出线程里直接读存储，和改成插件之前一样不多占内存。
- **`plugin check` / `call` / `render`** 在命令自己的临时数据目录里起一个不开端口的后端和一个插件进程，命令结束就全部释放，不碰正在运行的程序。

实测（`tools/bench_plugins.py`，100 万节点，同一台机器，2026-10-22）：

| | Linux（WSL2） | Windows |
|---|---|---|
| 插件进程启动 / 常驻内存 | 1.5 秒 / 50 MB | 0.7 秒 / 50 MB |
| 一次调用往返 | 0.4 ms | 0.6 ms |
| 导出 7 列共享内存（35 MB） | 20 ms | 12 ms |
| 插件第一次映射 / 之后 | 22 ms / 2 ms | 16 ms / 2 ms |
| 宿主端查询（匹配 99.9 万，取前 1000 条带路径） | 155 ms | 107 ms |
| 代码可视化第一帧（插件算权重）/ 之后每帧 | 126 ms / 1.5 ms | 111 ms / 1.2 ms |

- 插件进程的内存上限默认 1 GiB（清单最多要 4 GiB）：Windows 用作业对象，Linux 用 `RLIMIT_DATA`，macOS 由宿主按心跳报的常驻内存检查，超了就结束进程、按崩溃处理。
- 最多 8 个插件进程同时在跑，多了先停最久没用的；空闲 10 分钟的进程自动停（有订阅、流或监控器在用的不停）。
